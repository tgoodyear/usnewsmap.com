# Infrastructure (Bicep, one deployment stack per environment)

The lean hosting profile from [design doc 08](../docs/design/08-azure-infrastructure.md). In Azure it uses only PaaS: no VMs, scale sets, AKS clusters or Batch accounts, and an assigned policy denies them.

**What prod runs today (November 2026).** Public traffic is served on-prem behind Cloudflare ([`scripts/onprem/serving/`](../scripts/onprem/serving/README.md), [ADR-0029](../docs/design/adr/0029-onprem-primary-azure-failover.md)). Azure keeps the shared state (data lake, index account, Cosmos DB, OCR exchange account, scan archive), the registry, the Key Vaults, monitoring and alerts, and the API and searcher as a cold spare at zero replicas (`usnm-api-spare-ca-prod`, `usnm-qw-spare-ca-prod`) in an environment without a VNet. With `USNM_CAE_VNET`, `USNM_DATA_PRIVATE_ENDPOINTS` and `USNM_INGEST_JOBS` all `false`, prod deploys no `network`, `private-endpoints` or `ingestjobs` module, and no `id-usnm-ingest`. The on-prem hosts are Azure Arc machines; the stack grants their identities their roles (`onprem-serving`, `onprem-release`, `ocr-sync-runner`, `boinc-controller`, `searchlog-copy` and others in the settings table below).

## Separate index account (#283)

| Setting                           | Default | Effect                                                                                                                                                                                                                                                           |
| --------------------------------- | ------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `USNM_INDEX_STORAGE`              | `false` | Creates `usnmqwst{env}{suffix}` (ADR-0017) with private Blob endpoint and DNS, a parallel searcher `usnm-qw-search-ca-{env}` and container-scoped roles; the writer stages full rebuilds there while SERVE is false. **Keep on**: disabling deletes the account. |
| `USNM_INDEX_STORAGE_SERVE`        | `false` | Requires INDEX_STORAGE. After `reference/index-storage-pending.json` is verified and promoted, the API uses the new searcher; later releases publish `current.json` as usual. | `USNM_LAKE_BLOB_SOFT_DELETE_DAYS` | `3`     | Lake retention, 1–365 days. Restore `14` only after retiring or pruning old indexes; not the new account. The account is Standard LRS, Hot, flat namespace and Entra-only, with shared keys and public access off and **no versioning or blob/container soft delete**. It is not a public-policy exception; writes and deletes are logged like the lake's.

The writer job's system identity and the ingest user identity have Blob Data Contributor on its `qw-index`. The new searcher's system identity, and the API's during the transition, have Reader. There are no account-wide grants; `qw-cluster` and `qw-bench` stay in the lake. `searcher.yaml` and CI's roll-api keep each running searcher's account, so a merge with both settings absent doesn't retarget or restart the serving searcher. Switch with [Index storage cutover](../docs/operations/rebuild-and-index-storage.md#index-storage-cutover), not a normal release: Quickwit has one configured Azure account ([ADR-0021](../docs/design/adr/0021-separate-index-storage.md)).

### What this slice runs

`USNM_SEARCH_BACKEND=fixtures` (new-environment default) serves **baked synthetic fixtures** (memory backend) with the response cache in `cache/`, still exercising the managed identity, private endpoint and DNS, ingress, probes and scaling.

`USNM_SEARCH_BACKEND=quickwit` (prod; 08 §8.4.1): the API reads `current.json` and snapshots from `reference/` and queries a **Quickwit sidecar** on `127.0.0.1:7280`, which opens the file-backed metastore in `qw-index/` read-only, polling every 30 s. The API looks up each index of a new version before it goes live, so the searcher loads indexes created after it started. **Quickwit authenticates as the app's system-assigned identity**, the only one Quickwit 0.9's Azure SDK chain can use in Container Apps. Switch only after indexes and `current.json` exist; until then the API retries its first load. On the first `quickwit` deployment the role assignment lands after the app, so expect a few minutes of restarts.

`usnm-ingest run` calls `titles-sync` before each release to build the catalog it needs ([operations](../docs/operations/README.md)); `bootstrap.sh --domain` binds `usnewsmap.com`, `www.usnewsmap.com` and `api.usnewsmap.com` with managed certificates once DNS exists (§8.8).

## Naming guard and Phase 1/2 rollout

ADR-0017 Phase 1 and 2 are declared in the templates, which is **not evidence Azure has been migrated**. Prod keeps its lake, Cosmos, skeleton, OCR exchange and Phase 3 resources pinned; targets are in `names/prod.json`, the 21 remaining pins in `names/exceptions.json`.

### Protected-resource gate

Every stack create (bootstrap and teardown's partial provisions included) runs a full-payload `az deployment sub what-if` with the same parameter file and exported settings against the stack inventory. `scripts/lib/rename_guard.py` compares IDs case-insensitively and refuses if a managed storage account, Cosmos account, registry, workspace, vault, Container Apps environment, VNet, or public or private DNS zone would be ignored or deleted, even with a replacement missing. Unmanaged resources need no override. `scripts/azure/provision.sh --env prod --what-if` runs it read-only. Missing IDs, unsupported or malformed results and failed reads fail closed, with no override or retry; only `DeploymentStackNotFound` means a first deployment.

Keep loop counts independent of runtime outputs: the DNS CNAME loop always enumerates `www` and `api`, gated by the static API-deployment flag. An unresolved FQDN as loop size makes ARM skip the DNS module (as a condition, it hides existing CNAMEs); fix the plan rather than approve removing serving DNS.

Approve a removal by its exact **old** leaf name (no wildcards, resource IDs or empty values). The example is for the future Phase 3 scratch window, after its preconditions and rename PR. It is not a data migration: permissions, full what-if expansion and an approved migration are still required.

```sh
scripts/azure/provision.sh --env prod --what-if --allow-rename=stusnmsffapzy
scripts/azure/provision.sh --env prod --allow-rename=stusnmsffapzy
```

Archive-connected teardown first provisions without the archive and search cluster, which (with NFS search storage and ingest scratch off) removes the scratch account and file private-DNS zone. Confirming the environment name does **not** approve that. Inspect the live inventory and the guard output, then pass both real names:

```sh
# Set SCRATCH_ACCOUNT_NAME to the inspected account's exact old leaf name.
scripts/azure/teardown.sh --env dev \
  --allow-rename="$SCRATCH_ACCOUNT_NAME" \
  --allow-rename=privatelink.file.core.windows.net
```

Approvals cover only known Ignore/Delete results; failed, missing or unsupported plans still abort. The archive lock is restored and a rerun resumes from the saved detach marker. Partial provisions outside teardown follow the same rules.

## Retired Spot resource group

ADR-0017 Phase 1 (#309) dropped `rg-usnm-{env}-spot` and `policy-assignments-spot`: only that group's seven assignments, not the shared definitions or the platform and BOINC groups' assignments. Merging alone doesn't change Azure; existing groups need an **operator provision and cleanup**:

1. In the environment's subscription, inspect the group (prod shown). Stop if there is anything but the seven guardrail assignments; an absent group needs nothing.

   ```sh
   az group show -n rg-usnm-prod-spot
   az resource list -g rg-usnm-prod-spot -o table
   az policy assignment list --scope /subscriptions/<subscription-id>/resourceGroups/rg-usnm-prod-spot -o table
   ```

2. From merged main, `scripts/azure/provision.sh --env prod` (or the dev or experiment environment) deletes the assignments and detaches the group (`--action-on-unmanage deleteResources`; a plain what-if doesn't show this).
3. When `az stack sub show -n usnm-prod --query 'resources[].id' -o tsv` lists neither the Spot group nor its assignments, and the resource and assignment lists from step 1 are empty, run `az group delete -n rg-usnm-prod-spot` and check `az group exists -n rg-usnm-prod-spot` is `false`.

Repeat for any dev or experiment Spot group. `dev-status.sh` and the dev budget keep counting such groups until deleted. The ACI Spot alternative (08 §8.4) is not deployed.

## Deploy

One re-runnable command stands up an environment in any subscription or tenant and wires this repository to deploy it ([08 §8.9](../docs/design/08-azure-infrastructure.md)):

```sh
az login [--tenant TENANT]                 # and select the subscription, or pass --subscription
gh auth login
scripts/azure/bootstrap.sh --env prod --alert-email you@example.org --domain usnewsmap.com --ingest
```

Needs `az` 2.61+, `gh`, `curl`, **Owner** on the subscription and admin on the repository; creates no tenant-level objects. It registers providers; writes public settings to `infra/env/<env>.json` (commit it) and the rest locally ([below](#settings-and-the-deployment-stack)); deploys stack `usnm-<env>` without the API; creates GitHub Environment `prod` (restricted to `main`) and adds it to `USNM_DEPLOY_ENVIRONMENTS`; runs `ci` on `main` and waits for it; redeploys with the API; binds the apex, `www` and `api` once `--domain` is delegated (re-run after delegating); and checks `/readyz` and the site.

Options: `--subscription`, `--location` (`eastus2`), `--vnet-address-prefix` (new environments), `--repo` (default this clone's), `--domain`, `--alert-email` (alerts, and the $105 budget from this month), `--ingest` (ingest and backfill jobs), `--cleanup-legacy` (old repository variables and Static Web Apps token), `--move` (to another subscription, starting empty). Names: `prod`, `dev` or `x` plus 1–4 lowercase letters or digits. Check the result:

```sh
curl "$(scripts/azure/settings.sh --env prod --key API_URL)/v1/meta"   # "synthetic": true until the corpus is loaded
curl "$(scripts/azure/settings.sh --env prod --key API_URL)/readyz"
curl "$(scripts/azure/settings.sh --env prod --key API_URL)/v1/status"  # "pipeline": {"available": true, …} once the Cosmos role has propagated
```

Green `ci` on `main` publishes images to each environment in `USNM_DEPLOY_ENVIRONMENTS` and attests the API image, but doesn't roll the API (rolls cold-started prod's spare, #308). A `roll_api` dispatch or the `spare-roll` workflow rolls it, applying `infra/quickwit/searcher.yaml` if changed (`scripts/ci/roll-api.sh`).

**Other stack changes need a provision.** CI can only roll the app ([Container registry](#container-registry)); Bicep changes wait for an Owner to run `scripts/azure/provision.sh --env <env>` from an up-to-date `main`, flagged by CI's `stack change needs a provision` job. Index configs in `infra/quickwit/` (`pages-index.yaml`, `pages-ja-index.yaml`) ship in the ingest image instead. Pin a build with `scripts/azure/settings.sh --env prod --key USNM_IMAGE_TAG --value <commit sha>` and provision.

### Settings and the deployment stack

Settings live in three places (#295); [`env/schema.json`](env/schema.json) says which, [operations](../docs/operations/environments-and-deploys.md#settings) how to change one. A setting in the wrong place or two places stops a provision.

- **Committed:** public flags, sizes and schedules in [`env/<env>.json`](env). In CI, `scripts/lib/env_settings.py --check` rejects unknown, private, mistyped or unsorted keys, and settings `main.bicepparam` reads that the schema doesn't list.
- **Settings store:** private values in App Configuration `usnm-config-appcs-<suffix>` (stack `usnm-config`, [`settings/main.bicep`](settings/main.bicep), `SETTINGS_STORE_ENDPOINT`), one per subscription, labelled by environment, which `scripts/azure/provision.sh` reads with your sign-in ([ADR-0006](../docs/design/adr/0006-lean-hosting-profile.md)). Its admins (`scripts/azure/settings-store.sh --deploy --admins`) and last deployer can read and set every label. Before the first provision creates it, private values stay local; `scripts/azure/settings.sh --env <env> --migrate` moves them. Teardown keeps them.
- **Local:** outputs, subscription and tenant, `USNM_EXPERIMENT`, `USNM_IMAGE_TAG`, as `KEY="value"` lines in `~/.config/usnewsmap/<env>/.env` (or `$USNM_SETTINGS_HOME/<env>/.env`) when that directory exists, else the checkout's git-ignored `.azure/<env>/.env`; once the shared directory exists, checkout copies are ignored. It uses azd's layout, so azd environments carry over.

To move an environment's settings to the shared directory:

```sh
mkdir -p ~/.config/usnewsmap/dev && mv .azure/dev/.env ~/.config/usnewsmap/dev/.env
```

Provision exports every set value to `infra/main.bicepparam` (others take the defaults above), writes outputs (`API_URL`, `ACR_NAME`, …) back to the local file, and refuses while `infra/env/<env>.json` is uncommitted (`--allow-dirty` for dev experiments):

```sh
scripts/azure/settings.sh --env prod                      # show the committed and local ones
scripts/azure/settings.sh --env prod --key USNM_SEARCH_BACKEND --value quickwit   # edits infra/env/prod.json
# commit it, open a pull request, merge, pull; then, from main:
scripts/azure/provision.sh --env prod                     # deploy the stack with the new settings
```

The stack is `usnm-<env>` ([ADR-0011](../docs/design/adr/0011-deployment-stacks.md)):

- `--action-on-unmanage deleteResources`: dropped or switched-off resources (e.g. `USNM_INGEST_JOBS=false`) are deleted.
- `--deny-settings-mode denyDelete`: no one, Owners included, deletes managed resources outside it; deploy once with `--deny-settings-mode none` for an emergency delete. Undeclared resources (bootstrap's certificates, portal-made ones) are unmanaged.
- Policy definitions (`infra/guardrails.bicep`) are stack `usnm-guardrails`, deployed just before the environment's; the archival group assigns them too and `scripts/azure/archive-store.sh deploy` deploys the stack the same way. No resource is in two stacks. It also holds `budget-usnm-dev-groups` on dev's groups ($5 a month actual spend), so the budget exists while dev doesn't; it mails the last provisioned environment's `USNM_ALERT_EMAILS`, keeping its current ones when that has none (an archive deploy keeps them too).
- `scripts/azure/teardown.sh --env <env>` asks for the name, then in the recorded subscription detaches the archive and deletes the groups, custom role, GitHub Environment and, if unused, `usnm-guardrails`. `--subscription OLD` removes only the Azure copy left in an old subscription after a move.

## Web app

The API app serves the site ([ADR-0010](../docs/design/adr/0010-site-served-by-the-api.md)): the image build compiles `web/` into `/srv/site` (`USNM_SITE_DIR`) with brotli and gzip copies, so each rollout ships both. The site calls `/v1` on its own origin, needing no API URL or CORS; the API still allows the domain, `www`, the app hostname and `allowedOrigins`. There is no separate web deploy or deployment token.

## Domain (DNS)

With `USNM_DNS_ZONE_HOSTED=true` the zone is in Azure DNS (~$0.50/month):

```sh
scripts/azure/bootstrap.sh --env prod --domain usnewsmap.com
scripts/azure/settings.sh --env prod --key NAME_SERVERS   # set these four as the domain's name servers at the registrar
```

It holds an apex A record to the Container Apps environment's static IP; DigiCert-only CAA, no wildcards; `www` and `api` CNAMEs; `asuid`, `asuid.www` and `asuid.api` TXT; and no-mail SPF `v=spf1 -all`, DMARC `p=reject` and empty DKIM keys. **Copy other records in before delegating.** Bootstrap checks the delegation, then binds managed certificates (`www` and `api` validated by CNAME, the apex over HTTP), recorded as `USNM_SITE_CERT_ID`, `USNM_WWW_CERT_ID`, `USNM_API_CERT_ID` so Bicep keeps the bindings, and sets `SITE_URL` to `https://<domain>` and `API_URL` to `https://api.<domain>`. Re-run it if validation hits a record changed within the hour.

Prod's domain has been at Cloudflare since 20 October 2026 (#944): no zone, empty `NAME_SERVERS`, `USNM_DNS_ZONE` still set. [ADR-0028](../docs/design/adr/0028-cloudflare-with-azure-origin.md) proxied the apex, `www` and `api` to the Azure origin; ADR-0029 has since moved the primary origin on-prem. Proxied Azure names need DNS-01 certificates bound beforehand (Azure's managed renewal needs direct DNS); keep the private certificate-ID settings current so provisions keep those bindings. DNS, domain-verification TXT, CAA and site-verification records stay at Cloudflare.

## Container registry

Images are private in ACR Basic (`crusnm{env}…`), with no admin user or anonymous pull; apps and jobs pull by managed identity. CI pushes from `main` as `usnm-ci-id-{env}` (`id-usnm-ci-prod` before the Phase 2 provision; run `scripts/azure/bootstrap.sh` right after that rename to refresh `USNM_CI_CLIENT_ID`) over OIDC, trusted only for GitHub Environment `{env}`, with no stored secret.

CI has AcrPush and "usnm deployer" (`infra/modules/deployer.bicep`) on the group, which only rolls Container Apps (no data, keys, networking or role assignments). Group scope because Azure rejects app-scoped assignments and `az containerapp update` needs environment join; the group holds only this environment. It also has Managed Identity Operator on `id-usnm-app-{env}` alone, so it can't attach the ingest identity to the app.

The API runs `USNM_API_IMAGE_TAG`, else `USNM_IMAGE_TAG` (`main`); `USNM_SCHEDULED_INGEST_IMAGE_TAG` pins only `caj-usnm-ingest-*`. Both are public committed settings, reviewed before deployment. Prod pins both so an unrelated provision can't reset them to `:main`; move a pin by release PR.

A CI rollout doesn't move the pin (#1071), so `provision.sh` and its `--what-if` first read the API's latest ready revision (`az containerapp show`, `az containerapp revision show`; app and group from saved outputs, else the stack). They refuse before changing anything, printing the commands to continue, when:

- `USNM_API_IMAGE_TAG` pins a tag other than the served one;
- the stack's outputs name no API app or group, the app has no ready revision, or a read fails.

No comparison happens without a pin, when Azure says the API app isn't there (no stack yet, a stack deploying no API app, or no such app), or when it serves something other than ACR `usnewsmap-api:<tag>`, as with `USNM_USE_ACR` off (a note says so).

`--api-tag=live` keeps the served tag; `--api-tag=TAG` deploys that tag without reading the app, so it also gets past the second case (pass the new pin after a release PR moves it). Neither edits `infra/env/<env>.json`; fix the pin by PR. `bootstrap.sh` and `stand-up.sh` lack the flag and meet the same refusal on a stale pin, which that PR clears. `teardown.sh`'s partial provision skips the check.

Quickwit's image is pinned by digest per environment in `infra/quickwit-image.json`: v0.9.1 built in the environment's registry by `scripts/azure/build-quickwit.sh`, or, for an environment the file doesn't list, upstream v0.9.1 copied by CI ([operations](../docs/operations/search-serving.md#the-quickwit-image), ADR-0013).

## Checks

CI pins Bicep v0.48.1 (`scripts/ci/bicep-version`), lints (warnings fail) and builds every tracked `.bicep` template, and runs `scripts/ci/check-names.py`. PSRule needs Azure credentials, so it waits for the deploy pipeline. `scripts/azure/provision.sh --env <env> --what-if` uses `az stack-whatif sub create` (BOINC: the resource-group variant), requesting `PT3H` retention (Microsoft documents `PT1H`–`PT3H`).

Known What-If noise: Static Web Apps properties, diagnostic destination defaults, Azure Files soft-delete defaults. Compare with the live resource first; never suppress real delete or deny-setting diagnostics ([deployment-stacks What-If](https://learn.microsoft.com/en-us/azure/azure-resource-manager/bicep/deployment-stacks-what-if)).
