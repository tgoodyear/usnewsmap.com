# Infrastructure (Bicep, one deployment stack per environment)

The lean hosting profile from [design doc 08](../docs/design/08-azure-infrastructure.md). It uses only PaaS: there are no VMs, scale sets, AKS clusters or Batch accounts, and an assigned policy denies them.

## Separate index account (#283)

| Setting                           | Default | Effect                                                                                                                                                                                                                                                                    |
| --------------------------------- | ------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `USNM_INDEX_STORAGE`              | `false` | Create `usnmqwst{env}{suffix}` (ADR-0017), private Blob endpoint/DNS, parallel `usnm-qw-search-ca-{env}` searcher and container-scoped roles. Writer stages fresh full rebuilds there while SERVE is false. **Keep on**: disabling deletes the account through the stack. |
| `USNM_INDEX_STORAGE_SERVE`        | `false` | Requires INDEX_STORAGE. After verifying and promoting `reference/index-storage-pending.json`, switch the API to the new searcher. Later releases publish `current.json` normally. The lake searcher/sidecar and roles are retained for the old revision and rollback.     |
| `USNM_LAKE_BLOB_SOFT_DELETE_DAYS` | `3`     | Lake retention, 1–365 days. Restore `14` only after retiring or pruning its old indexes; does not affect the new account.                                                                                                                                                 |

The new account is Standard LRS, Hot, flat namespace, Entra-only, shared keys
and public access disabled, **no versioning and no blob or container soft
delete**. It is not a public-policy exception. Blob writes and deletes use
the same Log Analytics diagnostics as the lake. The writer job's system
identity and the ingest user identity have Blob Data Contributor on its
`qw-index`; the new searcher's system identity (and the API's system
identity, for the transition) have Reader. There are no account-wide data
grants. The experiment's `qw-cluster` and `qw-bench` stay in the lake. The
shared `searcher.yaml` and CI's roll-api continue preserving each running
searcher's account, so merging with both settings absent does not retarget or
restart the serving searcher.

Follow [Index storage cutover](../docs/operations/rebuild-and-index-storage.md#index-storage-cutover),
not an ordinary full release: Quickwit has one configured Azure account,
so switching pointers and readers requires the documented sequence. See
[ADR-0021](../docs/design/adr/0021-separate-index-storage.md).

### What this slice runs

With `USNM_SEARCH_BACKEND=fixtures` (the default for a new environment) the API runs on its **baked synthetic fixtures** (memory backend), and its persistent response cache is set to `cache/` on the data account. That exercises the production paths the real corpus will use: the managed identity, the Blob private endpoint and private DNS, ingress, probes and scaling.

`USNM_SEARCH_BACKEND=quickwit` switches to the production search path (08 §8.4.1):

- The API reads `current.json` and reference snapshots from `reference/`.
- It queries a **Quickwit searcher sidecar** on `127.0.0.1:7280`.
- The sidecar opens the file-backed metastore in `qw-index/` read-only, polling every 30 s. Before a new version goes live, the API looks up each index that version lists, so the searcher loads indexes created after it started.
- **Quickwit authenticates with the app's system-assigned identity.** Quickwit 0.9 uses the Azure SDK's default credential chain, which in Container Apps can only use the system-assigned identity. That identity has Blob Data Reader on `qw-index` and nothing else.

Switch only after the ingest jobs have published indexes and a `current.json`. Until then the API has nothing to serve and keeps retrying its first load. On the first deployment with `quickwit`, the identity's role assignment is created after the app, so the sidecar and API may restart a few times until the assignment propagates (a few minutes). This deployment is also where Quickwit's managed-identity auth is first confirmed against a real account (spike S-2). If it fails, the fallback is a user-delegation SAS minted by the API (08 §8.2).

Prod runs `USNM_SEARCH_BACKEND=quickwit`. The ingest job's `run` command calls `titles-sync` before each release to build the catalog it needs ([operations](../docs/operations/README.md)), and `bootstrap.sh --domain` binds the custom domains (`usnewsmap.com`, `www.usnewsmap.com`, `api.usnewsmap.com`) with managed certificates once the DNS records are in place (§8.8).

## Naming guard and Phase 1/2 rollout

ADR-0017's stateless Phase 1 changes and Phase 2 are declared in the
templates; that declaration is **not evidence that Azure has been
migrated**. Existing prod keeps its data lake, Cosmos, skeleton, OCR
exchange and Phase 3 ingest resources pinned. The reviewed target names
are in `names/prod.json`; the remaining 21 pins are in
`names/exceptions.json`.

### Protected-resource gate

Every environment stack create, including bootstrap and teardown's partial
provisions, reads the current stack inventory and runs a full-payload
`az deployment sub what-if` with the same parameter file and exported
settings. `scripts/lib/rename_guard.py` compares IDs case-insensitively and
refuses a managed storage account, Cosmos account, registry, workspace,
vault, Container Apps environment, VNet or a public or private DNS zone that
would be ignored or deleted. A removal without a replacement is protected
too. Unmanaged resources do not need an override.

`scripts/azure/provision.sh --env prod --what-if` also runs the gate without
writing anything. A missing protected ID, unsupported result, malformed
response or failed read or what-if fails closed and cannot be
overridden. Guard failures are not retried. A first deployment is
recognized only by `DeploymentStackNotFound`, not by an arbitrary failed
read.

Keep resource-loop counts independent of runtime outputs. The DNS CNAME loop
always enumerates `www` and `api`, with the root's static API-deployment flag
controlling each record. Using an unresolved API FQDN to size the loop makes
ARM skip the entire DNS module; using it as the record condition still hides
existing CNAMEs. The guard correctly refuses the missing zone. Resolve such
incomplete plans rather than approving the removal of the serving DNS.

For a deliberately approved removal, repeat the exact **old** leaf name:

```sh
scripts/azure/provision.sh --env prod --what-if --allow-rename=stusnmsffapzy
scripts/azure/provision.sh --env prod --allow-rename=stusnmsffapzy
```

This is not a data migration: the latter example is only for the future
Phase 3 scratch window, after its preconditions and rename PR. Wildcards,
resource IDs and empty overrides are refused. Permissions, complete
what-if expansion and an approved data migration remain mandatory.

Archive-connected teardown first provisions without the archive and the
search cluster before deleting the environment's groups. With NFS search
storage and ingest scratch disabled, that partial provision removes the
scratch account and file private-DNS zone. `teardown.sh` accepts and
forwards the same repeated exact-name approvals; confirming the
environment name does **not** approve protected removals. Inspect the live
inventory and partial provision's guard output, then explicitly approve
**both** old names, for example:

```sh
# Set SCRATCH_ACCOUNT_NAME to the inspected account's exact old leaf name.
scripts/azure/teardown.sh --env dev \
  --allow-rename="$SCRATCH_ACCOUNT_NAME" \
  --allow-rename=privatelink.file.core.windows.net
```

Use the actual managed names, not an empty variable or assumed prod
names. The approvals apply only to known Ignore/Delete results; failed,
missing or unsupported plans still abort before stack creation or
deletion. The archive lock is restored on failure, and a rerun resumes
the detach using its saved marker. No wildcard or automatic teardown
exemption is provided; a partial provision outside teardown follows the
same rules.

### Owner steps for the stateless Phase 1 and Phase 2 names

1. Before provisioning, reconcile the live stack inventory with the
   **pre-rollout** map (`git show 84f887c8:infra/names/prod.json`), then review
   its diff to the current target map. Compare actual resource IDs; account
   for optional resources, GUID children and display properties separately.
   `prod.json` is compiler-derived, not an authenticated live inventory.
   The 15 October read-only inventory found no production archive endpoint,
   so `archiveEndpoint` now uses the conventional name; recheck before
   provisioning if production begins using `USNM_ARCHIVE_ACCOUNT`.
2. Remove the unmanaged `Failure Anomalies - appi-usnm-prod` smart-detector
   rule **before** provisioning. Azure allows only one
   `FailureAnomaliesDetector` rule per Application Insights component, so
   while it exists the stack's `usnm-api-failures-alert-prod` can't be
   created and every provision attempt fails with "Only a single
   FailureAnomaliesDetector alert rule can be define for the same
   resource". The old rule was created by Azure, not the stack, and
   notifies the default "Application Insights Smart Detection" action
   group. Save it, then delete it; failure-anomaly alerting is off until
   the provision below recreates it:

   ```sh
   az resource show -g rg-usnm-prod --resource-type Microsoft.AlertsManagement/smartDetectorAlertRules \
     -n 'Failure Anomalies - appi-usnm-prod' --api-version 2021-04-01 > failure-anomalies-old.json
   az resource delete -g rg-usnm-prod --resource-type Microsoft.AlertsManagement/smartDetectorAlertRules \
     -n 'Failure Anomalies - appi-usnm-prod' --api-version 2021-04-01
   ```

   It was not stack-managed; removing a Bicep declaration cannot delete it.

3. Use Bicep CLI v0.48.1, the repository pin in `scripts/ci/bicep-version`. Pause CI deploys
   while provision and bootstrap run (serving is unaffected). Reset
   `USNM_BUDGET_START` to the first of the current month, commit that
   public setting through a PR, and provision from the approved main:

   ```sh
   scripts/azure/settings.sh --env prod --key USNM_BUDGET_START --value "$(date -u +%Y-%m-01)"
   # commit/review/merge any settings change, then pull main
   scripts/azure/provision.sh --env prod --what-if
   scripts/azure/provision.sh --env prod
   scripts/azure/bootstrap.sh --env prod
   ```

   Run bootstrap immediately: replacing `id-usnm-ci-prod` with
   `usnm-ci-id-prod` changes `CI_CLIENT_ID`; bootstrap rewrites the GitHub
   Environment's `USNM_CI_CLIENT_ID`. Resume CI and verify a successful push
   and rollout with the new identity. Do not leave the old client ID in CI.

4. Verify the actual deployed alert inventory and queries, the site web
   test, the `usnm-core-ag-prod` receivers and short name `usnm-prod`, the
   `usnm-core-budget-prod` start/notifications, and workbook titles
   `usnm pipeline (prod)` and `usnm API (prod)`. Do not use the issue's old
   alert count: later changes added and consolidated rules. The three OCR
   alert names also become conventional. The old history of fired alerts
   and availability results remains in the same workspace; the recreated
   rules have new resource IDs. Workbook GUIDs and custom role IDs and

## Retired Spot resource group

ADR-0017 Phase 1 (#309) removes `rg-usnm-{env}-spot` and its
`policy-assignments-spot` module from the template. It removes only that
group's seven policy assignments, not the shared policy definitions or the
assignments on the platform and BOINC groups. New environments never create
the Spot group. Existing environments need an **operator provision and
cleanup after merge**; merging code alone does not change Azure.

1. Select the environment's subscription and inspect the old group before
   provisioning. For prod:

   ```sh
   az group show -n rg-usnm-prod-spot
   az resource list -g rg-usnm-prod-spot -o table
   az policy assignment list --scope /subscriptions/<subscription-id>/resourceGroups/rg-usnm-prod-spot -o table
   ```

   Expect no workloads and only the seven project guardrail assignments.
   Stop if it holds anything else; do not delete another workload. A group
   that is already absent needs no cleanup.

2. From merged main, run `scripts/azure/provision.sh --env prod` (substitute the
   environment for dev or an experiment). The stack's
   `--action-on-unmanage deleteResources` deletes the old assignments and
   detaches, rather than deletes, the resource group. A deployment what-if
   alone does not enumerate these stack-unmanage deletions.
3. Check that `az stack sub show -n usnm-prod --query 'resources[].id' -o tsv`
   contains neither the Spot group nor its assignments. Repeat the resource
   and policy-assignment lists above; both must be empty. Then, and only
   then, run `az group delete -n rg-usnm-prod-spot` and confirm
   `az group exists -n rg-usnm-prod-spot` returns `false`.

Repeat for any previously deployed dev or experiment Spot group.
`dev-status.sh` and the dev budget deliberately still discover and cost
these legacy groups until cleanup is complete; a detached Spot group must
not make an environment appear empty. The ACI Spot alternative remains
documented in design doc 08 §8.4, but is not deployed.

## Deploy

One command stands up an environment in any subscription or tenant, wires this repository to deploy it, and can be re-run at any time to bring it up to date ([08 §8.9](../docs/design/08-azure-infrastructure.md)):

```sh
az login [--tenant TENANT]                 # and select the subscription, or pass --subscription
gh auth login
scripts/azure/bootstrap.sh --env prod --alert-email you@example.org --domain usnewsmap.com --ingest
```

Prerequisites: `az` (2.61 or later), `gh` and `curl`; **Owner** on the subscription (the deployment creates role assignments and policy definitions); admin on the GitHub repository (it creates the GitHub Environment and its variables). No tenant-level objects are created.

What it does:

1. Registers the resource providers.
2. Writes the environment's settings: the public ones to `infra/env/<env>.json` (commit it), the rest to the local file ([Settings and the deployment stack](#settings-and-the-deployment-stack)).
3. Deploys the stack `usnm-<env>`: everything except the API, which has no image yet.
4. Creates the GitHub Environment `prod`, restricted to `main`, with its variables, and adds it to `USNM_DEPLOY_ENVIRONMENTS`.
5. Runs `ci` on `main` (every time, so the registry holds the current `main`) and waits for that run.
6. Deploys the stack again on the registry, which deploys the API.
7. Once the registrar delegates `--domain` to the zone, binds the apex, `www` and `api` to the API app, which serves the site and the API, with managed certificates (re-run it after delegating). The retired Static Web App is not managed or deleted by bootstrap.
8. Checks the API's `/readyz` and the site.

Options: `--subscription`, `--location` (default `eastus2`), `--vnet-address-prefix` (the VNet's private block, `USNM_VNET_ADDRESS_PREFIX`; needed for a new environment), `--repo` (default: this clone's), `--domain`, `--alert-email` (alerts, and the $80 budget from this month), `--ingest` (the ingest and backfill jobs), `--cleanup-legacy` (removes the repository-level variables and the old Static Web Apps token secret from before per-environment deployment), `--move` (lets an existing environment move to another subscription, starting there with no data). Environment names are `prod`, `dev` or `x` plus 1–4 lowercase letters or digits (ADR-0017).

Check the result:

```sh
curl "$(scripts/azure/settings.sh --env prod --key API_URL)/v1/meta"   # "synthetic": true until the corpus is loaded
curl "$(scripts/azure/settings.sh --env prod --key API_URL)/readyz"
curl "$(scripts/azure/settings.sh --env prod --key API_URL)/v1/status"  # "pipeline": {"available": true, …} once the Cosmos role has propagated
```

After that, every green `ci` run on `main` publishes the images to each listed environment and rolls its API app, which carries the site, onto the commit. The rollout also applies the Quickwit searcher's config, `infra/quickwit/searcher.yaml`, when the running one differs (`scripts/ci/roll-api.sh`), so a change to that file goes live on merge.

**Other stack changes are not deployed by a merge.** CI's identity can only roll the app ([Container registry](#container-registry)), so a change to the Bicep (resources, settings, scale rules, alerts, workbooks) waits until someone with Owner runs `scripts/azure/provision.sh --env <env>` from an up-to-date `main`. The index configs in `infra/quickwit/` (`pages-index.yaml`, `pages-ja-index.yaml`) are not stack changes: they are compiled into the ingest image, which every merge publishes. CI says so on the run: the `stack change needs a provision` job adds a warning and the commands to the run's summary. To pin a specific build instead, run `scripts/azure/settings.sh --env prod --key USNM_IMAGE_TAG --value <commit sha>` (default `main`) and `scripts/azure/provision.sh --env prod`.

### Settings and the deployment stack

An environment's settings live in three places (#295); [`env/schema.json`](env/schema.json) says which setting goes where, and [operations](../docs/operations/environments-and-deploys.md#settings) shows how to change each:

- **Committed:** the public choices (flags, sizes, caps, schedules) in [`env/<env>.json`](env/), so a change goes through a pull request and its history is git's. `scripts/lib/env_settings.py --check` (CI) fails on an unknown setting, a private one, a wrong type or unsorted keys, and on a setting `main.bicepparam` reads that the schema doesn't list.
- **The settings store:** the private ones (addresses, principals, resource ids) in one App Configuration store for every environment in the subscription, `usnm-config-appcs-<suffix>` (its own stack `usnm-config`, [`settings/main.bicep`](settings/main.bicep); its endpoint saved as `SETTINGS_STORE_ENDPOINT`). Each environment's settings sit under its own label, which `scripts/azure/provision.sh` reads with your sign-in ([ADR-0006](../docs/design/adr/0006-lean-hosting-profile.md)). The operators in the store's admin list (`scripts/azure/settings-store.sh --deploy --admins`) and the account that last deployed it can read and set them; the role covers every label. The first provision in a subscription creates the store; until then private settings stay in the local file, and `scripts/azure/settings.sh --env <env> --migrate` then moves them. An environment's teardown keeps them.
- **Local:** everything else, the stack's outputs, the subscription and tenant, and what the scripts keep (`USNM_EXPERIMENT`, `USNM_IMAGE_TAG`), in the local file below.

A setting in the wrong place, or in two, stops a provision. The local file is `KEY="value"` lines: `~/.config/usnewsmap/<env>/.env` (or `$USNM_SETTINGS_HOME/<env>/.env`) when that directory exists, so every checkout and worktree reads the same settings; otherwise it's the checkout's own `.azure/<env>/.env`, which is git-ignored. Once the shared directory exists, a copy in a checkout is ignored (the scripts say so). To move an environment's settings there:

```sh
mkdir -p ~/.config/usnewsmap/dev && mv .azure/dev/.env ~/.config/usnewsmap/dev/.env
```

The file uses the layout azd used, so environments created with azd carry over. `infra/main.bicepparam` reads the settings from the environment (provision exports those with a value, from all three places; the rest take the defaults above), and the template's outputs (`API_URL`, `ACR_NAME`, …) are written back to the local file after each deployment.

```sh
scripts/azure/settings.sh --env prod                      # show the committed and local ones
scripts/azure/settings.sh --env prod --key USNM_SEARCH_BACKEND --value quickwit   # edits infra/env/prod.json
# commit it, open a pull request, merge, pull; then, from main:
scripts/azure/provision.sh --env prod                     # deploy the stack with the new settings
```

`provision.sh` refuses while `infra/env/<env>.json` has uncommitted changes; `--allow-dirty` is for experiments in dev.

Everything is one **deployment stack** at subscription scope, `usnm-<env>` ([ADR-0011](../docs/design/adr/0011-deployment-stacks.md)):

- **Removed from the template means removed from Azure.** Each deployment runs with `--action-on-unmanage deleteResources`, so a resource dropped from the Bicep (or switched off by a setting, such as `USNM_INGEST_JOBS=false`) is deleted, not left running.
- **Nothing the stack manages can be deleted outside it.** `--deny-settings-mode denyDelete` puts a deny assignment on every managed resource, the resource groups included, that blocks deletes by anyone, Owners too. Changes still go through the stack. To delete by hand in an emergency, deploy once with `--deny-settings-mode none`.
- Resources the template doesn't declare (the certificates bootstrap binds, anything made in the portal) aren't managed: the stack neither protects nor deletes them.
- The guard-rail policy definitions every environment in the subscription assigns (`infra/guardrails.bicep`) are a stack of their own, `usnm-guardrails`, deployed just before the environment's. The archival account's group assigns them too, and `scripts/azure/archive-store.sh deploy` deploys the stack the same way. Two stacks never manage the same resource. The same stack holds the budget on dev's groups, `budget-usnm-dev-groups` (an alert at $5 a month of actual spend, [Dev environment lifecycle](../docs/operations/environments-and-deploys.md#dev-environment-lifecycle)), so it exists while dev doesn't. It mails the alert recipients (`USNM_ALERT_EMAILS`) of the environment provisioned last, or keeps the ones it has when that environment has none (an archive deploy keeps them too).
- `scripts/azure/teardown.sh --env <env>` deletes an environment: its resource groups, its custom role, its GitHub Environment, and the guard-rail stack (`usnm-guardrails`, the policy definitions) when neither another environment in the subscription nor the archival account uses it. It asks for the name first, and works in the environment's recorded subscription. `--subscription OLD` removes only the Azure copy left in an old subscription after a move. An environment that uses the archival account is detached from it first ([Dev environment lifecycle](../docs/operations/environments-and-deploys.md#dev-environment-lifecycle)).

## Web app

The API app serves the site ([ADR-0010](../docs/design/adr/0010-site-served-by-the-api.md)). The API image's build compiles `web/` into `/srv/site` (`USNM_SITE_DIR`), with brotli and gzip copies of each text file. So every image `ci` publishes carries the site, and each rollout ships both together. The site calls `/v1` on its own origin, so it needs no API URL and no CORS. The API still allows the domain, `www`, the app's own hostname and any `allowedOrigins` for other callers. There is no separate web deploy and no deployment token.

## Domain (DNS)

The zone for the site's domain lives in Azure DNS (~$0.50/month):

```sh
scripts/azure/bootstrap.sh --env prod --domain usnewsmap.com
scripts/azure/settings.sh --env prod --key NAME_SERVERS   # set these four as the domain's name servers at the registrar
```

The zone holds:

- the apex: an A record to the Container Apps environment's static IP, plus CAA records allowing only DigiCert (the managed certificates' CA), with no wildcards;
- `www` and `api`: CNAMEs to the API app;
- `asuid`, `asuid.www` and `asuid.api`: the TXT records Container Apps checks before binding each name.

It also carries over the domain's no-mail records (SPF `v=spf1 -all`, DMARC `p=reject`, and an empty key for every DKIM selector), as they were on the previous DNS host. **Before switching name servers, copy any other records the domain still needs into the zone**: once delegated, only the zone's records resolve. Once the registrar delegates the domain, `scripts/azure/bootstrap.sh` binds the names (it checks the delegation first, and re-running it later finishes the job):

- Each name gets a free managed certificate from the Container Apps environment. `www` and `api` are validated by their CNAMEs, and the apex over HTTP through its A record.
- The certificate ids are recorded as `USNM_SITE_CERT_ID`, `USNM_WWW_CERT_ID` and `USNM_API_CERT_ID`. Bicep declares the bindings from them, so later deployments keep them.
- `SITE_URL` then becomes `https://<domain>`, and `API_URL` becomes `https://api.<domain>`.
- If a name's DNS record changed within the last hour, resolvers may still hold the old one and validation can fail. Re-run bootstrap later.

Prod's domain has been hosted at Cloudflare since 20 October 2026 (#944), with `usnewsmap.com`, `www` and `api` as DNS-only records, so its settings set `USNM_DNS_ZONE_HOSTED=false`: the stack deploys no zone and `NAME_SERVERS` is empty. `USNM_DNS_ZONE` stays set, because the custom domains, managed certificates, CORS origins and availability tests come from it. The records the zone held (the apex A record, the `www` and `api` CNAMEs, the `asuid` TXT records, CAA allowing DigiCert, and the no-mail and site-verification TXT records) are kept at Cloudflare by hand. Managed-certificate renewal needs only that the names keep resolving straight to the app, not Azure DNS ([free certificate requirements](https://learn.microsoft.com/azure/container-apps/custom-domains-managed-certificates#free-certificate-requirements)). A proxied (orange-cloud) record would put Cloudflare in between and block renewal.

## Container registry

Images are private, in ACR Basic (`crusnm{env}…`), with no admin user and no anonymous pull. The apps and jobs pull with their managed identities.

CI pushes from `main` as `usnm-ci-id-{env}`, signing in with OIDC (`id-usnm-ci-prod` before the Phase 2 provision). That identity trusts only jobs in the GitHub Environment `{env}`, and no secret is stored anywhere. `scripts/azure/bootstrap.sh` sets it all up and must run immediately after the identity rename to refresh `USNM_CI_CLIENT_ID`.

The CI identity's rights are AcrPush on its registry, and a custom role, "usnm deployer", on its resource group (`infra/modules/deployer.bicep`). The role can roll Container Apps onto new images (which carry the site too), and nothing else: no data, keys, networking or role assignments. It's scoped to the group because Azure rejects role assignments scoped to a Container App itself, and because `az containerapp update` also needs join rights on the app's environment; the group holds only this environment. The update also needs assign rights on the app's identity: CI has Managed Identity Operator on `id-usnm-app-{env}` alone, never on the group, so it can't attach the ingest identity (and its data access) to the app.

Each stack deployment sets the API image to `USNM_API_IMAGE_TAG`, falling back to
`USNM_IMAGE_TAG` (default `main`). `USNM_SCHEDULED_INGEST_IMAGE_TAG` similarly
pins only the primary `caj-usnm-ingest-*` job; backfill, OCR sync and other
ingest-image jobs still follow `USNM_IMAGE_TAG`. Both overrides are public
committed settings in `infra/env/<env>.json`, reviewed before deployment.
Production records its existing independent API and primary-ingest tags so a
provision for an unrelated workbook or output change does not silently replace
either with `:main`. Update the relevant pin through a release PR when
intentionally rolling that workload; a CI app rollout does not update these stack
pins.

The Quickwit image (the searcher sidecar, and the base of the ingest image) is pinned by digest per environment in `infra/quickwit-image.json`: our build of v0.9.1, which `scripts/azure/build-quickwit.sh` builds in the environment's registry, or for an environment the file doesn't list, upstream v0.9.1, which CI copies in ([operations](../docs/operations/search-serving.md#the-quickwit-image), ADR-0013).
