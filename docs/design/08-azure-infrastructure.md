# 08: Azure Infrastructure & Delivery

Azure holds the shared state, a cold spare of the API and searcher, the registry, the Key Vaults and the monitoring. Since 31 October 2026 public traffic is served on-prem behind Cloudflare ([03 §3.3](03-architecture-overview.md#33-deployment-today-november-2026), [ADR-0029](adr/0029-onprem-primary-azure-failover.md)), and the ingest commands, releases and OCR pickup run on on-prem hosts that reach Azure as Azure Arc machines. Everything in Azure is in Bicep (§8.5). The template still builds the original layout (a VNet-integrated environment with private endpoints, an API app with a Quickwit sidecar, and the ingest and backfill jobs) behind settings that prod turns off: `USNM_CAE_VNET`, `USNM_DATA_PRIVATE_ENDPOINTS` and `USNM_INGEST_JOBS` are `false` in [`infra/env/prod.json`](../../infra/env/prod.json). [`infra/README.md`](../../infra/README.md) lists every module and setting.

### 8.1.1 Resource logs and maintenance windows

Every resource with resource logs sends them to `log-usnm` through a diagnostic setting declared in [`infra/modules/diagnostics.bicep`](../../infra/modules/diagnostics.bicep). What the on-prem OCR hosts control goes to their own workspace instead (§8.3.1). An audit policy flags any resource of those types without a setting (§8.5). The archival account is exempt (`usnm-archive-no-diagnostics`), because every workspace belongs to an environment and goes with its teardown, while the account outlives them.

| Resource                                               | Categories                                                                                                                   |
| ------------------------------------------------------ | ---------------------------------------------------------------------------------------------------------------------------- |
| Log Analytics, registry; storage queue, table and file | All (`allLogs`). The exchange account's queue logs go to the OCR workspace                                                   |
| Container Apps environment                             | `ContainerAppConsoleLogs`, `ContainerAppSystemLogs` (`appLogsConfiguration` is `azure-monitor`, so no workspace key is used) |
| Cosmos DB                                              | `ControlPlaneRequests`                                                                                                       |
| Blob service of each storage account                   | `StorageWrite`, `StorageDelete`, into `StorageBlobLogs` on the Auxiliary plan                                                |
| The OCR hosts' data collection rule                    | `LogErrors`, into `DCRLogErrors` in the OCR workspace                                                                        |

- **Per-request categories are left out** because they would fill the daily cap and some carry search text: blob reads (every split a searcher reads), Cosmos `DataPlaneRequests`, and Container Apps HTTP logs, which hold each request's query string. The API reports its own requests without paths or query strings (§8.1.2). Writes, deletes and control-plane changes are the audit trail.
- **Also left out:** Application Insights' own resource logs (it is workspace-based, so they would store every row twice) and metrics-only resources, whose platform metrics Azure Monitor keeps 93 days at no cost.
- **Retention.** The workspace keeps 30 days (31 are included in the ingestion price, so less saves nothing). The Application Insights tables keep 90 days. `CDBControlPlaneRequests` and `ContainerRegistryRepositoryEvents` are kept 365 days (30 queryable, then long-term retention); they hold about 5 MB a month.
- **Daily cap.** When the cap is reached, everything on the Analytics and Basic plans stops until the workspace's daily reset: logs, telemetry and every log-based alert. In the Azure-serving days a normal prod day was about 53 MB (30 September to 9 October 2026), and #231 cut about 13 MB of duplicate rows from that.
- **Blob writes on the Auxiliary plan.** `StorageBlobLogs` has a row of about 1.2 KB per write or delete request, so its volume follows the bulk jobs; on 7 October 2026 it filled the cap and stopped all logging. On the Auxiliary plan (`infra/modules/monitoring.bicep`) the cap doesn't apply. Auxiliary rows cost $0.15/GB and aren't covered by the free 5 GB. Nothing queries the table; it stays queryable with full KQL for its 30 days but can't feed a log alert.
- **Cap alert.** _Log Analytics daily cap reached_ (severity 1) fires on the workspace's own `OverQuota` event in `_LogOperation`, which is free and keeps being written when the cap stops everything else. It is checked every 15 minutes and sends one email per event.
- **Bicep writes the settings, not a `deployIfNotExists` policy.** The template chooses categories per resource, while the built-in initiatives enable whole category groups that include the per-request logs. The policy is audit-only and catches drift.

**Maintenance windows: none apply.** Customer-scheduled maintenance covers VMs, Azure SQL and some gateways, none of which this stack has. Container Apps planned maintenance applies only to Dedicated workload profiles, which prod doesn't run, and is billed on the Dedicated plan management meter (about $73 a month).

### 8.1.2 Logs, telemetry and alerts: ingest jobs and API

`crates/usnm-telemetry` holds the setup that the API (`usnm-api`), the ingest commands (`usnm-ingest`) and the OCR pickup share. Each exports OpenTelemetry traces and metrics to Application Insights with an Entra token for `https://monitor.azure.com/` (Monitoring Metrics Publisher on the component). The connection string only names the ingestion endpoint; with local auth off it authenticates nothing. In Azure the identity is the app's managed identity; on-prem it is the host's Arc machine identity (`scripts/onprem/ingest-env.sh`, `scripts/onprem/serving/gen-env.sh`). Console lines go to `ContainerAppConsoleLogs` in Azure and to journald on-prem.

**The ingest commands.** `usnm-ingest` writes JSON lines; every failed command ends with one `command failed` line. Spans: `release`, and one `curate` per batch. Metrics: `ingest.docs_sent`, `ingest.bytes_sent`, `ingest.retries`, `curate.batches`, `curate.pages`, `curate.duration_seconds`, `release.docs_expected`, `work_disk_free_bytes` and `ingest.command_failures` (by command and outcome). The pipeline forwards the Quickwit writer's warnings, errors and readiness lines as `target: quickwit`; if the writer fails to start, its last 50 lines go into the error.

- A release logs `release progress` every 30 s and after each batch: documents sent and expected, MB sent, documents per second, 429/503 retries, the work directory's free disk, and the memory of the pipeline and of the writer.
- A curate worker logs each batch's stages in the batch's span (`claimed`, `waiting for a download slot`, `download slot granted`, `download started`, `archive read`, `issue items written`) and one outcome: `curated`, `curation failed`, `curation timed out` or `throttled`. While it holds a batch, a separate task logs `curate progress` every 60 s with the stage (`waiting_for_slot`, `connecting`, `downloading`, `issues`, `committing`), the seconds in it, and the MB, pages and parts so far, so a stuck batch still reports where it is stuck. A batch unfinished 45 minutes after its download slot was granted is abandoned and re-queued (45 minutes is 3.6 times the p99 of a batch in the September 2026 backfill). The worker renews its 2 h lease when the slot is granted, so the limit ends inside the lease.
- The ingest-job alerts (`infra/modules/ingest-alerts.bicep`: job failed, ingest not progressing, release stalled, backfill stalled, backfill replica silent) and the _usnm pipeline_ workbook read `ContainerAppConsoleLogs` and exist only with `USNM_INGEST_JOBS`, so prod has neither. The on-prem OCR pickup has its own alerts, from the metrics it sends (`infra/modules/ocr-sync-alerts.bicep`: a failed run, no run for 2 hours, output left in `ocr-out` over 72 hours; [operations](../operations/onprem-ocr.md)). Saved queries are in `ops/queries/`; `scripts/azure/logs.sh --env <env> --query-name <query> [--span <timespan>]` runs one with the operator's Entra sign-in.

**The API** reports under the cloud role `usnm-api`, from either origin:

- **Requests.** Every request except `/healthz` and `/readyz` is one `AppRequests` row: name `<method> <route template>` (`GET /v1/aggregate`; `(site)` for the site's files, `(no route)` for an unknown API path), result code, duration, and success (false only for a 5xx). `usnm.index_version` is the version the response came from; `usnm.problem` is an error response's problem `type`, so the server-error alert can leave out slow searches. No path, query string or client address is recorded (09 §9.4.2). Warnings and errors logged during a request go to `AppTraces`, linked to it. There is no console line per request.
- **Metrics** (`AppMetrics`, every 30 s):

  | Metric                                                                                                                        | Dimensions and meaning                                                                                                                                                                                                                               |
  | ----------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
  | `api.backend_duration_seconds`                                                                                                | Search backend time for aggregate and hits, by `endpoint` and `outcome`                                                                                                                                                                              |
  | `api.cache_lookups`                                                                                                           | By `layer` (`memory`, `blob`) and `result` (`hit`, `miss`)                                                                                                                                                                                           |
  | `api.rejected_queries`                                                                                                        | By `reason`: `syntax`, `bad_parameter`, `unsupported`, `too_broad`, `rate_limited`, `bad_beacon`                                                                                                                                                     |
  | `api.slow_searches`                                                                                                           | Searches longer than a visitor waits, by `endpoint` and `outcome` (`ok`, `timeout`, `error`, `abandoned`), and searches refused because the slot queue was full or waited out (`busy`, 06 §6.6)                                                      |
  | `api.search_queue_wait_seconds`                                                                                               | Each search's wait for a computation slot, by `endpoint` and `outcome` (`slot`, `busy`)                                                                                                                                                              |
  | `api.reference_reloads`                                                                                                       | By `outcome`: `published`, `failed`                                                                                                                                                                                                                  |
  | `api.prewarm_duration_seconds`, `api.prewarm_queries`, `api.prewarm_query_seconds`                                            | Cache warm-up runs by `trigger` (`startup`, `publish`, `searcher_restart`), queries by `outcome`, and each query by `endpoint` and `source` (`cache`, `computed`; 06 §6.5)                                                                           |
  | `api.beacons`                                                                                                                 | Page views by `outcome`: `forwarded`, `bot`, `opted_out` (DNT or GPC), `other_origin`, `dropped`, `off`                                                                                                                                              |
  | `api.index_version`                                                                                                           | 1, with the serving version in `index_version`                                                                                                                                                                                                       |
  | `api.searcher_cache_bytes`, `_items`, `_hits`, `_misses`, `_evictions`                                                        | The Quickwit searcher's caches by `cache` (`split_footer`, `fast_field`, `partial_request`, `predicate`): gauges for what each holds, counts since the last report                                                                                   |
  | `api.searcher_pool_tasks`, `api.searcher_runtime_threads`, `api.searcher_runtime_busy_ms`, `api.searcher_runtime_capacity_ms` | The searcher's thread pools (`pool`: `search`, `small_tasks`; `state`: `ongoing`, `pending`) and Tokio runtimes (`main`, which downloads and opens splits), to tell a search waiting on the search pool's cores from one waiting on downloads (#251) |
  | `api.search_log`, `api.search_log_writes`                                                                                     | The search log (06 §6.8): searches by `outcome` (`queued`, `dropped`, `written`, `lost`, `opted_out`, `bot`, `other_origin`) and blob writes by `op` and `outcome`. No search text                                                                   |

  The API reads the searcher's Prometheus endpoint (`USNM_QUICKWIT_URL/metrics`) every `USNM_SEARCHER_METRICS_SECS` (60). Those reads are also how it notices a searcher restart and warms the searcher again (06 §6.5), so `0` turns that off too. It reports a cache gauge when it changes or every 15 minutes, the pool and runtime gauges at every read, and counts only when they aren't zero. Counters that go down log `the searcher restarted; its counters start again from 0`. Busy over capacity, summed over a span, is the runtime's busy share. A remote searcher's rows carry `Properties["usnm.searcher"]`, the origin of `USNM_QUICKWIT_URL` without credentials, path or query (#364).

- **Page views** (`AppPageViews`, cloud role `usnm-web`). The site posts one per page to `POST /v1/beacon` (06 §6.3.7, 07 §7.8); the API forwards it as a `PageView` envelope, batched for up to 5 s or 100 views. Each has the page name, the page's path only, and `referrer_origin`, `utm_*`, `title`, `device_type` and `browser`. The visitor's address goes only in the `ai.location.ip` tag, from which ingestion derives city, region and country before storing `ClientIP` as `0.0.0.0`.
- **Cache warm-up** (06 §6.5): one `warm-up finished` line per run with its counts and timings; `slow warm-up query` for a query of 1 s or more and `warm-up query failed` for a failure, neither with the query string.
- **Searcher logs.** Quickwit logs at `quickwit=info`, except `quickwit_serve::search_api` and `quickwit_search` at `warn`, because at info they log every search's query, which is the visitor's search text (09 §9.4.2). Azure sets `RUST_LOG` in `infra/modules/containerapp.bicep`, and `gen-env.sh` copies it for on-prem.
- **Queries:** `scripts/azure/logs.sh --env <env> --query-name` `api-requests` (requests, 4xx, 5xx and p50/p95 by route), `api-errors` (5xx by route, and the warning and error lines; a failed search names its cause by category, never Quickwit's own text, which can echo the query), `searcher-health`, `searcher-caches` and `traffic` (page views by day, page, referrer, campaign, country, device and browser).
- **Alerts** (`infra/modules/api-alerts.bicep`). The log alerts read only `usnm-api` rows from the API's own component (`_ResourceId`), since anyone with Monitoring Metrics Publisher can write rows under any role name. None is checked more often than every 15 minutes (#308):
  - _API server errors_ (severity 2): at least 8 5xx responses in 15 minutes that are also over 2% of requests, or at least 15 search timeouts and busy refusals. Split by `Kind` and `TopRoute`.
  - _Slow aggregate searches_ (severity 3): p95 of `/v1/aggregate` over 3 s in 15 minutes, with at least 20 requests and 3 of them over 3 s.
  - _Searches longer than a visitor waits_ (severity 3): at least 3 in an hour from `api.slow_searches`.
  - _Search capacity: searches waiting for a slot_ (severity 4, #238): on each of the last two days, the p90 wait for a computation slot over 3 s, with at least 20 such searches a day. Checked daily; it emails every day the condition holds. With the replica CPU alert (below) it was the signal for revisiting a second searcher.
  - _Search capacity: replica CPU_ (severity 4): the app's `UsageNanoCores` averaging over 3 vCPU for 6 hours. Deployed only where the API keeps a replica running (`USNM_API_MIN_REPLICAS` above 0), so not in prod since the spare went to zero replicas.
  - _Site unavailable_ (severity 1): a standard availability test of `https://{domain}/` from three locations, firing when 2 fail. The template deploys it only while the custom domain's certificate is bound to an Azure app (`siteUrl` in `infra/main.bicep`); UNVERIFIED whether prod still has it now that no Azure app binds the domains (§8.8). On-prem's health is watched by the Worker's heartbeat ([ADR-0029](adr/0029-onprem-primary-azure-failover.md)) and Cloudflare's tunnel health alert.

**Workbooks** (`infra/modules/workbooks.bicep`, definitions in `infra/workbooks/`): _usnm API_ (requests, latency by route, backend time, cache hit rates, the searcher's caches, rejected queries, warm-up runs, reference loads, a 14-day search capacity section, and a Traffic section from `AppPageViews`), _usnm pipeline_ (only with the ingest jobs) and _usnm OCR nodes_ (over the OCR workspace). Opening one runs its queries; they have no charge of their own. Backend time shows mean and max, because `AppMetrics` keeps a histogram's sum, count, min and max per export, not its buckets.

### Separate Quickwit account (#283, opt-in)

The index lives in its own account, `usnmqwst{env}{suffix}`, apart from the lake's system-of-record data ([ADR-0021](adr/0021-separate-index-storage.md)). Prod has run on it since the #283 cutover (`USNM_INDEX_STORAGE` and `USNM_INDEX_STORAGE_SERVE` both `true`), and the lake's old `qw-index` versions were purged under #245. The account is Hot, LRS, flat namespace and Entra ID only, with no blob or container soft delete and no versioning, since everything in it can be rebuilt. Turning `USNM_INDEX_STORAGE` off deletes the account. Quickwit URIs stay `azure://qw-index`; `storage.azure.account` in the searcher's YAML and the writer's `QW_AZURE_STORAGE_ACCOUNT` pick the account, because one Quickwit process reads one account. The cutover, rollback and pruning steps are in [operations](../operations/rebuild-and-index-storage.md#index-storage-cutover).

**No shared keys anywhere.** Local (key) auth is off on every service that has the switch, and policy denies turning it back on: storage (`allowSharedKeyAccess: false`), Cosmos (`disableLocalAuth`), Log Analytics, Application Insights and the registry (no admin user, no anonymous pull). No SAS of any kind, user-delegation included. `scripts/ci/no-shared-keys.sh` fails CI on any key pattern.

**How Quickwit authenticates.** From 0.9.0, with no access key configured, Quickwit authenticates to Blob with the Azure SDK's default credential chain. In Container Apps that chain reaches the managed identity endpoint through its App Service credential, which asks for the **system-assigned** identity and ignores `AZURE_CLIENT_ID`. So each searcher (and the Azure writer) has a system-assigned identity with Reader (or, for the writer, Contributor) on `qw-index` alone. Our build ([ADR-0013](adr/0013-quickwit-from-our-fork.md)) uses the same credential, created once per process. On-prem the searcher reads a local `file://` metastore and needs no Azure access; the release host's writer uses the host's Arc identity.

## 8.3 Networking

- **Public entry points.** `usnewsmap.com`, `www` and `api` resolve to Cloudflare. Its health-check Worker sends each request through the `usnm-serving` tunnel to on-prem while on-prem's `/readyz` answers, and to the spare's default `azurecontainerapps.io` hostname otherwise ([ADR-0029](adr/0029-onprem-primary-azure-failover.md), [`edge/fallback-worker/`](../../edge/fallback-worker/README.md)). The on-prem container opens no inbound port; `cloudflared` dials out ([ADR-0027](adr/0027-onprem-serving-behind-cloudflare.md) decision 2). The spare searcher has internal ingress only.
- **DNS** is at Cloudflare (§8.8).
- **CORS:** the site calls the API on its own origin. The API allows the domain, `www`, the app's own hostname and any `allowedOrigins`, GET only, no credentials.
- **Abuse protection:** the Worker's per-address limit on the search paths (09 §9.3.1, "Flood"), the API's per-client token bucket (salted-hash keys, in memory), request timeouts, a query-complexity budget and 2 computation slots per searcher (06 §6.6). The spare's `maxReplicas: 2` bounds its bill.
- **Data accounts.** Since 6 November 2026 (#308, [ADR-0008, amendment of November 2026](adr/0008-private-networking.md#amendment-november-2026-no-vnet-for-the-spare-308)) the lake, the index account and Cosmos accept every network (`USNM_DATA_ALL_NETWORKS`), because the spare's environment has no VNet and the private endpoints cost about $23 a month to protect a path that carries no traffic until a failover. Entra roles are the only way in: no keys, no SAS, no anonymous access. The exchange account and the scan archive keep their deny-by-default firewalls with the on-prem IP rules, since nothing in Azure reads them. The public-network policy lists all five accounts by id (`infra/public-accounts.bicep`). Turning `USNM_DATA_ALL_NETWORKS` off restores the IP and subnet rules, which stay in the template.
- **Not private, accepted:** telemetry ingestion (no IP firewall on Application Insights; Entra tokens required), image pulls from the registry's public endpoint (Entra tokens required; a private endpoint needs ACR Premium), and LoC downloads.
- **The VNet design.** With `USNM_CAE_VNET` and `USNM_DATA_PRIVATE_ENDPOINTS` on, the template builds the original layout: `vnet-usnm-{env}` with `snet-cae` (the environment) and `snet-pe` (private endpoints for Blob and Cosmos, with linked private DNS zones), and the data accounts closed to public networks. `USNM_DATA_SUBNET_ACCESS` admits the subnet by service endpoint instead, for a switch without a gap. The ingest jobs and the Azure BOINC hand-off job need the VNet; prod has neither.

## 8.4 Compute sizing notes

- **On-prem serving** ([ADR-0027](adr/0027-onprem-serving-behind-cloudflare.md) decision 1): one unprivileged LXC container with about 4 cores at a high CPU weight and about 12 GiB, holding Caddy, the two API colors, the Quickwit searcher and `cloudflared`. The searcher reads the index from read-only local NVMe. Units and deploys are in [`scripts/onprem/serving/`](../../scripts/onprem/serving/README.md).
- **The API** needs little: Rust serves cached responses at hundreds of requests a second on a fraction of a core, so the searcher is the bottleneck. The spare's API container has 1.0 vCPU / 2 GiB, because two Chromium captures (share images) missed their deadline at 0.25 vCPU (`infra/modules/containerapp.bicep`).
- **The searcher.** The spare searcher has 3.75 vCPU / 7.5 GiB, the most a Consumption replica allows next to a small container (since 9 October 2026, #251: on the American Stories index the searcher was CPU-bound at 2.0 of 2.0 vCPU). It caches only in memory, with the capacities in [`infra/quickwit/searcher.yaml`](../../infra/quickwit/searcher.yaml): split footers 256 MB, fast fields 1 GB, partial results and predicate results 32 MB each; no disk split cache.
  - **Image ([ADR-0013](adr/0013-quickwit-from-our-fork.md)).** Our build of Quickwit v0.9.1 (`quickwit/quickwit-usnm`, from the fork `tgoodyear/quickwit`), pinned by digest in `infra/quickwit-image.json`. Upstream's Azure client opens a new connection and TLS handshake for every Blob request and builds a new client and credential for every search; in dev that was 2.0 to 3.0 s of runtime work per cold search. Ours shares one pooled HTTP client and one credential: 0.09 to 0.26 s, and a cold median of 0.18 s against 0.72 s (#251). `QW_AZURE_POOL=false` restores upstream's client without a new image.
  - **Threads (#251).** Quickwit 0.9.1 searches each split on one thread of its search pool. Left alone it sizes that pool from Rust's CPU count, which rounds the 3.75 quota down to 3, and runs every download on one Tokio thread. The template sets `RAYON_NUM_THREADS=4`, `QW_TOKIO_RUNTIME_NUM_THREADS=4` (at 2 the runtime was 96 to 99% busy in a cold-search test while the search pool sat idle) and `QW_NUM_CPUS=4`. `max_num_concurrent_split_searches` (48) bounds splits downloading at once; `warmup_memory_budget` (3 GB; Quickwit's default is 100 GB) pauses new downloads once their estimated memory passes it, as an admission budget rather than a ceiling.
  - **The split footer cache should hold every footer** of the serving version (#125). A search reads each split's footer before anything else, and a footer the cache dropped is fetched again on every cold search. Each release logs `footer_bytes` and `largest_footer_bytes` on its `index layout` lines and records them in the manifest (05 §5.5.1). The footers fit when the version's total is below `split_footer_cache_capacity` and footer misses stop after warm-up. Evictions alone prove nothing: Quickwit 0.9.1 also counts replacing an entry as an eviction. Quickwit reads `256MB` as 256,000,000 bytes ([operations](../operations/search-serving.md#searcher-caches)).
  - One searcher serves each origin. A second replica would add concurrency, not per-query speed, and would start cold and split the cache hits; more capacity is a Quickwit cluster (#239), deferred while the capacity alerts stay quiet (#238). Per-query levers are the searcher's size, its caches and the index layout.
- **The searcher app (#267).** In the original layout the searcher ran as a sidecar in the API's app, so every API image restarted it with empty caches. With `USNM_SEARCHER_APP` (or the index-account searcher, which the spare uses) it is its own app with internal ingress and one replica, so API deploys don't touch it, and the API reads its metrics over the environment's network. When those metrics show a restart, the API runs a searcher-restart warm-up that bypasses both response caches to refill Quickwit's (06 §6.5). Rollback to a sidecar and its checks are in [operations](../operations/search-serving.md#searcher-app). Shared-searcher visitor slots (#364): `USNM_COMPUTE_CONCURRENCY` is the per-searcher budget (default 2), and each API container gets `floor(budget / USNM_API_MAX_REPLICAS)` slots when Quickwit is remote (06 §6.6).
- **Updates from LoC.** LoC has no notification of new batches. With the ingest job, `usnm-ingest run` polls on `USNM_INGEST_CRON`: it fetches LoC's batch listing once, queues new batches and versions, curates them through the shared download pacer, fetches title records for titles not yet catalogued (04 §4.6), and releases a delta; with nothing new it logs `no newly curated batches; nothing to release` and exits 0. Curation stops claiming 6 h after the start (`--curate-max-runtime-secs`) and titles-sync stops after 8 h (`--titles-max-runtime-secs`), so a large publication can't push the release past the job's timeout. A full release goes ahead only once titles-sync has every title LoC lists. Prod has no ingest job and no schedule: releases are built on the on-prem release host when an operator starts one ([full rebuild on-prem](../operations/rebuild-and-index-storage.md#full-rebuild-on-prem)), and batches LoC publishes meanwhile wait for the next release.
- **Writer scratch disk.** The Quickwit writer keeps its write-ahead log, the splits it builds and its merges on local disk. On-prem that is the release host's own ZFS dataset. In Azure a replica's own disk (about 13 GiB free at the start of a release) holds a weekly delta (the delta of 10 October 2026 used about 0.1 GB) but not a full rebuild, which peaked at 11 to 14 GB, so a full rebuild in Azure provisions an NFS Azure Files share, `qw-scratch`, for its duration (`USNM_INGEST_SCRATCH_GIB`, 0 by default, 128 for the rebuild). Sizing at about 23 KB of index per page: the largest merge reads splits holding under 200,000 pages and writes one, under 10 GB together, one merge at a time (`merge_concurrency: 1`), plus the write-ahead log (4 GiB cap), the uploaded-split cache (4 GiB) and the split being built (about 2 GiB): about 20 GB. The release refuses to start with less than three quarters of the share free, and removes a previous run's writer data first, since an old write-ahead log would otherwise replay into an index a published version may list. NFS has no identity: access is by network, the exception recorded in [ADR-0009](adr/0009-entra-identity-only.md#the-ingest-scratch-share-exception-proposed-in-pr-74).
- **Writer memory.** The pipeline itself stays under 400 MB, plus the American Stories text of the batch it is indexing (logged as `text_mb`). The writer's use has three parts: indexing (a 1 GiB heap and up to 1 GiB of in-memory ingest queue), merging, and uploading. The upload is the large one: Quickwit 0.9.1 sends a split to Blob as 100 MB blocks, up to 100 at once, reading each into memory first, so a split of S GB holds about min(S, 10) GB until it is uploaded. Measured in the October 2026 full release: 5.0 GB at most while indexing and uploading 110,000-page splits (about 2.6 GB each), and 7.0 GB 30 s after a million-page merge (about 23 GB) began to upload, before the writer was killed. Hence `split_num_docs_target`: 100,000 at first; 60,000 once the common-word pairs (05 §5.5.3) made a page about 37 KB of index rather than 23; and 30,000 in the template since American Stories' text and pairs (05 §5.5.4) made a covered page about 74 KB. That keeps a merged split near 2.4 GB and never above about 4.4 GB, inside a Consumption replica's 7.5 GiB. `USNM_SPLIT_DOCS` overrides the target for the next full base (60,000 in prod, #283). Options weighed:
  - _More memory:_ a Consumption replica stops at 8 GiB. A Dedicated E4 profile (4 vCPU / 32 GiB) can be added for an Azure full rebuild only (`USNM_DEDICATED_PROFILE`, `USNM_INGEST_ON_DEDICATED`), since any Dedicated profile adds the $73-a-month management fee while it exists. The on-prem release host has neither limit.
  - _Fewer blocks in flight:_ the 100-block limit is fixed in Quickwit 0.9.1's Azure storage; changing it means another commit on our fork.
  - _Smaller splits (chosen):_ at the cost of cold searches opening more splits: about 220 at 110,000 pages for the full corpus, about 360 at 60,000, about 800 at 30,000 (05 §5.5.1).

  If the writer dies, the pipeline, which owns its process, fails with how it ended (for example "killed by signal 9 (SIGKILL): it ran out of memory") and its last lines. It doesn't restart the writer: the merge planner would plan the same merge again with the same memory.

- **Merge wait.** The release waits for merges up to `USNM_MERGE_TIMEOUT_SECS` (4 h by default). In October 2026 a merge of 10 splits into one of about 110,000 pages took about 77 s, and merges fell behind ingest by about 8 an hour, so the merges left after ingest take about 1.7 hours for 23.8M pages. A release can't resume in a new execution, so a timeout loses the whole rebuild: the Azure ingest job's replica timeout is 48 h (#172), and the on-prem release has none. `release-finish` completes an on-prem release whose merge wait ran out ([operations](../operations/rebuild-and-index-storage.md#finishing-a-release)).
- **Backfill.** Spike S-1 measured the whole corpus at about 175 worker-hours of curation (bzip2-bound, 04 §4.1.1). LoC's bulk limit (10 requests per 10 minutes per IP), not CPU, sets the pace: downloads are spaced 75 s apart across all workers (04 §4.4), so the corpus takes about 2.5 days. In Azure, `caj-usnm-backfill` starts 4 replicas of `usnm-ingest curate` (1 vCPU / 2 GiB each), which claim batches from Cosmos until none remain; each stops claiming 22 h after it starts (`--max-runtime-secs 79200`), logs `max runtime reached; claiming no more batches`, and exits 0 inside the 24 h replica timeout. Workers stream each archive, verifying its sha256 before committing, so they need no scratch disk. A replica that dies leaves its batch leased until the lease expires. On-prem, `USNM_BACKFILL_ONPREM` gives the batch host the same commands' grants. The ACI Spot alternative of the first design isn't built and isn't planned (maintainer, 10 October 2026, [ADR-0017](adr/0017-resource-naming.md)).

### 8.4.1 Quickwit metastore: one writer, many readers

Quickwit's file-backed metastore (a JSON file per index) doesn't support concurrent writers. The design separates readers from the writer:

| Process                                                    | Quickwit roles                                                        | Metastore access                                                                                                                                                                    | Count                                                                                                           |
| ---------------------------------------------------------- | --------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------- |
| Each searcher (on-prem, the spare)                         | `searcher` plus the metastore service at the file-backed URI, polling | **Read-only.** Picks up newly published splits by polling (`#polling_interval=30s` on Blob). No indexer or janitor runs here; the Azure identity has only Blob Reader on `qw-index` | One per origin                                                                                                  |
| A release (`usnm-ingest`, on-prem or the Azure ingest job) | `indexer` + `janitor`, a child process of the pipeline                | **Sole writer.** Writes only a **new** index (a delta, or a new base), never one a published version already lists                                                                  | At most 1, by the Cosmos `ops/quickwit-writer` lease (ETag compare-and-swap, 2-hour TTL, renewed while running) |

The on-prem release builds on local disk and copies the finished version to the index account with `usnm-ingest publish-staged`; it doesn't take the Cosmos lease, so ingest and prune must not run beside it ([operations](../operations/rebuild-and-index-storage.md#full-rebuild-on-prem)).

**Index versions are immutable sets of sealed indexes.** An `index_version` names an explicit list of Quickwit indexes in `current.json`: one base plus zero or more deltas.

- **Sealing:** once an index appears in a published version, no job writes to it again; replacement or deletion happens only by building a new base.
- **Explicit index lists:** the API passes exactly the listed index ids to Quickwit. No query touches a new delta until a new `current.json` lists it, so a given version always returns identical results, and rolling back to the previous `current.json` restores the previous set exactly.
- **Warming new indexes (S-2):** a read-only searcher reads the metastore's index list only at startup; a search naming an index created later fails with "could not find indexes". Looking the index up by id (`GET /api/v1/indexes/{id}`) loads it and adds it to the polled set, so the API looks up every index a new `current.json` lists before it swaps in that version (`SearchBackend::prepare`). If any lookup fails, it keeps serving the previous version and retries on the next poll.
- **Increments** add new pages as a new delta, then publish a version listing base and all deltas.
- **Replacements** (new batch versions, OCR reprocessing) and **title-metadata changes** can't be applied to sealed indexes. They wait for the next full release, which builds a new base and clears the deltas. Nothing schedules full releases; an operator starts one (12 §12.5). Until then the previous text and place assignments keep serving, consistently with their reference snapshot.
- **Garbage collection:** `usnm-ingest prune` (#245) deletes through Quickwit every index that neither the serving version nor its rollback (`previous_version`) names, nor a published version newer than the serving one. It takes the writer lock, lists what it would delete unless given `--delete`, and refuses without a readable `current.json` ([operations](../operations/rebuild-and-index-storage.md#prune-old-index-versions)).
- **Azure AI Search (growth profile)** can't query several indexes in one request, so that backend would publish only full releases.

S-2 checked this on Quickwit 0.9.1: a searcher-only node serves the writer's indexes, never writes the metastore, and serves indexes created after it started once they are looked up as above. CI repeats it on every change (the `quickwit` job, `scripts/dev/quickwit-fixtures.sh`). The fallback, a PostgreSQL metastore, would support any number of Quickwit nodes.

## 8.6 CI/CD (GitHub Actions)

- **`ci`** runs every check on each pull request and push: Rust (fmt, clippy, tests), the web app (`npm audit`, lint, format, typecheck, vitest, build, and Playwright with axe), the scripts' tests, Bicep lint and builds, the shared-key scan, the documentation links, and the `quickwit` job (§8.4.1). CodeQL and Dependabot run beside it.
- **`publish`**, on `main` once every check passes, runs for each environment in `USNM_DEPLOY_ENVIRONMENTS`: it pushes the images to that environment's registry (`usnewsmap-api:main` and `:<commit>`) and attests the API image. Only the commit `main` currently points at publishes, so a slow run for an older commit can't overwrite a newer one (`scripts/ci/head-of-main.sh --unless-changed image`).
- **On-prem follows `main`.** The serving container's update timer reads the `main` manifest every few minutes, verifies its build provenance attestation from `ci.yml` on `main`, and deploys it blue/green: the idle color starts the new image, Caddy switches once its `/readyz` passes, and the old color stops 130 s later. A color that never gets ready leaves the old one serving, and its digest is rejected ([deploys](../../scripts/onprem/serving/README.md#deploys)). A push takes effect within about 15 minutes, most of it the new color's load and warm-up.
- **The spare** no longer rolls on every push, because each roll cold-started it (#308). The `spare-roll` workflow rolls it after an index publish and before a cold drill; `ci`'s roll job runs only in a dispatched run with `roll_api` (bootstrap, or by hand). The API app is in single-revision mode: Container Apps keeps the old revision serving until the new one passes its startup probe (`/readyz`), and `scripts/ci/roll-api.sh` waits up to 15 minutes for `latestReadyRevisionName`.
- **The edge** deploys from `main` too: `edge-worker-deploy` checks the commit is still current and deploys the fallback Worker with `scripts/ci/deploy-edge-worker.sh`.
- **Stack changes** need `scripts/azure/provision.sh`, which CI's identity can't run; a merge that makes one gets a warning from the `stack change needs a provision` job.
- **Images.** The API image is built on a pinned distroless base. The Quickwit image is pinned by digest per environment in `infra/quickwit-image.json`, which `infra/main.bicep`, `publish` and `scripts/onprem/install-quickwit.sh` all read. An environment listed there runs our build, made in its registry by `scripts/azure/build-quickwit.sh` (ACR Tasks, about an hour) or imported with the same digest; any other runs upstream v0.9.1, which publish copies into ACR by digest. Image builds pull Docker Hub base images through Google's mirror, `mirror.gcr.io`, because anonymous Docker Hub pulls from shared runners hit its rate limit (two publish failures on 9 October 2026); on a mirror miss BuildKit goes to Docker Hub itself.
- **Data deploys** are separate from app deploys. A new `index_version` is published by a release and picked up by each API's reference refresher, not by redeploying.

## 8.8 Domain and DNS

- The `usnewsmap.com` registration should sit with an account the project controls, with auto-renew and at least two admins; it was one of the legacy site's single points of failure (10 §10.4).
- **DNS is at Cloudflare** (delegated 20 October 2026, #944), and its records are kept there by hand, not in Bicep. The apex, `www` and `api` are proxied, and the Worker on their routes picks the origin (ADR-0029). `boinc.usnewsmap.com` is a proxied CNAME to the BOINC server's own tunnel ([ADR-0024](adr/0024-cloudflare-tunnel-and-r2-credentials.md)). The Azure DNS zone was deleted on 24 October 2026; prod sets `dnsZoneHosted` (`USNM_DNS_ZONE_HOSTED`) to false.
- **Certificates.** Cloudflare's Universal SSL certificate covers the apex and a wildcard at the edge. For an Azure origin, one Let's Encrypt DNS-01 certificate for all three names is renewed weekly into Key Vault by the `origin-tls` workflow; since #308 it isn't uploaded to Azure, and no Azure app binds the custom domains ([origin TLS](../operations/origin-tls.md)). Azure's managed certificates couldn't renew behind a proxied record, which is why [ADR-0028](adr/0028-cloudflare-with-azure-origin.md) moved to DNS-01.
- **CAA records** (read on 24 October 2026) allow DigiCert and the CAs Cloudflare issues from (Let's Encrypt, Google Trust Services, SSL.com, Sectigo), for `issue` and `issuewild`. An old `issuewild ";"` record authorizes no CA and so doesn't stop the others ([RFC 8659](https://www.rfc-editor.org/rfc/rfc8659)).
- `dnsZoneName` (`USNM_DNS_ZONE`) is still the site's domain in the template: the CORS origins and the availability test follow it, and in an environment whose zone Azure hosts, `bootstrap.sh` binds the names to the app with managed certificates once the domain is delegated.
- The legacy `/loc_api` endpoints aren't kept.

## 8.9 Portability: redeploying into another subscription or tenant

The Azure side can be stood up from this repository in any subscription, in any tenant, with one command, and the corpus rebuilt from public sources. No single account, subscription or person may be load-bearing; that is how the legacy site died. The on-prem side is rebuilt from `scripts/onprem/` plus the lab repository's container scripts, which hold the host names and addresses.

**Command:** `scripts/azure/bootstrap.sh --env <env> [--subscription ID] [--location REGION] [--vnet-address-prefix CIDR] [--domain NAME] [--alert-email ADDR] [--ingest] [--move]`. It is idempotent. It:

1. checks the sign-ins (`az`, `gh`) and registers the resource providers the templates use;
2. writes the environment's settings: the public choices to `infra/env/<env>.json`, to commit, and the rest to the settings store (#295; [operations](../operations/environments-and-deploys.md#settings)), including the repository's immutable ids for OIDC and whether the subscription's Cosmos DB free-tier slot is free;
3. deploys the stack `usnm-<env>` (everything but the API, which has no image yet);
4. creates the GitHub Environment of the same name, restricted to `main`, writes its variables and adds it to `USNM_DEPLOY_ENVIRONMENTS`;
5. runs `ci` on `main`, which publishes the images, and waits for it;
6. switches to the registry (`USNM_USE_ACR=true`) and deploys the stack again, which deploys the API;
7. binds the custom domains where Azure DNS hosts the zone, once the registrar delegates it;
8. checks the API's `/readyz` and the site.

A new environment starts with no data. Everything in Blob and Cosmos is derived from LoC's public data by a deterministic pipeline: about 4.5 h of title sync (LoC's 20-requests-a-minute API limit) and about 2.5 days of curation (§8.4), then a full release. An environment with the archival account seeds the title sync from the newest saved copy instead (`scripts/azure/titles-seed.sh`). Hand-curated state belongs in git: the catalog overrides (`catalog/overrides/places.json`, `catalog/overrides/titles.json`) ship in the ingest image, and an environment's public choices are committed in `infra/env/<env>.json`.

**What is per environment, and what is shared:**

| Thing                                                          | Scope                        | Notes                                                                                                                                                                                                                                                    |
| -------------------------------------------------------------- | ---------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| The deployment stack `usnm-{env}` and everything in its groups | Per environment              | Globally unique names carry a suffix derived from the subscription and environment                                                                                                                                                                       |
| CI identity and GitHub Environment `{env}`                     | Per environment              | The identity trusts only jobs in that Environment of the configured repository, which only `main` may use. No secret is stored                                                                                                                           |
| Guard-rail policy definitions                                  | Per subscription             | Stack `usnm-guardrails`; needs Owner or Resource Policy Contributor                                                                                                                                                                                      |
| Cosmos DB free tier                                            | One account per subscription | Bootstrap turns it off for a second environment in the same subscription (about $1–3 a month serverless instead)                                                                                                                                         |
| The settings store `usnm-config-appcs-{sfx}`                   | Per subscription             | Stack `usnm-config`, so no environment's teardown deletes it. The operators in its admin list have App Configuration Data Owner; CI doesn't read it. `scripts/azure/settings.sh --migrate` moves an environment's settings to a new subscription's store |
| The domain                                                     | One environment              | The one the Worker routes to                                                                                                                                                                                                                             |

**Prerequisites:** Owner on the subscription; admin on the GitHub repository. No tenant-level objects are created (no app registrations), so no Entra admin is needed. A fork works the same way.

**Moving production** to another subscription or tenant: run `bootstrap.sh --env <env> --subscription NEW --domain usnewsmap.com --ingest --move` (`--move` resets the settings that describe the old subscription, and the old store's private settings are copied over), let the new environment rebuild the corpus, check it on its app's default hostname, then point the Worker at the new spare and grant the on-prem hosts' Arc identities their roles in the new stack. Remove the old one with `scripts/azure/teardown.sh --env <env> --subscription OLD`. [Operations](../operations/environments-and-deploys.md#settings) has the details.

## 8.10 Naming

Resource names follow [ADR-0017](adr/0017-resource-naming.md) (proposed): `usnm-{function}-{type}-{env}`, for example `usnm-ocr-appi-prod`, with a compact form for storage accounts, registries and Key Vaults (`usnmocrstprodffapzy`) and the deployment suffix only on names that are unique across Azure.

- New resources take the convention from their first commit, in every environment.
- Prod's older names (`rg-usnm-prod`, `crusnmprodffapzy`, `log-usnm-prod`, `appi-usnm-prod`, `stusnmdffapzy`, `cosmos-usnm-prod-ffapzy` and others) keep their names until a rebuild such as the subscription move in §8.9, which comes up under the new names.
- Names are built in one place, `infra/naming.bicep`. Scripts and queries read names from stack outputs or tags, never by matching prefixes.
