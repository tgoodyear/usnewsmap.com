# 09: Operations, Security & Cost

Public traffic is served on-prem behind Cloudflare, with Azure as shared state and a cold spare ([03 §3.3](03-architecture-overview.md#33-deployment-today-november-2026)). The SLOs, privacy rules and threat model cover both origins. The runbooks themselves are in the [operations guide](../operations/README.md); this document keeps the targets, the on-prem serving runbook (§9.3.1), the security and privacy rules, the costs and the recovery plan.

## 9.1 Service level objectives

| SLI                                                                                                                                                                                                   | SLO (30-day)                              | Measured by                                 |
| ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------- | ------------------------------------------- |
| Availability of `/v1/aggregate` and `/v1/hits`: good = non-5xx; every 5xx (including 503 backend timeout) counts as bad; 4xx (400 syntax, 422 query-too-broad, 429) are client outcomes, not failures | 99.0%                                     | API telemetry, the Worker's outcome records |
| Latency of `/v1/aggregate`, uncached, typical query set                                                                                                                                               | p95 ≤ **2 s** (high-frequency set ≤ 15 s) | API server spans                            |
| Latency of `/v1/aggregate`, cached (in-process, Blob or local store)                                                                                                                                  | p95 ≤ **150 ms**                          | API server spans                            |
| Data freshness (LoC batch published → searchable)                                                                                                                                                     | ≤ **7 days** for 95% of batches           | Manifests vs discover log                   |
| SPA LCP                                                                                                                                                                                               | p75 ≤ **2.5 s**                           | Not measured yet (§9.2)                     |

The error budget for 99.0% is about 7.3 hours a month. When it is exhausted, feature deploys pause in favor of reliability work. A 503 from the Worker, when neither origin got ready, counts against the budget. The on-prem gate [G4](../operations/onprem-serving-phase2.md#g4-30-days-at-990-with-fallback-answers-counted-as-downtime) is stricter and counts answers from the Azure spare as downtime too.

Prod has no scheduled ingest (08 §8.4), so the freshness objective isn't met while releases wait for an operator; it applies again once a weekly release runs on-prem.

## 9.2 Observability

- **The API**, from either origin, sends one Application Insights request per request except the health probes (route template, status, duration), and metrics for backend time, cache hits, rejected queries, the search log, reference reloads, the serving version and the Quickwit searcher's caches and threads (08 §8.1.2). `scripts/azure/logs.sh --env <env> --query-name api-requests` and `api-errors` summarize them. Page views reach `AppPageViews` through `POST /v1/beacon` (06 §6.3.7), summarized by the `traffic` query and the API workbook's Traffic section. Browser telemetry beyond page views, `traceparent` propagation from the SPA and LCP measurement are not built.
- **Logs** are structured JSON from `tracing`. No query text is logged. Query text goes only into the search log (§9.4.2), which is a blob container, not a log. On-prem, the serving container, the release host and the batch host log to journald (30 days for the serving container); in Azure, to `ContainerAppConsoleLogs`.
- **On-prem pipeline.** The release, the ingest commands and the hourly OCR pickup send traces and metrics to Application Insights with their hosts' Arc identities (08 §8.1.2); the pickup's alerts come from those metrics. The OCR dashboard ([14](14-corpus-data-flow.md)) shows the pipeline's state on the LAN.
- **The edge.** The fallback Worker writes fixed outcome records (origin, reason, status) to Analytics Engine, and Cloudflare keeps its invocation logs (§9.4.2). Its heartbeat checks on-prem's readiness every minute.
- **Workbooks:** _usnm API_ and _usnm OCR nodes_ (08 §8.1.2). Cost to date and top queries aren't in them.
- **Alerts** go by email through the action group: API server errors, slow aggregate searches, searches longer than a visitor waits, the search-capacity signal (08 §8.1.2); the OCR pickup's failed, stale and backlog alerts; the Japanese OCR alerts; the BOINC feed-health alerts (#1441); the OCR hosts' log volume and cap; the Log Analytics daily cap (08 §8.1.1); the budget. Cloudflare's tunnel health alert covers the tunnel. SLO burn-rate alerts are not built. No alert yet covers failed units, OOM kills, a full disk or NVMe wear in the serving container ([open items](../../scripts/onprem/serving/README.md#open-items-for-phase-2)).

### 9.3.1 On-prem serving

Since 31 October 2026 the API, the site and the searcher serve the public from one on-prem container, behind the Cloudflare Tunnel `usnm-serving` ([ADR-0027](adr/0027-onprem-serving-behind-cloudflare.md), [ADR-0029](adr/0029-onprem-primary-azure-failover.md)). [`scripts/onprem/serving/README.md`](../../scripts/onprem/serving/README.md) describes the units, deploys, rolling the API back and the hold file, `/etc/usnm-serving/hold`, which stops the update timer's deploys while it exists. The health-check Worker ([`edge/fallback-worker/`](../../edge/fallback-worker/README.md)) checks on-prem's `/readyz` every minute and before each request; when a second probe 1 s later also fails, it sends the request to the Azure spare and waits for it to start from zero. If neither origin gets ready in time it answers 503 with `Retry-After`. The production cold drill answered first from Azure about 68 s after the connector stopped, with no failed requests ([fallback Worker](../../edge/fallback-worker/README.md)); a first start after a provision took 207 s on 6 November 2026, over the Worker's 180 s budget (#308).

**Host reboot.** The container starts at boot, and with it the searcher, Caddy, `cloudflared`, the update timer and the API color that served last (`update-api.sh` enables only that color at boot). The reboot is a gate in [Phase 2](../operations/onprem-serving-phase2.md#g5-rehearsed-reboot); while the host is down, the Worker serves from the spare.

1. Plan it for an off-peak time, as with the Proxmox update window (ADR-0027 decision 11). The API loads `current.json` and the reference snapshot from the lake at start, so a color that starts without the lake never becomes ready.
2. After the boot, check in the container that `systemctl --failed` lists no unit, `curl -fsS 127.0.0.1:7280/health/readyz` answers (the searcher), and `curl -fsS 127.0.0.1:8080/readyz` answers through Caddy. Cloudflare's tunnel health alert clears once `cloudflared` has reconnected.
3. If the color doesn't get ready, read `journalctl -u usnm-api@<color>`. A missing index mount or no lake access is the likely cause. With `USNM_READY_REQUIRES_PUBLISHED_INDEXES` on, `/readyz` also fails while the searcher lacks an index `current.json` names.

**Home IP change.** The tunnel is unaffected, and since 6 November 2026 the lake, the index account and Cosmos accept every network (08 §8.3), so serving keeps working. The exchange account and the scan archive stop accepting the hosts, because their firewalls allow only the on-prem addresses, so BOINC claim and collect and the OCR pickup fail. The Cloudflare tokens limited to the old address stop working too.

1. Put the new address in the settings and provision ([operations](../operations/onprem-ocr.md#on-prem-ocr-nodes)):

   ```bash
   scripts/azure/settings.sh --env prod --key USNM_OCR_NODE_IPS --value <new IP>
   scripts/azure/provision.sh --env prod
   ```

2. In Cloudflare, change the client IP filter of each pinned token to the new address: the API token for the zone and the tunnel (ADR-0024), and the Workers token (ADR-0027 decision 7).

**Tunnel token lost or leaked.** The `usnm-serving` token is in Key Vault and in one root-only file in the container, `/etc/cloudflared/usnm-serving.env` (ADR-0027 decision 7, under ADR-0024's rules). Replace it in ADR-0024's order:

1. Rotate the tunnel's token in Cloudflare, and put the new one in the Key Vault secret. The old token can't open new connections, but a connector already running on it stays connected until it restarts ([Cloudflare](https://developers.cloudflare.com/tunnel/reference/tunnel-tokens/)).
2. On the Proxmox host, run the lab repository's `serving-ct.sh --tunnel` with the new token in a root-only file. It rewrites the container's environment file and restarts `cloudflared-usnm-serving`. Delete the token file afterwards.
3. If the token leaked, also delete all the tunnel's connections with ADR-0024's API token, from the address it's limited to (`DELETE /accounts/<account>/cfd_tunnel/<tunnel>/connections`). Then check in Cloudflare that the tunnel is healthy again.

While no connector is connected, the Worker serves from the spare.

**NVMe failure.** The NVMe pool holds the versions the searcher serves and the response cache. The previous version stays on `tank` in a dataset of its own (ADR-0027 decision 5).

1. On the host, mount the `tank` copy read-only at the path its release wrote, and a cache directory on `tank` in place of the NVMe one (`serving-ct.sh --mounts`). If the mounts show as pending, restart the container. The cache refills on demand.
2. If `current.json` names a newer version than the copy, roll it back to the copy's version first (Rollback index, §9.3). Both origins read the same `current.json`, so the spare rolls back too.
3. Point the searcher at the copy: `gen-env.sh --index-dir`, `serving-ct.sh --config`, then `install.sh`, which restarts the searcher. The site serves from the HDDs, more slowly.
4. Unless the container restarted in step 1, wait until `curl -fsS 127.0.0.1:7280/health/readyz` answers, then redeploy the API with `usnm-serving-update --registry <registry> --redeploy`. A running color keeps the cache mount it started with, and the redeploy starts the idle color on the new one.
5. With a new drive in, copy the version to it as a release does (`zfs send` and `zfs recv`), and reverse these steps, the redeploy included.

If the copy on `tank` is lost too, the index has to be rebuilt, which takes 15 to 20 hours; the spare serves meanwhile.

**Searcher restart (an upgrade or a new index version).** There is one searcher, so a restart is a short outage with cold caches. Do it at a scheduled off-peak time (ADR-0027 settled decision 8). While it restarts, the API serves cached searches and answers the rest with its own 503. The searcher's readiness fails meanwhile, so the Worker may send traffic to the spare and wake it.

- An upgrade: change the pin in `infra/quickwit-image.json`, then run `install.sh` in the container from a checkout that has it. `install.sh` restarts the searcher only when its config, environment, binary or unit changed.
- A new index version needs a new index directory, a new `searcher.yaml` (`gen-env.sh --index-dir`) and then `install.sh`. How each version is mounted waits on a Phase 2 test (ADR-0027 settled decision 6; [open items](../../scripts/onprem/serving/README.md#open-items-for-phase-2)).

Then check `curl -fsS 127.0.0.1:7280/health/readyz` and `curl -fsS 127.0.0.1:8080/readyz`.

**Flood.** The fallback Worker limits the search and MCP paths at the edge (ADR-0027 settled decision 9, #1541): `/v1/aggregate`, `/v1/hits`, `/v1/search-report`, their `/api/v1` twins, `/mcp` and `/mcp/`, every method but `OPTIONS`. It counts each client address (IPv6 by /64, as the API does) in each Cloudflare location, and above the limit answers the API's own 429 problem with `Retry-After: 10` and `X-USNM-Edge-Limit`, so the request doesn't cross the tunnel. The normal limit, 80 requests in 10 seconds, is above the most the API admits one client (60 in 10 seconds: a burst of 40, then 120 a minute), so it never stops a client the API would answer. The counts are approximate and per location, and a client spread over many addresses isn't caught. The zone's one Free rate-limit rule holds the leaked-credential check; leave it alone. Signs of a flood: a jump in the search routes' `Client4xx` count in `scripts/azure/logs.sh --env prod --query-name api-requests`, one address sending many searches in Security Analytics, or many `edge-rate-limit` outcomes in the Worker's records.

1. Tighten or turn off the limit with the Worker variable `SEARCH_EDGE_LIMIT`: `normal` (the default, also for any other value), `strict` (20 in 10 seconds, the API's sustained rate) or `off`. For an immediate change, edit the variable on `usnm-fallback` in the dashboard (Workers & Pages → `usnm-fallback` → Settings → Variables and Secrets) and deploy. The next deploy from `main` puts back the committed value, so a lasting change goes in `edge/fallback-worker/wrangler.jsonc` and `wrangler.health.jsonc` through a pull request.
2. Check it: a search sent 100 times in a few seconds from one address gets `429` with `X-USNM-Edge-Limit` once past the limit, and a single search from another address still gets `200`.
3. For a flood the limit doesn't stop (many addresses, one network), add a free custom WAF rule that blocks the network (`ip.src in {...}` or `ip.src.asnum`) on the search paths, with the action Block: a challenge would set the `cf_clearance` cookie, and `/privacy` says the site sets none. Don't use Under Attack Mode: it breaks API scripts. Requests a WAF rule blocks are kept in Security Events (§9.4.2). Remove the rule and set `SEARCH_EDGE_LIMIT` back to `normal` once the flood stops.
4. When publishing new search routes, add them to `LIMITED_PATHS` in `edge/fallback-worker/worker.mjs`; `scripts/onprem/serving/test_serving.py` checks that list against the API's routes.

### 9.4.2 Privacy

- The application collects no accounts, cookies or PII.
- **IP addresses.** The API never writes client IPs to its logs or telemetry. The one place it passes a client address on is a page view's `ai.location.ip` tag (06 §6.3.7): ingestion derives the city, region and country from it and stores `0.0.0.0`. On-prem, the API takes the client address from `CF-Connecting-IP` only when the request arrives from loopback, that is, through the tunnel (`USNM_TRUST_CF_CONNECTING_IP`, `crates/usnm-api/src/ratelimit.rs`). The rate limiter's keys are salted hashes held only in memory. Neither origin keeps HTTP access logs: Container Apps doesn't emit them unless turned on, and the serving container's Caddy has none. If access logs are ever turned on to investigate abuse, they hold raw client IPs and the request URI with the search text in `q`, so a Log Analytics ingestion-time transformation that drops the query string must be in place first, and they are kept at most 30 days.
- **Query text** is treated as potentially sensitive (genealogy searches contain family names). The API's request records and traces carry the route template only, and a test checks that search text in a query string reaches neither the exported telemetry nor the console log. Quickwit's search targets log at `warn`, because at info they log every query (08 §8.1.2). The response caches (in memory for up to a day, and stored responses deleted 14 days after they are written, by the lake's lifecycle rule in Azure and a tmpfiles rule on-prem) hold responses that echo the canonical query, with nothing about who asked. Page views can't carry search text: `/v1/beacon` accepts a page name, never a path or query (06 §6.3.7).
- **Search log** ([ADR-0012](adr/0012-anonymous-search-log.md), 06 §6.8). The one place search text is kept on purpose, indefinitely, in the `searches` container of the data lake, written by both origins. Each search is one record with the words, the filters, the page count, the index version and the UTC day, and nothing about who searched: no address, user agent, referrer, identifier, location or time of day. The day is kept, not the hour, because `AppPageViews` has each view's exact time and approximate location for 90 days, and on a small site an hour and a city can single out one visitor. Day files are shuffled so their order doesn't give the time back. Searches with Do Not Track or Global Privacy Control, from bots, from other sites and from the cache warm-up are not recorded. A search the edge answers from its cache is reported by the site, so the API still counts it (06 §6.5). Only operators listed in `USNM_SEARCH_LOG_READERS` and the copy host (§9.6) can read it. Nothing public shows raw queries; anything ever published from it must be k-anonymized with k ≥ 5.
  - **Sitemap (#1484):** only curated `/examples/<id>` searches and site information pages are listed. Visitor searches don't become indexable pages, and existing search links work with `noindex`.
  - **Reading it:** `scripts/azure/searches.sh --env <env> [--days N]` (default 30) downloads the day files to a temporary directory with the operator's Entra sign-in, prints searches per day, the top 50 queries and the top 50 that found nothing, and the share of searches by date span and decade partitions (#123), then deletes the files.
- **The dataset details page** (`/datasets`, data from `GET /v1/status`, [06 §6.3.6](06-api-design.md#636-get-v1status)) is public on purpose: batch names, LoC URLs and counts are public data. It shows no identities, hostnames, resource names, client ids, blob URLs or full worker ids, and pipeline error text is sanitized and shortened before it is served. Its Cosmos access is the read-only Data Reader role on `batches`, `index_runs` and `ops`, at most one refresh (three queries) per minute per API process, cached 30 s in browsers.
- **Page views** (07 §7.8): one per page, with the page name and title, the referrer's origin and `utm_*` tags on the first page of a load, and the device type and browser family the API works out from the user agent. No cookie, storage or identifier, so page views can't be joined into visits. Do Not Track and Global Privacy Control turn them off in the browser, and the API drops any that arrive with either header.
- **Cloudflare.** Every request to `usnewsmap.com`, `www` and `api` passes through Cloudflare, which terminates TLS and so sees the client's IP address, the full URL (a search's words are in `q`) and the request headers. Cloudflare's [privacy policy](https://www.cloudflare.com/privacypolicy/) (section 6) makes it a processor for Customer Logs and for content transiting its network, and a controller for other personal information it collects about visitors; its [customer DPA](https://www.cloudflare.com/cloudflare-customer-dpa/) applies under the Self-Serve Subscription Agreement. On 24 October 2026 the maintainer accepted these as exceptions to the access-log rule above (ADR-0027 settled decision 1, which also amends ADR-0012):
  - [Security Analytics](https://developers.cloudflare.com/waf/analytics/security-analytics/) keeps sampled requests with the client IP and path for up to 31 days on the Free plan, possibly with a search's words. Whether Security Analytics or Security Events keep the query string is Phase 2 measurement [M11](../operations/onprem-serving-phase2.md#m11-do-security-analytics-or-security-events-keep-the-query-string).
  - The fallback Worker's invocation logs are on (`--worker-logs` in `scripts/ci/deploy-edge-worker.sh`), at the maintainer's request ([ADR-0029](adr/0029-onprem-primary-azure-failover.md)). Query strings are redacted, but the platform's invocation metadata includes client-IP headers and geolocation. `/privacy` says Cloudflare keeps them for up to seven days. The Worker's own outcome records hold origin, reason and status only.
  - The edge caches `/v1/aggregate` responses for about 14 days and never caches `/v1/hits` or HTML.
  - The Worker's rate limit keeps no record of the searches it refuses; a WAF rule added by hand during a flood keeps the requests it blocks in Security Events. Bot Fight Mode stays off, so Cloudflare sets no `__cf_bm` cookie, and Web Analytics' automatic setup is off.
- **Where the data is.** The API, the site, the searcher and the on-prem response cache run on the on-prem host. The search log, the OCR-request list, reference data, pipeline state (Cosmos) and telemetry are in Azure East US 2. Cloudflare says it stores information "primarily" in the United States and the European Economic Area.
- **No client IPs or search text in the host's logs.** `cloudflared` logs at info (at debug it logs every URI), and `run-cloudflared.sh` cuts the query string from its error lines. Caddy has no access log, and its error log drops each line's request field (the URI and the headers). The API's console logs go to journald with no client IPs or query strings. Phase 2 measurement [M6](../operations/onprem-serving-phase2.md#m6-a-forced-upstream-failure-leaves-no-search-or-client-ip-in-a-retained-log) checks this with a forced upstream failure.
- **Retention.** Application Insights data (`AppPageViews`, `AppRequests`, `AppTraces`, `AppMetrics`) is kept 90 days. `ContainerAppConsoleLogs` and the storage write and delete logs are kept 30 days, and the serving container's journal 30 days.
- **The privacy page** (`/privacy`, `web/src/privacy/PrivacyPage.tsx`) states what is collected: page views and their fields, approximate location with the address not stored, request records without search text, the search log, the response caches, the rate limiter's in-memory hashes, Cloudflare's role and logs, where the data is, the retention, legitimate interest as the basis, why there is no consent banner (nothing is stored on the device), the basemap from OpenFreeMap, and newspaper pages at the Library of Congress under their own policies. Its statements are checked against the code and the deployment; change them together.
- These rules replace the legacy practice of storing IPs, cookies and full headers for every search, indefinitely ([01](01-background-and-legacy-analysis.md)).

| OCR exchange: egress and storage                                                                                         | about 5–10  |
| Registry, monitoring, lake, scan archive, BOINC group and the rest                                                       | about 30    |
| Cloudflare (Free plan: tunnel, Universal SSL, cache rules, Workers Free, free WAF, one rate-limit rule, DDoS protection) | 0           |

The three cuts of 6 November: no spare wake on each merge to `main` (about −$45, estimated), the BOINC controller's shorter journal listings on the exchange account (about −$27 of egress), and the environment without a VNet (−$21.90 for the load balancer and static IP). Removing the private endpoints the same day saved about $22.90 more ([ADR-0008](adr/0008-private-networking.md)). Items that moved on-prem, such as the searcher at about $90 a month idle, are gone from the bill.

- **The index tier.** Cool would save about $0.30 a day on storage, but each release's writes, early-deletion charges and a failover's reads cost more at the pace releases came in October 2026 (2 to 12 days apart), so the maintainer kept it Hot ([search serving](../operations/search-serving.md#network-and-tier)). `USNM_INDEX_ACCESS_TIER` lets this be revisited.
- **The spare's ceiling.** At `maxReplicas: 2`, both apps running at the active rate all month (a sustained attack) would cost about $450 a month (two API replicas at 1 vCPU / 2 GiB and the searcher at 3.75 vCPU / 7.5 GiB, at $0.000024 per vCPU-second and $0.000003 per GiB-second), so the budget alerts at $40, $60 and $75 actual and $80 forecast are the control. The Worker wakes the spare only when on-prem fails.
- **On-prem** purchases (the NVMe, the replacement `tank` drives, the UPS, the NIC) aren't priced here, and power isn't measured yet (Phase 2 measurement [M14](../operations/onprem-serving-phase2.md#m14-on-prem-power-draw)).
- **A full release** on-prem reads `curated` from the lake: about $38 of egress (441 GB at $0.087/GB) each time, until releases read a local copy (#308).

### On-prem serving (#955)

Before the move, Azure serving cost about $250 a month (16 to 20 October 2026: two searcher apps at about $3 a day each, the index storage, the lake's old index and the endpoints), and all of Azure about $427 a month on 22 October 2026. The maintainer's end state for #955 keeps in Azure only a Cold-tier copy of what can't be re-derived, about $5 to $15 a month; ADR-0029 then kept the spare and one current release, which is most of today's bill. The October figures and their method are in #955's architecture comment and [ADR-0027](adr/0027-onprem-serving-behind-cloudflare.md).

### One-time backfill

The backfill curates about 3,000 batches, paced by LoC's download limit to about 2.5 days (08 §8.4). On Container Apps Jobs it costs about $20–30 of compute at list prices (4 workers at 1 vCPU / 2 GiB, billed while they wait for a download slot), plus about $5 of storage transactions; on-prem it costs no Azure compute. A full release then builds the index (§9.5 above for its egress).

### Growth profile

The original design's upgrade path: Front Door Standard, a larger searcher, ZRS storage and raw archive retention, about $180 to $700 a month. Managed Azure AI Search (L1, one partition) is about $2,800 a month, about $5,600 with two replicas for an SLA. Neither is in the budget ([ADR-0001](adr/0001-search-engine.md), [ADR-0006](adr/0006-lean-hosting-profile.md)).

### Cost controls

- Budget alerts at $40, $60 and $75 actual and $80 forecast
- `maxReplicas: 2` on the spare, and no wake except on an on-prem failure
- Log Analytics daily caps (0.5 GB for the environment, 0.1 GB for the OCR hosts)
- Curated data in Cool storage after 7 days unread; raw archives not retained
- `dev` exists only during an experiment, with a $5-a-month budget alert on its groups ([dev environment lifecycle](../operations/environments-and-deploys.md#dev-environment-lifecycle))
- A tag policy (`project=usnm`, `env=`) enables cost-by-environment views

**Restoring the index to Azure.** If the index account is lost, restore the serving version from the on-prem run directory that built it with `release.sh --run-dir DIR --step restore` (`publish-staged --restore`). It needs that directory's `state.json`, `reference/index-storage-pending.json` and `qw/`, kept on `tank`, and copies about 1.2 TB, about 2.7 hours at 1 Gbps. It refuses unless `current.json` names that version, and writes neither `current.json` nor the pending pointer. Then `release.sh --run-dir DIR --step ready --app-url URL --index-version VERSION` waits until the app's `/readyz` passes and `/v1/meta` names the version. [Restoring serving to Azure](../operations/rebuild-and-index-storage.md#restoring-serving-to-azure) has the commands and limits.
