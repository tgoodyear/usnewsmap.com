# 09: Operations, Security & Cost

## 9.1 Service level objectives

| SLI                                                                                                                                                                                                       | SLO (30-day)                                      | Measured by                    |
| --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------- | ------------------------------ |
| Availability of `/v1/aggregate` and `/v1/hits`: good = non-5xx; **every 5xx (including 503 backend timeout) counts as bad**; 4xx (400 syntax, 422 query-too-broad, 429) are client outcomes, not failures | **99.0%** (lean) / 99.5% (growth)                 | API logs + availability tests  |
| Latency of `/v1/aggregate`, uncached, typical query set                                                                                                                                                   | p95 ≤ **2 s** (high-frequency set ≤ 15 s on lean) | API server spans               |
| Latency of `/v1/aggregate`, cached (moka or Blob)                                                                                                                                                         | p95 ≤ **150 ms**                                  | API server spans               |
| Data freshness (LoC batch published → searchable)                                                                                                                                                         | ≤ **7 days** for 95% of batches                   | Manifests vs discover log      |
| SPA LCP                                                                                                                                                                                                   | p75 ≤ **2.5 s**                                   | App Insights browser telemetry |

The error budget for 99.0% is about 7.3 hours per month. When it is exhausted, feature deploys pause in favor of reliability work.

## 9.2 Observability

- **Traces:** OpenTelemetry from the SPA (App Insights JS) → API → search backend. The trace id is propagated with `traceparent`. Spans: `parse`, `cache`, `backend.aggregate`, `postprocess`, `encode`.
- **Metrics:** request rate, error rate and latency per endpoint; cache hit ratio (moka and Blob); backend latency; searcher CPU/memory/split-cache hits; ingest pages/s; batches queued/claimed/failed (Cosmos); public-access window state; index doc count by version.
- **Logs:** structured JSON (`tracing` → OTLP). **No query text is logged at info level**. Query text goes only into the search log (below), which is a blob container, not a log.
- **API (as built):** one Application Insights request per request except the health probes, named by method and route template, with its status and duration; metrics for search backend time, cache hits and misses (in-process and Blob), rejected queries, reference reloads and the serving index version (08 §8.1.2). `scripts/azure/logs.sh --env <env> --query-name api-requests` and `api-errors` summarize them. The site's page views reach `AppPageViews` through the API (`POST /v1/beacon`, 06 §6.3.7), and `scripts/azure/logs.sh --env <env> --query-name traffic` and the API workbook's Traffic section summarize them. Other browser telemetry and `traceparent` propagation from the SPA are not built.
- **Ingest jobs:** JSON console logs in Log Analytics, traces and metrics in Application Insights (08 §8.1.2). To look at a run: `scripts/azure/logs.sh --env <env> --query-name release-progress`, `curation-throughput`, `curate-replicas`, `errors-by-batch` or `job-executions` (queries in `ops/queries/`), then the `release` and `curate` traces in Application Insights.
- **Dashboards:** an Azure Workbook "USNM Overview" with golden signals, cost to date, ingest status, and the top canonical queries (k ≥ 5, from the search log). Built so far: the workbooks "usnewsmap pipeline" and "usnewsmap API" (08 §8.1.2), with no query text; cost to date and top queries are not in them.
- **Alerts (Action Group → email + optional Teams/Slack webhook):** SLO burn rate (fast 2%/1 h, slow 5%/6 h); built: API 5xx (at least 5 in 10 minutes and over 2% of requests; searches that ran past their 2-minute limit or were refused as busy (the queue for a computation slot full or waited out) are counted apart, and raise it only at 10 in 10 minutes, which looks like a searcher that has stopped answering), `/v1/aggregate` p95 over 3 s for 15 minutes, at least 3 searches in an hour longer than a visitor waits or refused as busy (severity 3, from `api.slow_searches`; the API workbook charts them), the site's home page or `/readyz` failing from 2 of 3 locations (standard availability tests, 08 §8.1.2), and two search capacity signals (severity 4, #238): the p90 wait for a computation slot over 3 s on each of the last two days (emailed daily while it holds) and a replica's CPU averaging over 3 vCPU for 6 hours; an ingest or backfill job failed (any failure but the expected titles-sync stop, within 15 minutes, naming the execution and the reason); the ingest job not progressing (severity 3: titles-sync stops not followed by another execution within 3 hours, or 3 in a row without fewer titles left); a release stalled (no progress line for 10 minutes); a backfill stalled (no batch curated in an hour while workers run); a backfill replica silent for 15 minutes while it runs; oldest `queued` batch > 48 h; budget at 80% forecast; the Log Analytics daily cap reached (severity 1, from the workspace's own `OverQuota` event, which the cap doesn't stop; 08 §8.1.1).

### 9.3.1 On-prem serving

From #955 Phase 2 the API, the site and the searcher also run in one container on pve-big, behind the Cloudflare Tunnel `usnm-serving` ([ADR-0027](adr/0027-onprem-serving-behind-cloudflare.md)). The public reaches it from Phase 3. [`scripts/onprem/serving/README.md`](../../scripts/onprem/serving/README.md) describes the units, deploys, rolling the API back and the hold file, `/etc/usnm-serving/hold`, which stops the update timer's deploys while it exists. During Phase 3, when the tunnel fails (a 502, a 530 or 1033, or a thrown fetch), the fallback Worker retries the request at `ca-usnm-prod`. It passes the API's own 503s through, so it doesn't cover a searcher outage. After Phase 4 the Worker serves the last good page shell with a status banner instead, and answers `/v1` with a 503 (ADR-0027 decision 10 and settled decision 2).

**Host reboot.** The container starts at boot, and with it the searcher, Caddy, `cloudflared`, the update timer and the API color that served last (`update-api.sh` enables only that color at boot). Phase 2 drills a reboot, and Phase 4's gate needs one rehearsed.

1. Plan it for an off-peak time, as with the Proxmox update window (ADR-0027 decision 11). Don't reboot while the lake is unreachable (home IP change, below). Until Phase 5 moves reference data on-prem, a color that starts without the lake never becomes ready, so the site stays down until access is back.
2. After the boot, check in the container that `systemctl --failed` lists no unit, `curl -fsS 127.0.0.1:7280/health/readyz` answers (the searcher), and `curl -fsS 127.0.0.1:8080/readyz` answers through Caddy. Cloudflare's Tunnel Health Alert clears once `cloudflared` has reconnected.
3. If the color doesn't get ready, read `journalctl -u usnm-api@<color>`. A missing index mount or no lake access is the likely cause. With `USNM_READY_REQUIRES_PUBLISHED_INDEXES` on, `/readyz` also fails while the searcher lacks an index `current.json` names.

**Home IP change.** A new home address cuts the container off from the lake and Cosmos, and the Cloudflare tokens pinned to the old address stop working. The tunnel is unaffected. The color that serves keeps serving the version it has, and logs `reload failed; keeping current version` at each reference reload. Search-log records wait in memory and are retried at each flush. They are lost if they aren't written within 45 minutes after their UTC day ends, or if the API restarts.

1. No restarts and no deploys until lake access is back, because a color started without the lake never becomes ready. In the container, `touch /etc/usnm-serving/hold` stops the timer's deploys. Don't reboot the host, restart a unit or run `install.sh`.
2. Put the new address in the settings and provision, as for the OCR nodes ([operations](../operations/onprem-ocr.md#on-prem-ocr-nodes)). With `onPremServing` on, the lake's and Cosmos's IP rules come from `USNM_OCR_NODE_IPS`:

   ```bash
   scripts/azure/settings.sh --env prod --key USNM_OCR_NODE_IPS --value <new IP>
   scripts/azure/provision.sh --env prod
   ```

3. In Cloudflare, change the client IP filter of each pinned token to the new address: the API token for the zone and the tunnel (ADR-0024), and the Workers token (ADR-0027 decision 7).
4. Once the serving color's journal shows no new `reload failed` lines, delete `/etc/usnm-serving/hold`.

**Tunnel token lost or leaked.** The `usnm-serving` token is in Key Vault and in one root-only file in the container, `/etc/cloudflared/usnm-serving.env` (ADR-0027 decision 7, under ADR-0024's rules). Replace it in ADR-0024's order:

1. Rotate the tunnel's token in Cloudflare, and put the new one in the Key Vault secret. From then on the old token can't open new connections, but a connector already running on it stays connected until it restarts ([Cloudflare](https://developers.cloudflare.com/tunnel/reference/tunnel-tokens/)).
2. On the Proxmox host, run home-infra's `serving-ct.sh --tunnel` with the new token in a root-only file. It rewrites the container's environment file and restarts `cloudflared-usnm-serving`, which reconnects with the new token. Delete the token file afterwards.
3. If the token leaked, also delete all the tunnel's connections, with ADR-0024's API token from the address it's limited to (`DELETE /accounts/<account>/cfd_tunnel/<tunnel>/connections`). That drops any connector still running on the old token. Then check in Cloudflare that the tunnel is healthy again, because `cloudflared-usnm-serving` has to reconnect with the new token.

While no connector is connected, the tunnel serves nothing, and during Phase 3 the Worker falls back to Azure.

**NVMe failure.** The NVMe pool holds the versions the searcher serves and the response cache. The previous version stays on `tank` in a dataset of its own (ADR-0027 decision 5).

1. On the host, mount the `tank` copy read-only at the path its release wrote, and a cache directory on `tank` in place of the NVMe one (home-infra's `serving-ct.sh --mounts`). If the mounts show as pending, restart the container. The cache refills on demand.
2. If `current.json` names a newer version than the copy, roll it back to the copy's version first (Rollback index, above). With `USNM_READY_REQUIRES_PUBLISHED_INDEXES` on, `/readyz` fails while the searcher lacks an index `current.json` names. Both origins read the same `current.json`, so during Phase 3 Azure rolls back too.
3. Point the searcher at the copy: `gen-env.sh --index-dir`, `serving-ct.sh --config`, then `install.sh`, which restarts the searcher and makes the colors' cache directories. The site serves from the HDDs, more slowly.
4. Unless the container restarted in step 1, wait until `curl -fsS 127.0.0.1:7280/health/readyz` answers, then redeploy the API with `usnm-serving-update --registry <registry> --redeploy`; a run does nothing while the searcher isn't ready. A running color keeps the cache mount it started with, and the redeploy starts the idle color on the new one.
5. With a new drive in, copy the version to it as a release does (`zfs send` and `zfs recv`), and reverse these steps, the redeploy included.

If the copy on `tank` is lost too, the index has to be rebuilt, which takes 15 to 20 hours.

**Searcher restart (an upgrade or a new index version).** There is one searcher, so a restart is a short outage. Do it at a scheduled off-peak time (ADR-0027 settled decision 8). While it restarts, the API serves cached searches and answers the rest with its own 503, and the site shows its banner (Search engine down, above). The Worker passes those 503s through, so Azure doesn't take over. The searcher's caches are cold afterwards.

- An upgrade: change the pin in `infra/quickwit-image.json`, then run `install.sh` in the container from a checkout that has it. `install.sh` restarts the searcher only when its config, environment, binary or unit changed.
- A new index version needs a new index directory, a new `searcher.yaml` (`gen-env.sh --index-dir`) and then `install.sh`. How each version is mounted is decided after a Phase 2 test (settled decision 6), and these steps will follow that decision.

Then check `curl -fsS 127.0.0.1:7280/health/readyz` and `curl -fsS 127.0.0.1:8080/readyz`.

**Flood.** Cloudflare's one Free rate-limit rule is written and off (ADR-0027 settled decision 9). Turn it on when single addresses send searches far past the API's own limit (120 a minute, burst 40), because the API's 429s still cross the tunnel and load the host. The signs are a jump in the search routes' `Client4xx` count (which includes the 429s) in `scripts/azure/logs.sh --env prod --query-name api-requests`, or one address sending many searches in Security Analytics.

1. Enable the rule in the zone's rate-limiting rules. It matches `/v1/aggregate`, `/v1/hits`, `/api/v1/aggregate` and `/api/v1/hits`, counts each IP's requests over 10 seconds, and blocks an IP above about 50 for 10 seconds. The rule's recorded definition is `scripts/onprem/serving/flood-rule.json`; until the zone-settings script exists, the dashboard rule must match it (ADR-0027 settled decision 12).
2. Keep its action at Block. A challenge would set the `cf_clearance` cookie, and `/privacy` says the site sets none. Don't use Under Attack Mode either: it breaks API scripts.
3. While the rule is on, every search it blocks is kept in Security Events (§9.4.2). Turn it off once the flood stops.

### 9.4.2 Privacy

- The application collects **no accounts, cookies or PII**. The site is anonymous by design. The one bounded exception is platform access logs, described next.
- **IP addresses:** the API never writes client IPs to its logs or telemetry, and App Insights IP collection stays masked (the default). The one place the API passes a client address on is a page view's `ai.location.ip` tag (06 §6.3.7): ingestion derives the city, region and country from it and stores `0.0.0.0`. Container Apps doesn't emit per-request access logs by default, and the lean profile leaves them off. **Exception:** if HTTP access logs are turned on to investigate abuse (or Front Door logs in the growth profile), they contain raw client IPs, go only to Log Analytics, and are **retained for at most 30 days**. Those logs would also record the request URI, and every search puts its text in `q`. So a Log Analytics **ingestion-time transformation** (data collection rule) is attached before such logs are enabled; it **drops the query string** from the URI fields (`requestUri`, `RequestUri_s` and equivalents), so only the path is stored. A deployment check refuses to enable access-log diagnostic settings without that transformation. The API rate-limiter keys are **salted hashes** held only in memory.
- **Query text** is treated as potentially sensitive (genealogy searches contain family names). It is never logged per request. The API's request records and traces record the **route template only** (`/v1/aggregate`, never the path or query string), and a test checks that search text in a query string reaches neither the exported telemetry nor the console log. At info, the Quickwit sidecar logs every search's query; `infra/modules/containerapp.bicep` sets its search targets to `warn` (08 §8.1.2), which takes effect when the stack is deployed. The lines logged before that carry no client address and leave `ContainerAppConsoleLogs` after its 30-day retention. The response cache (in memory for up to a day, and slow responses in the `cache/` container, deleted 14 days after they are written) holds responses that echo the canonical query, with nothing about who asked. Page views can't carry search text: `/v1/beacon` accepts a page name, never a path or query (06 §6.3.7). Access logs, if enabled, are scrubbed as described above.
- **Search log** ([ADR-0012](adr/0012-anonymous-search-log.md), 06 §6.8). The one place search text is kept on purpose, indefinitely, in the `searches` container of the private data account. Each search is one record with the words, the filters, the page count, the index version and the UTC day, and nothing about who searched: no address, user agent, referrer, identifier, location or time of day. The day is kept, not the hour, because `AppPageViews` has each view's exact time and approximate location for 90 days, and on a small site an hour and a city can single out one visitor. Day files are shuffled so their order doesn't give the time back. Searches with Do Not Track or Global Privacy Control, from bots, from other sites and from the cache warm-up are not recorded. Only operators listed in `USNM_SEARCH_LOG_READERS` can read it (Storage Blob Data Reader on the container). Nothing public shows raw queries; anything ever published from it must be k-anonymized with k ≥ 5 (only queries searched at least five times, with no rare combination of query and filters).
  - **Reading it:** `scripts/azure/searches.sh --env <env> [--days N]` (default 30) lists the day files, downloads them to a temporary directory with the operator's Entra sign-in (`az storage blob download --auth-mode login`) and prints searches per day (by source, with those that found nothing), the top 50 queries and the top 50 that found nothing, and the share of searches by date span and by decade partitions touched (counts only, for #123), then deletes the files. The data account takes connections only through its private endpoint (ADR-0008), so the script runs from a network that reaches the account.
- **The dataset details page** (`/datasets`, formerly the status page at `/status`, data from `GET /v1/status`, [06 §6.3.6](06-api-design.md#636-get-v1status)) is public on purpose: batch names, LoC URLs and counts are public data. It shows no identities, hostnames, resource names, client ids, blob URLs or full worker ids, and pipeline error text is sanitized and shortened in the API before it is served. Its Cosmos access is the read-only Data Reader role on the three containers it shows (`batches`, `index_runs`, `ops`), and its cost is bounded: at most one refresh (three queries) per minute per API replica (two at most), whatever the traffic, cached for 30 s in browsers. Its pages by state, by language and by year, and its counts per source of text, come from the reference snapshot already in memory, so they add no Cosmos or search queries. Pages by language need the snapshot's `title_pages.json`, which every release writes for the whole version; if the published version is older than that file, the table shows newspaper counts only until the next release.
- **Page views** (07 §7.8): one per page, with the page name and title, the referrer's origin and `utm_*` tags on the first page of a load, and the device type and browser family the API works out from the user agent. No cookie, storage or identifier, so page views can't be joined into visits or visitors. Do Not Track and Global Privacy Control turn them off in the browser, and the API drops any that arrive with either header.
- **Retention.** Application Insights data (`AppPageViews`, `AppRequests`, `AppTraces`, `AppMetrics`) is kept 90 days, the component's default, which the workspace's 30-day default doesn't shorten. Console logs (`ContainerAppConsoleLogs`) and the storage write and delete logs (`StorageBlobLogs`, on the Auxiliary plan, 08 §8.1.1) are kept 30 days. The workspace and the component are in East US 2.
- **The privacy page** (`/privacy`, `web/src/privacy/PrivacyPage.tsx`) states what is collected: page views and their fields, approximate location with the address not stored, the request records without search text, the search log (search words kept indefinitely with only the filters, page count and day, not recorded under DNT or GPC), the response cache, the rate limiter's in-memory hashes, the region and the retention, legitimate interest as the basis, why there is no consent banner (nothing is stored on the device), the basemap from OpenFreeMap and newspaper pages at the Library of Congress under their own policies, and the maintainer's contact page. Its statements are checked against the code and the deployment; change them together. From the on-prem cutover (next bullet), it also covers Cloudflare's role and where the data is.
- **On-prem serving** ([ADR-0027](adr/0027-onprem-serving-behind-cloudflare.md)). These rules apply from the public cutover (#955 Phase 3), when the API, the site and the searcher move to an on-prem host behind a Cloudflare Tunnel. Until then, serving is in Azure as described above.
  - **Cloudflare.** Every request to `usnewsmap.com`, `www` and `api` passes through Cloudflare, which terminates TLS and so sees the client's IP address, the full URL (a search's words are in `q`) and the request headers. Cloudflare's [privacy policy](https://www.cloudflare.com/privacypolicy/) (section 6) makes it a processor, acting on the site's instructions, for Customer Logs (the visitor data its dashboard shows the site) and for the content that transits its network, and a controller for the other personal information it collects about visitors. Its [customer DPA](https://www.cloudflare.com/cloudflare-customer-dpa/) applies under the Self-Serve Subscription Agreement. Its [Security Analytics](https://developers.cloudflare.com/waf/analytics/security-analytics/) keeps sampled requests with the client IP and path for up to 31 days on the Free plan. That is a second place raw IPs are kept, beside the access logs above, and one day longer than their 30. It may also keep a search's words with that IP. On 24 October 2026 the maintainer accepted this as an exception to the rule for access logs above (ADR-0027, settled decision 1, which also amends ADR-0012). Phase 2 measures whether Security Analytics or Security Events keep the query string, and this bullet and `/privacy` then say exactly what is kept. Cloudflare's one rate-limit rule, for floods on the search paths, is written but off until the flood runbook turns it on; while it is on, the searches it blocks are kept in Security Events. Bot Fight Mode stays off, so it sets no `__cf_bm` cookie, and Web Analytics' automatic setup is turned off, so it adds no script.
  - **Where the data is.** The API, the site, the searcher and the response cache run on the on-prem host. The search log, the OCR-request queue, reference data, pipeline state (Cosmos) and telemetry stay in Azure East US 2, read and written with the serving container's own Arc identity. Cloudflare's privacy policy says it stores information "primarily" in the United States and the European Economic Area.
  - **No client IPs or search text in the host's logs.** `cloudflared` logs at info (at debug it logs every URI). Caddy, the loopback proxy in front of the API, keeps its access logs off. Quickwit keeps the `RUST_LOG` filter that sets its search targets to `warn`. The API's console logs go to journald instead of `ContainerAppConsoleLogs`, with no client IPs or query strings, as today. The host keeps no access logs. Error logs carry request data too: `cloudflared` can log a failed request's destination URL, and Caddy's error logger records the request's URI and headers, so both are set to drop or redact the query string, the headers and the client IP before anything reaches journald. A Phase 2 drill forces an upstream failure at each proxy and checks the retained logs for a marked search and the client IP. The fallback Worker in front of the tunnel during Phase 3 has Workers Logs off.
  - **The client IP** comes from `CF-Connecting-IP`, which the API reads only when the request arrives from loopback (that is, through the tunnel). It's used as today: the rate limiter's salted hash in memory, and a page view's `ai.location.ip` tag.
  - **The response cache** is a dataset on the host. A tmpfiles rule, in place of the lifecycle rule, deletes each cached response 14 days after it's written. The in-memory cache is unchanged.
  - **The search log** keeps the same record in the same container. The edge never caches `/v1/aggregate` or `/v1/hits`, so the API still sees every search. During Phase 3 both origins write the one log, and the on-prem origin's log settings stay unset until then.
- These rules replace the legacy practice of storing IPs, cookies and full headers for every search, indefinitely.

## 9.5 Cost model (monthly, USD, list prices; confirm with the Azure Pricing Calculator)

**Rate assumptions (East US 2, pay-as-you-go).**

- **Container Apps Consumption:** active use is $0.000024 per vCPU-second and $0.000003 per GiB-second. The idle rate applies when a replica is warm but not processing requests. Every column **exceeds $80**, driven by compute: the 4 vCPU / 8 GiB replica is a stopgap for cold-search latency on the American Stories index (#251) until the index-side fixes there land, after which it can go back down. "High" is a press-spike month billed at the upper idle rates. The ingest scratch share (October 2026) is what lets a full rebuild's writer merge the index into a few large splits, which cold searches need (05 §5.5.1). Since #308 it exists only while a rebuild runs (`USNM_INGEST_SCRATCH_GIB`, 0 by default), so a month without a rebuild carries none of it, and the "High" column is a month with one. The hard cap is `maxReplicas: 2`: even if both replicas ran at the **active** rate all month (a sustained attack, not realistic traffic), compute would be about $620 at 4 vCPU / 8 GiB each (8 vCPU at $0.000024/s plus 16 GiB at $0.000003/s over 30 days; about $350 at the earlier 2.25 / 4.5). Budget alerts at $40, $60 and $75 (actual) and $80 (forecast) trigger the cost-spike runbook well before that.

Outside the environments, the archival account (`usnm-archive`, [operations](../operations/environments-and-deploys.md#archival-storage)) holds batch archives and sample sets at the Cold tier, $0.0036 per GB-month: the 1% set's 23.8 GB is about $0.09 a month, reading it all back once about $0.71. Production doesn't use it. Each environment that does (`USNM_ARCHIVE_ACCOUNT`) adds its own private endpoint, about $7.30 a month.

**Rollouts.** Each rollout of the API runs two replicas side by side: the old revision serves until the new replica has loaded and finished its startup warm-up, which in prod uses its whole 5-minute budget (06 §6.6, 08 §8.6). Since #265 that is about 4 minutes longer than when a replica went ready at a 1-minute cap. The old replica is mostly idle then, so each rollout costs about 1 cent more at the idle rate (4 vCPU and 8 GiB for 240 s at $0.000003/s each), or 3 cents at the active rate. Prod had 7 to 27 rollouts a day from 28 September to 9 October 2026, about 17 on average: about $4 a month ($14 at the active rate), not in the table above. Environments that scale to zero keep the 1-minute cap.

**Searcher app (#267).** With `USNM_SEARCHER_APP` the sidecar becomes its own app, so web and API deploys stop restarting it. Container Apps bills each replica by vCPU-seconds and GiB-seconds, linearly, so a 3.75 / 7.5 searcher and a 0.25 / 0.5 API cost the same as the one 4 / 8 replica if both bill at the same rate: about $89 + $6 = $95 a month idle. Whether each app bills idle once split is to be measured (Cost Management per app, [operations](../operations/search-serving.md#searcher-app)): the API app now waits between visitors on its own, and the searcher still polls the metastore and answers the API's metrics read every minute. Rollouts get cheaper: the API's old revision overlapping the new one is 0.25 / 0.5, not 4 / 8. The setting is off until measured; the decision is pending.

**Sidecar size is the biggest cost lever.** Quickwit went from 1 to 2 vCPU in October 2026 and to 3.75 vCPU / 7.5 GiB on 9 October 2026 (#251). Each vCPU with its 2 GiB costs about $24 a month at the idle rate. Going back to 2 vCPU / 4 GiB (replica 2.25 / 4.5) saves about $41 a month once the index needs less CPU per search; the other options are dropping the private endpoints (−$17, back to identity-only) or accepting slower common-word searches.

**DR runbook: serving from Azure again after Phase 4.** This is Phase 4's rollback ([ADR-0027](adr/0027-onprem-serving-behind-cloudflare.md), Phases), for an on-prem outage too long to wait out. It takes hours.

1. Provision the API and searcher apps again.
2. Publish the index to Azure with `release.sh --step publish`: about 1.2 TB, about 2.7 hours at 1 Gbps. It sends the copy on `tank`, so it needs pve-big's storage and uplink. Without them, the index is rebuilt first (Search index, above). As built, this step can't restore the version that serves, because `publish-staged` copies a release only while `current.json` still names the release's `previous_version` (`crates/usnm-ingest/src/onprem.rs`). A path that restores it doesn't exist yet (#1061).
3. Point the Worker at the new app's default `azurecontainerapps.io` name, which needs no certificates.
4. Bind the custom domains later, as a separate step. Their `asuid` TXT records stay in Cloudflare for it (08 §8.8).
