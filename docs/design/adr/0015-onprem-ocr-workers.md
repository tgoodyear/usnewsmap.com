# ADR-0015: On-prem OCR workers with Azure Arc identities and an exchange account

- **Status:** Proposed
- **Date:** 2026-10 (node grants moved to an Entra group, and monitoring with the Azure Monitor Agent into the nodes' own workspace, 2026-10-10; scans from a local cache, 2026-10-11)
- **Extends:** ADR-0008 (private networking) and ADR-0009 (Entra identity only)
- **Amends:** ADR-0009 §2, with one exception: a client secret for Arc onboarding, on a service principal made for one run (decision 1)

## Context

The language report ([`docs/reports/2026-10-language-analysis/report.md`](../../reports/2026-10-language-analysis/report.md)) scored a 10% sample of index version `pages-v20261003-1`: 2,371,337 pages from all 2,989 batches. Damage is the share of occurrences of a language's 20 most common words that LoC's OCR read one edit wrong; a page is badly damaged above 0.25. Some parts of the corpus are read badly:

- **German before the 1920s.** 57,580 sampled German pages from the 1850s to the 1910s, so about 580,000 pages in the index. The _Nebraska Staats-Zeitung_ has median damage 0.62, with 99% of 292 sampled pages badly damaged; the _Richmonder Anzeiger_ is at 0.43. The report's hypothesis is Fraktur type; no sampled page's typeface has been checked (#246).
- **The worst English batches.** `nn_kant_ver01`, `txdn_japan_ver01`, `nn_bentham_ver01`, `nn_carson_ver02` and `kyu_frenchie_ver02` have median damage 0.46 to 0.52, and 88% to 99.8% of their scored pages are badly damaged.
- **Serbian, Russian and Czech.** Serbian (the _Amerikanski Srbobran_) has median damage 0.257, with 52.7% of pages badly damaged; Russian 0.240 (41.2%); Czech 0.212 (39.2%). Part of the Serbian and Czech score may come from the metric's bias against inflected languages.

Search can't find a page whose words were misread. Re-reading these pages on cloud compute or a cloud OCR service would cost far more than the project's monthly budget (ADR-0005). Two local machines can do the work instead (#296). They are outside Azure, so they have no managed identity, and they can't reach the data lake, which allows private endpoints only (ADR-0008).

## Decision

1. **The nodes are Azure Arc-enabled servers running AlmaLinux 9 (or RHEL 10).**
   - The Connected Machine agent gives each node a system-assigned managed identity. The worker gets Entra tokens from the agent at `localhost:40342`, so no key, secret or certificate is stored on the node (ADR-0009).
   - Arc [supports](https://learn.microsoft.com/en-us/azure/azure-arc/servers/prerequisites) AlmaLinux 9 and RHEL 10 on x86-64 and not Fedora, which the first node ran. Node setup installs no OCR engine: EL9's AppStream has only Tesseract 4.1.1 and EPEL 9 has none, so the engines come as pinned container images (podman) or a source build.
   - The machines are resources in the environment's group, `rg-usnm-<env>`, outside the deployment stack. The no-IaaS policy denies VMs, scale sets, AKS and Batch; `Microsoft.HybridCompute/machines` isn't on its list, and the machines are on-prem hardware.
   - The Bicep doesn't declare the machine resources. The agent creates each one when it connects, and Microsoft documents no way to create one before that.
   - **The node roles go to an Entra security group, `usnm-ocr-nodes-grp-<env>`, and the nodes' identities are its members.** Under ADR-0017, `group.sh` relabels an existing `usnm-ocr-nodes-<env>` at the same saved object ID (`--dry-run` previews it); no group, membership or grant is replaced. The template grants the group (its object id in `USNM_OCR_NODE_GROUP`, `principalType: 'Group'`); each role assignment's name comes from its scope, the group and the role. `onboard.sh` adds a node's system-assigned identity to the group once it connects, and `scripts/ocr-node/offboard.sh` takes it out, so adding or removing a node needs no provision. Microsoft [describes this pattern](https://learn.microsoft.com/en-us/entra/identity/managed-identities-azure-resources/managed-identity-best-practice-recommendations#using-user-assigned-identities-to-reduce-administration) for system-assigned identities that need the same access.
   - `scripts/ocr-node/group.sh` creates the group, once per environment, with `az ad group create`, and saves its id. The Bicep can't: the Microsoft Graph Bicep extension can declare groups, but deployment stacks don't support extensible resources ([Microsoft](https://learn.microsoft.com/en-us/graph/templates/bicep/limitations#unsupported-deployment-features)), and every environment is one stack (ADR-0011). A second, non-stack deployment just for the group would also need the deployer to hold Graph rights during every provision; the script needs them once. It's a plain security group, not mail-enabled and not role-assignable, and the script makes whoever runs it an owner, which is enough to add and remove members.
   - `scripts/ocr-node/onboard.sh` connects a node with a throwaway service principal: an app registration made for that run, with a client secret that expires after 2 hours and only [Azure Connected Machine Onboarding](https://learn.microsoft.com/en-us/azure/role-based-access-control/built-in-roles/management-and-governance#azure-connected-machine-onboarding) on the environment's group. The tenant, app id and secret go on ssh's stdin, and `azcmagent connect --config` reads the secret from a root-only file on tmpfs that is deleted straight after, as [Microsoft advises](https://learn.microsoft.com/en-us/azure/azure-arc/servers/azcmagent-connect#authentication-options). The connect is the principal's only use, so as soon as `node-setup.sh` has finished, or when the script stops before that (on failure or Ctrl-C too), the script deletes the role assignment, the service principal and the app registration and purges them from Entra's deleted items.
2. **The agent is locked down before it connects.** Its extension allow list holds one extension, the Azure Monitor Linux Agent (`extensions.allowlist Microsoft.Azure.Monitor/AzureMonitorLinuxAgent`, decision 8), and `guestconfiguration.enabled false`, so nobody in Azure can run a command (Run Command, Custom Script), install any other extension or apply a machine configuration on the node; `incomingconnections.enabled false`, so there's no SSH through Arc. `node-setup.sh` sets the allow list, with extensions off while a different list is replaced, and reads it back before it turns the extension manager on (`extensions.enabled true`), since an empty list allows every extension. On a node that's already connected it applies all of this again. The allow list doesn't remove an extension installed before it, and that one runs again once the extension manager is on ([Microsoft](https://learn.microsoft.com/en-us/azure/azure-arc/servers/security-extensions)), so `node-setup.sh` stops, with extensions off, if `/var/lib/waagent` holds any other extension, and `onboard.sh` stops if the machine has any other extension in Azure. The first version turned extensions off altogether. The worker runs as the unprivileged `usnm` user in the `himds` group (needed to read the agent's token challenge), from a hardened systemd unit that starts only once the worker binary is installed.
3. **A separate exchange account, `stusnmo<suffix>`, holds the queues and the nodes' output** (`infra/modules/ocr-exchange.bicep`, with `USNM_OCR_NODES`).
   Current prod remains pinned to `stusnmoffapzy`; dev and experiments use
   `usnmocrst<env><suffix>`. The window ADR-0017 set for migrating the
   account while it was empty has passed, and this account also serves
   BOINC hand-off. Do not unpin it until the live queues, blobs and clients
   are inventoried and an owner approves a plan to drain or copy them,
   quiesce the account and reconfigure the clients
   ([rollout/blockers](../../../infra/README.md#explicitly-blocked-later-changes)).
   - Entra only: shared keys off, public blob access off.
   - Public network access is on and the firewall's default action is Deny. It allows the node IPs (`USNM_OCR_NODE_IPS`, the operator's home IP, kept in the environment's settings and never in the repository) and the Container Apps subnet, through a Microsoft.Storage service endpoint on `snet-cae`. There's no trusted-service bypass.
   - The public-network policy exempts it by resource id in the environment's assignment.
4. **The work queues are Azure Storage queues:** `ocr-priority`, `ocr-bulk` and `ocr-deadletter`.
   - One page per message: lccn, date, edition, sequence, batch, expected language and why it was queued. No search text.
   - A worker takes from `ocr-priority` first. It hides a message for a fixed time when it takes it, long enough for its slowest page. Renewing the hide (Update Message) needs `messages/write`, which would also let a node add or rewrite messages; the nodes don't get it. A crashed worker's page comes back when the time runs out. A message taken 5 times goes to `ocr-deadletter`.
5. **The nodes write staging data only.** Through the group, each node's identity has Storage Queue Data Message Processor on `ocr-priority` and `ocr-bulk` (take, peek and delete), Storage Queue Data Message Sender on `ocr-deadletter` (add only), Storage Queue Data Reader on each of the three queues (their lengths and a peek, for the LAN dashboard; nothing that takes or deletes), and a custom role on the `ocr-out` container that lists, reads and creates blobs but can't delete them, so one node can't remove another's output. Nothing on `curated`, `reference`, the index or Cosmos. A cloud job running as `id-usnm-ingest` checks each part (schema, `doc_id` against its `PageKey`, text size), copies it to `curated/ocr-local/pages/` and deletes it from `ocr-out`; a lifecycle rule deletes anything left there after 30 days.
6. **The production worker is Rust**, a binary built from this workspace (ADR-0004), so it shares `PageKey`, `doc_id`, the Parquet overlay types and the Entra credential code with ingest. That credential code gets an Arc source: today it uses a managed identity only when `IDENTITY_HEADER` is set (Container Apps), and Arc's endpoint needs its `WWW-Authenticate` challenge instead. Python stays for the engine survey and audits.
7. **The engine survey comes first.** Before any bulk run, Node 1 compares engines on sampled pages from each group, measuring damage, character error rate on hand-transcribed crops, seconds per page and peak memory. Its results go in a draft report, and we choose the bulk engine by its gain and pages per day.
8. **The nodes are monitored with the Azure Monitor Agent, into a workspace of their own.**
   - **The nodes' own workspace and Application Insights component** (`infra/modules/ocr-node-monitoring.bicep`, with `USNM_OCR_NODES`): Log Analytics `usnm-ocr-log-<env>` with a daily cap of its own (0.1 GB to start), and the workspace-based component `usnm-ocr-appi-<env>` on it, both with local auth off. The template grants the nodes' group Monitoring Metrics Publisher on that component only; the group has nothing on the environment's `appi-usnm-<env>`. The worker sends its traces and metrics there with the node's identity (the provision saves the component's connection string as `OCR_NODE_APPINSIGHTS`). The exchange account's queue logs, a row for every node request, and the rule's own errors (`DCRLogErrors`) go to the nodes' workspace too. The exchange account's blob write logs stay in the environment's workspace, in `StorageBlobLogs` on the Auxiliary plan, which no daily cap covers.
   - **Why a workspace of their own.** Monitoring Metrics Publisher grants `Metrics/Write` and `Telemetry/Write` on a whole component, and Application Insights ingestion has no IP firewall, so a node, or anyone holding a node's token, can write any telemetry under any cloud role, from anywhere. On the environment's component that could be fake `usnm-api` rows, which the API alerts read, or enough rows to fill the environment's 1 GB daily cap and stop all its logging and log alerts until the reset, as a 0.15 GB cap did on 7 October 2026. In their own workspace, the most a node can do is fill the nodes' cap, which stops the nodes' monitoring and nothing else. The API alerts also read only rows whose `_ResourceId` is the API's component. Decided 10 October 2026.
   - **One data collection rule for every node, `usnm-ocr-dcr-<env>`**, sends to the nodes' workspace: syslog at Warning and above; the worker's lines at Info and above, which its unit sends to `local0` (the worker writes JSON lines to stdout, so journald records all of them at info, warnings and errors included, and a Warning threshold would drop every one); CPU, memory, disk and network counters every 60 s; and VM insights' log-based metrics (`\VmInsights\DetailedMetrics` into `InsightsMetrics`) every 60 s, so each Arc machine's Insights pane shows as configured and its Performance tab works. It doesn't use VM insights' OpenTelemetry mode, which needs an Azure Monitor workspace, or the Dependency agent (no Map), so the agent stays the only extension. Added 11 October 2026. The agent sends with the machine's managed identity; the workspace accepts no key (ADR-0009).
   - `scripts/ocr-node/onboard.sh` installs the extension, with automatic upgrades on, and associates the machine with the rule, using the operator's `az` sign-in, once the machine reports the allow list to Azure. `offboard.sh` removes both. Adding or removing a node needs no provision, as with the group (decision 1). Azure Policy and per-machine Bicep were the other ways in; see the alternatives.
   - Syslog, Perf and InsightsMetrics stay on the Analytics plan. The estimate is 20 to 45 MB a day per node, queue logs and VM insights included, before the worker's telemetry, which hasn't been measured; `ops/queries/ocr-node-health.kql` measures each node and the workspace's last 24 hours against the cap. With alert emails set, one log alert fires when a node sends more than a tenth of the cap in an hour, through the agent and its telemetry together, and another when the nodes' workspace reaches its cap.
9. **Scans can come from a local cache, with their provenance** (#368). The damaged pages' scans are fetched once onto pve-big's `tank/ocr/scans` (12 §12.2.4), and the nodes read them from a scan server in the fetch container over HTTP on the LAN; they mount nothing. Each cached scan has a sidecar with the image URL it came from on `tile.loc.gov`, its IIIF base, the fetch time, its size and its sha256. A worker asks the cache before it fetches. A scan whose size and sha256 match its sidecar, and whose URL is on `tile.loc.gov`, is used. The result records that URL as `image_url` and the scan's sha256 (in the ALTO's `sourceImageInformation/fileIdentifier` and, once it is written, the runs record's `scan_sha256`), so `ocr-sync`'s check that `image_url` is on `tile.loc.gov` (12 Step 8, check 5) still holds and a result can be traced to the exact bytes read. A scan without that record is never used: the worker fetches from LoC instead. This is separate from `image=local` in `ocr_engine` (13 §13.8.1), which marks an engine image the lock doesn't pin and stays refused. The scans are split into a keep set, kept for good, and a buffer set, which a worker deletes through the server once its output is uploaded; the server refuses to delete keep-set scans. The server serves only the node IPs, so a node that has been tampered with could still delete buffer scans or put a manifest; it can't change a scan, and a node can already write whatever text it likes to `ocr-out`. The sha256 says which bytes a node read, not that LoC served them. The first version shared `tank/ocr` with the nodes over NFS, read-write; a `hard` NFS read can't be cancelled and could pin worker threads while pve-big was away, so the maintainer chose HTTP (11 October). **Amended 12 October (#368): the scan may be the batch's JP2.** The fetcher reads each page's original JP2 from its batch directory on tile.loc.gov's storage service, found through the batch's BagIt manifest and the issue's METS. It checks the file against the md5 the bag lists, so a JP2 scan is checked against LoC's own record of the file, not only against its sidecar. Its sidecar records the storage-service URL, the bag's md5, the sha256, the size and the IIIF base, which stays the page's id and the overlay's `image_url`; the ALTO's `sourceImageInformation` records the storage-service URL, the sha256 and the md5. `ocr-sync`'s check is unchanged: both URLs are on `tile.loc.gov`. The IIIF JPEGs already fetched stay valid, and pages the batch route can't place still come through the item API as JPEGs (12 §12.2.4).

## Consequences

- **The nodes run a supported OS**, at the cost of rebuilding Node 1 from Fedora as AlmaLinux 9. AlmaLinux 10 isn't on Arc's list yet; RHEL 10 is.
- **A home IP change cuts the nodes off** until `USNM_OCR_NODE_IPS` is updated and the environment provisioned ([operations](../../operations.md#on-prem-ocr-nodes)). The queues hold the work meanwhile, and hidden messages come back.
- **The service endpoint changes the subnet's storage traffic.** Requests from `snet-cae` to storage public endpoints leave from private addresses. The data lake and archive accounts are reached through private endpoints, so nothing they do changes. Turning the endpoint on or off closes open connections to storage public endpoints ([Microsoft](https://learn.microsoft.com/en-us/azure/virtual-network/virtual-network-service-endpoints-overview)), so it's provisioned between jobs.
- **Onboarding briefly creates an Entra app registration**, a tenant-level object the project otherwise avoids, and the operator needs the right to register applications as well as to assign roles on the group. Root on the node during onboarding could copy the secret. What it would get is Azure Connected Machine Onboarding on one resource group (create and update Arc machines and their settings, add extensions to them) until the script deletes the principal, and at most 2 hours if the cleanup didn't run. A cleanup that fails prints what is left, to delete by hand.
- **Root on a node can undo the lockdown.** Anyone who can run commands as root can change the agent's configuration ([Microsoft](https://learn.microsoft.com/en-us/azure/azure-arc/servers/security-extensions)). Its local settings protect the node from Azure, not from its own administrators. Losing a node exposes only what its identity can do: take pages, add dead letters, write to `ocr-out` and send telemetry to the nodes' component.
- **Azure can now run one extension on the nodes, as root.** The Azure Monitor Agent is Microsoft's, checked against a signed catalog before it runs, and upgrades itself. Whoever can write data collection rules and associations in the environment's resource group decides what it collects on the nodes and where it sends it; that takes Monitoring Contributor, Contributor or Owner on the group, and the last two could already open the exchange account's firewall. Nobody in Azure can install anything else or run a command.
- **No new charge for Arc.** The Arc control plane for servers has no charge, and neither has the Azure Monitor Agent; Storage queue operations, the account's storage and its logs, and the nodes' syslog and counters (inside the free 5 GB a month at the estimated volume) are the new costs. The nodes' workspace and component have no base fee. `StorageQueueLogs` has a row per queue request, empty polls included, so the worker backs off while the queues are empty.
- **One node can fill the nodes' daily cap.** Its agent, its worker's telemetry and its queue requests all count under `usnm-ocr-log-<env>`'s cap, with nothing to stop a crash loop, debug logging (`RUST_LOG=debug` turns on every library's debug lines, to syslog and Application Insights alike) or a compromised node. Once the cap is reached, no node has monitoring until the reset; the environment's own logs, telemetry and alerts go on. The volume alert (a tenth of the cap in an hour from one node) fires before that, the cap alert when it happens, and the operations guide scopes debug logging to the worker. The cap starts at 0.1 GB, so the worker's telemetry, once measured, may need a higher one.
- **Arc machines aren't in the stack.** Teardown deletes them with the resource group. Their associations with the nodes' data collection rule aren't in it either, and Azure won't delete a rule that still has associations, so every node is offboarded before `USNM_OCR_NODES` is turned off; otherwise the provision fails (`provision` checks first and stops). Turning it off also deletes the nodes' workspace, with its data, and their component. The group isn't in the stack either, and teardown leaves it: delete it by hand (`az ad group delete`). A machine connected again under the same name gets a new identity, which `onboard.sh` adds to the group; the old one went out of the group when its machine was deleted.
- **Removing a node isn't instant.** Group membership travels as a claim in the access token, and managed identity tokens are cached per resource for around 24 hours; Microsoft says a change to a managed identity's group membership can take several hours to apply and a refresh can't be forced ([Microsoft](https://learn.microsoft.com/en-us/entra/identity/managed-identities-azure-resources/managed-identity-best-practice-recommendations#limitation-of-using-managed-identities-for-authorization)). A removed node can use the exchange account for up to about a day on a token it already has. `offboard.sh` also disconnects the agent and deletes the machine, which stops new tokens; a node that's stolen or misbehaving can be cut off at once by taking its IP out of `USNM_OCR_NODE_IPS` and provisioning. Adding a node has the same delay in reverse if it fetched a storage token before joining, so `node-setup.sh` checks the agent with a Resource Manager token, not a storage one.
- **The group is a tenant-level object.** It outlives the environment's stack, and the operator needs the right to create security groups once (the default user setting, or Groups Administrator).

## Addendum: BOINC as a second queue consumer (#296)

The BOINC hand-off job (ADR-0019) reads `ocr-priority` and `ocr-bulk` beside the nodes. Its identity gets Storage Queue Data Message Processor and Message Sender on those two queues, per queue, and nothing on `ocr-deadletter`; Message Sender is the one role the nodes don't have on them, so that a message BOINC can't use is put back for a node instead of being held for its lease. A claim hides a message for up to 96 hours with a fixed hide, as decision 4 does for the nodes, and the message is deleted after `collect` has put the page in `ocr-out`. The decisions above are unchanged: no Update Message, no shared key, no SAS. The claim file in `boinc-handoff/claims/` holds a message's pop receipt. Azure checks the caller's queue role as well as the receipt, so a reader of the file (the hand-off writers: the hand-off job, the BOINC bridge and the scan fetcher) can do nothing with it unless it also holds a queue role, and only the hand-off job does. [Queue-fed work](../../boinc-batch-scheduler.md#queue-fed-work) has the mechanism.
