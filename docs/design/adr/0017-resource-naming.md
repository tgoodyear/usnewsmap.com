# ADR-0017: Resource naming: usnm-{function}-{type}-{env}

- **Status:** Proposed
- **Date:** 2026-10
- **Amends:** 08 §8.1 (resource names), ADR-0011 (adds a rename guard before each stack deployment)

## Context

The project has no written naming convention. No ADR, design doc or issue covers it. In practice names follow the type-first order from the Cloud Adoption Framework (CAF): `{abbr}-usnm-[{function}-]{env}[-{suffix}]`, compressed for types that allow only letters and digits. The suffix is `take(uniqueString(subscription().id, env), 6)` (`infra/main.bicep:158`), which is `ffapzy` in prod.

The current names were checked against the templates and, read-only, against the live subscription on 10 October 2026. They are inconsistent in these ways:

1. Storage accounts have no env token and a one-letter function (`stusnmdffapzy`, `stusnmtffapzy`, `stusnmsffapzy`, `stusnmoffapzy`). The archive account spells its function out (`stusnmarchiveyjuocl`) and takes its suffix from a different seed (`'usnm-archive'`, `infra/archive/main.bicep:17`).
2. The registry puts env then suffix with no separator (`crusnmprodffapzy`); Cosmos DB and Document Intelligence put the suffix after a hyphenated env (`cosmos-usnm-prod-ffapzy`, `di-usnm-prod-ffapzy`).
3. `rg-usnm-prod-spot` puts the env in the middle.
4. The private endpoints have no env token: `pe-usnm-blob`, `pe-usnm-cosmos`, `pe-usnm-file`, and `pe-usnm-archive-blob` (not deployed in prod). `pe` is not the CAF abbreviation (`pep`).
5. The API app has no function token (`ca-usnm-prod`, `infra/main.bicep:170`), while the jobs do (`caj-usnm-ingest-prod`, `caj-usnm-backfill-prod`, `caj-usnm-jaocr-prod`, `caj-usnm-jaone-prod`).
6. `id-usnm-ci-prod` is declared in `registry.bicep`, not `identities.bicep`, and the Container Apps environment name is written twice (`infra/main.bicep:359` and `:628`).
7. The Arc machine `usnm-ocr-node1` (also Proxmox VM 120 and its hostname) has no env token. The PR #240 apps `ca-usnm-qw-{i}`, `ca-usnm-qws-{i}` and `ca-usnm-qwl-0` have none either.
8. Workbook display names say `usnewsmap` (`usnewsmap pipeline`, `usnewsmap API`), as do the image repositories, while everything else says `usnm`.
9. Custom role display names use spaces: `usnm deployer (25bf257c/rg-usnm-prod)`, `usnm search log writer (…)`, `usnm OCR node writer (…)`.
10. Design doc 08 §8.1 and ADR-0008 use names that don't exist: `stusnmdata`, `stusnmtiles`, `job-ingest-*`.
11. Planned resources already disagree: PR #304 names the data collection rule `dcr-usnm-ocr-nodes-{env}`, design doc 12 says `dcr-usnm-ocrnodes-<env>`.
12. Some names already start with `usnm`: the Entra group `usnm-ocr-nodes-prod`, the deployment stacks `usnm-prod`, `usnm-guardrails` and `usnm-archive`, the policy definitions `usnm-deny-*` and `usnm-audit-*`, the lock `usnm-archive-keep`, and the Arc machine.

The maintainer asked for one order: the `usnm` prefix, a short function, the type abbreviation, and the environment last, as in `usnm-ocr-appi-prod`. Several facts shape how far and how fast that can go:

- **Azure has no rename.** "The resource name in Azure is immutable… you must delete the resource in Azure and then recreate it" ([Arc][arc]); a resource group can't be renamed either ([ARM FAQ][faq]). Only display properties can change in place: a custom role's `roleName` ("Even if a role is renamed, the role ID does not change", [custom roles][roles]), a workbook's `displayName` ([workbooks][wb]), a policy definition's `displayName`, and an Entra group's `displayName` ([Graph group][grp]).
- **The stack deletes what it no longer declares.** `usnm-prod` deploys with `--action-on-unmanage deleteResources` and `denyDelete` (ADR-0011). Changing a name in Bicep creates the new resource and deletes the old one in the same run. For the data lake (about 7.24 TB), Cosmos DB, the registry and the Log Analytics workspace that loses data unless a migration or a detach comes first. The repo already avoids renames for this reason in three places: the policy definition still named `audit` although it denies (`guardrails.bicep:133-136`), the federated credential `github-main` (`registry.bicep:43-45`) and the deployer role seed `usnm-swa-deployer` (`deployer.bicep:22-24`).
- **Some types can't take hyphens or long names.** Storage accounts are 3-24 lowercase letters and digits and globally unique; container registries are 5-50 alphanumerics and globally unique ([naming rules][r]). Container app and job names "must be less than 32 characters" ([CLI][cli]). Cosmos DB accounts are 3-44 ([naming rules][r]; the template reference says 50, so the stricter 44 applies). Key Vault names are 3-24 ([naming rules][r]). An action group's `groupShortName` is at most 12 ([template reference][ag]). In #304 an Arc machine's name is also the worker's node id, capped at 32.
- **Global names need a suffix.** Storage, registry, Cosmos DB, the Document Intelligence custom subdomain, Key Vault and App Configuration names are global. `bootstrap.sh` supports any subscription, so the suffix stays.
- **The environment name is too loose.** `scripts/lib/env.sh:13` allows 1-16 characters and `main.bicep` has `@maxLength(16)`. That already overflows a 24-character storage name, and an environment called `archive` would collide with the stack `usnm-archive` and the group `rg-usnm-archive`.
- **Consumers match on type prefixes.** `ingest-alerts.bicep:59-60, 97-98, 249, 253`, `infra/workbooks/pipeline.json:411`, `ops/queries/job-executions.kql:26`, `ops/queries/searcher-health.kql:24`, `scripts/ja-ocr/start-quality.sh:32-52` (hard-coded job names), `scripts/ja-ocr/quality-rows.sh:22` (regex), `scripts/bootstrap.sh:117` (Cosmos free-tier filter) and `scripts/teardown.sh:84`. The public status page redacts resource names by the same prefixes (`crates/usnm-api/src/status/sanitize.rs`, `RESOURCE_PREFIXES`), so a name like `usnm-ocr-appi-prod` would not be redacted today. That list also lacks `di-usnm`, `ag-usnm` and `dcr-usnm`.
- **CAF allows the order.** CAF lists the components type first in its examples (`rg-workload1-prod-001`) but says "Standardize component order" and "Every organization needs a tailored naming convention" ([CAF naming][caf]). It also says "Include only information that remains constant in the name" and that not every resource allows a delimiter ([CAF naming][caf]).

Priorities are search latency and running cost, a single maintainer, and Bicep for every Azure change. Dev holds zero resources unless an experiment runs, so dev can adopt any convention for free.

## Decision

### Form

- **Hyphenated:** `usnm-{desc}-{abbr}-{env}`, for example `usnm-ocr-appi-prod`, `usnm-ingest-caj-prod`, `usnm-api-searches-slow-alert-prod`.
- **Hyphenated global:** `usnm-{desc}-{abbr}-{env}-{sfx}` for types whose name is unique across Azure and allows hyphens, for example `usnm-state-cosno-prod-ffapzy`, `usnm-jaocr-di-prod-ffapzy`. The suffix stays after `env` on these names, decided by the maintainer, 10 October 2026 (see Alternatives).
- **Compact:** `usnm{fn}{abbr}{env}{sfx}` for types that allow only letters and digits or cap names at 24 characters (storage accounts, registries, Key Vaults), for example `usnmocrstprodffapzy`, `usnmscratchstprodffapzy`.
- Everything is lowercase ASCII letters and digits, with single hyphens in the hyphenated forms.

### Tokens

| Token  | Rule                                                                                                                                                                                                                                                                                                                                                            |
| ------ | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `usnm` | Fixed project prefix.                                                                                                                                                                                                                                                                                                                                           |
| `desc` | A function word from the registry below, followed by up to three qualifier words when one function has several resources of the same type (alerts, private endpoints, nodes, cluster members). A function word is 2-9 characters, starts with a letter and has no hyphen; a qualifier is 1-12. Compact names use the function word alone, at most 7 characters. |
| `abbr` | The type abbreviation from the table below. A function word is never an abbreviation.                                                                                                                                                                                                                                                                           |
| `env`  | `prod`, `dev`, or a short-lived experiment `x{topic}`: `^(prod\|dev\|x[a-z0-9]{1,4})$`, at most 5 characters.                                                                                                                                                                                                                                                   |
| `sfx`  | The existing deployment suffix, `take(uniqueString(subscription().id, env), 6)` (`ffapzy` in prod). Only on global types. It is the one token allowed after `env`, in the slot where CAF puts its instance number.                                                                                                                                              |

Instance numbers go inside `desc`, never after `env`: `usnm-ocr-node2-arcs-prod`, `usnm-qw-3-ca-dev`.

The env rule replaces `^[a-z][a-z0-9]{0,15}$` in `valid_env_name` and `@maxLength(16)` in `main.bicep`. It is a closed list, so `guardrails`, `archive` and `shared` can no longer be environment names, and the reserved-word check in `env.sh` becomes unnecessary. CI's lint environment changes from `ci` to `dev` (`.github/workflows/ci.yml:228`), since `ci` is a function word.

**Parsing.** Split on hyphens. The first token is `usnm`. The last is `env`, or `sfx` with `env` just before it on a global type. The token before `env` is `abbr`, and everything between `usnm` and `abbr` is `desc`. `abbr` and `env` come from closed lists, so the split is unambiguous, and `usnm-*` names that aren't resources (`usnm-ingest`, `usnm-ocr-worker`) never parse as resources.

### Display names

Where Azure fixes the real name as a GUID, the display name follows the convention, except for workbook titles:

- Custom role `roleName`: `usnm-{desc}-role-{env} ({sub8}/{rg})`. The resource group stays in it because `roleName` is unique per tenant ([custom roles][roles]); without it, a side-by-side rebuild would create new role IDs with the same `roleName` and fail while the old roles exist. The role ID and its `guid()` seed don't change.
- Workbook `displayName`: a readable title, `usnm {Title} ({env})`, for example `usnm pipeline (prod)` and `usnm API (prod)`, decided by the maintainer, 10 October 2026. People read these titles in the portal's workbook gallery, and the workbook resource name is a GUID anyway. The titles still come from `names()`, and the CI check matches them against `^usnm [A-Za-z ]+ \((prod|dev|x[a-z0-9]{1,4})\)$`.
- Entra group `displayName` and `mailNickname`: `usnm-{desc}-grp-{env}`.

### Governance objects

Deployment stacks keep `usnm-{env}` and `usnm-{purpose}`; policy definitions and assignments keep `usnm-{effect}-{subject}`. They already start with `usnm` and are subscription-level handles. A policy definition's `name` can't change, and an assigned definition can't be deleted (`guardrails.bicep:133-136`), so a rename would be add, reassign, delete across three provisions for no gain. `teardown.sh` finds environments by stack name. Display names can change.

### Not covered

- **Child resources** keep plain names: blob containers, queues, file shares, the Cosmos database `usnm` and its containers, subnets, diagnostic settings (`to-log-analytics`), federated credentials (`github-main`, `github-ids`), Container Apps environment storages (`ingest-scratch`) and workload profiles, DNS records, private DNS zone links and DCR associations. Code depends on them and their parent carries the convention.
- **GUID names**: role assignments, Cosmos SQL role assignments, role definition IDs, workbook names.
- **Names Azure generates**: managed certificates (`mc-cae-usnm-prod-usnewsmap-com-0857` and two others), the `ME_cae-usnm-prod_rg-usnm-prod_eastus2` group of the existing environment, the NICs of the existing private endpoints (`pe-usnm-blob.nic.<guid>`), and execution names (`caj-usnm-ingest-prod-8dmuvwz`; after a rename the env is no longer the last token, and `ops/index-history.json` keeps its 9 old execution names as history).
- **Domains**: `usnewsmap.com` and the `privatelink.*` zones.
- **Module deployment names** (`Microsoft.Resources/deployments` in the deployment history), such as `ocr-exchange`, `policy-assignments-spot` and `diagnostics-${dataStorageName}`. They are history entries, not resources, and the CI string check skips a module's `name:`.
- **Names outside Azure** that share the prefix: crates and binaries, telemetry roles `usnm-api`, `usnm-web` and `usnm-ocr-worker`, the Quickwit cluster `usnm-searcher`, the `usnm-ocr-worker.service` unit, the Linux user `usnm`, the `usnewsmap-*` image repositories, and GitHub variable names.
- **Other projects** in subscription 25bf257c (hyperfix, atlasrelay and their groups). Other projects in the subscription don't use the `usnm` prefix, and nothing here renames, moves or matches them. The only prefix matches left after Phase 0 are `teardown.sh`'s lookup of policy definitions (`/policyDefinitions/usnm-`), which stay in the governance form, and its lookup of environment stacks, which Phase 0 narrows to the closed environment list.

### Where names are built

`infra/naming.bicep` is the only file that spells out a resource name. It exports user-defined functions:

```bicep
@export()
func usnmName(desc string, abbr string, env string) string => 'usnm-${desc}-${abbr}-${env}'

@export()
func usnmGlobalName(desc string, abbr string, env string, sfx string) string => '${usnmName(desc, abbr, env)}-${sfx}'

@export()
func usnmCompactName(fn string, abbr string, env string, sfx string) string => 'usnm${fn}${abbr}${env}${sfx}'

// One key per resource, sorted alphabetically.
@export()
func names(env string, sfx string, pinned bool) object => {
  dataLake: pinned ? 'stusnmd${sfx}' : usnmCompactName('data', 'st', env, sfx)
  ingestJob: pinned ? 'caj-usnm-ingest-${env}' : usnmName('ingest', 'caj', env)
  // Phase 1 deletes this ternary.
  ocrExchange: pinned ? 'stusnmo${sfx}' : usnmCompactName('ocr', 'st', env, sfx)
  // Create-only properties: empty when pinned, and the module leaves them unset.
  stateSqlNic: pinned ? '' : usnmName('state-sql', 'nic', env)
  // ...
}
```

`main.bicep` imports `names`, sets `var n = names(env, suffix, suffix == legacyProdSuffix)` with `var legacyProdSuffix = 'ffapzy'`, and passes `n.<key>` to every module. The suffix stays a variable in `main.bicep` and is passed in, so naming doesn't depend on deployment scope. `guardrails.bicep` and `archive/main.bicep` keep their names and don't import it.

`pinned` is true only for the current prod deployment, the one whose suffix is `ffapzy` (prod in subscription 25bf257c). It is keyed on the suffix, not on the environment name, because a rebuild in another subscription also runs as `prod` (08 §8.9):

- The current prod keeps its legacy name for every key that is still an exception, including any provision against the old subscription while a rebuild overlaps it.
- A prod rebuilt in another subscription gets a new suffix and comes up fully conventional.
- Dev and experiment environments come up fully conventional, so new names run end to end in dev before prod adopts them.
- Each prod rename PR deletes one ternary.
- Pinning is in code, not in a settings file, so a lost or edited settings file can't rename the data lake, which the stack would then delete.

A prototype of these functions compiles with the Bicep version CI pins (0.47.16), and `bicep build-params` evaluates them offline, `uniqueString` included: `names('prod', 'ffapzy', true)` gives `stusnmdffapzy` and `caj-usnm-ingest-prod`. Older Bicep builds reject `func` (BCP343, an experimental feature there), so local scripts call `az bicep` or the binary `scripts/ci/install-bicep.sh` installs, not whatever `bicep` is on `PATH`.

New Container Apps environments set `infrastructureResourceGroup` and new private endpoints set `customNetworkInterfaceName`, because both can only be set at creation ([custom VNet][cvnet], [private endpoints][pe]). The existing prod endpoints (`pe-usnm-blob`, `pe-usnm-cosmos`) and `cae-usnm-prod` are declared by the same modules as dev's, so these values go through `names()` too: a NIC-name or infrastructure-group key returns `''` when pinned, and the module sets the property only when the value is not empty. Otherwise the next prod provision would try to change a create-only property and fail.

### Rules of use

1. A new resource takes its conventional name from its first commit, in every environment.
2. A prod name in the exception table keeps its name until its trigger.
3. Names are built only in `infra/naming.bicep`. Modules receive names as parameters; consumers read them from stack outputs or settings, never rebuild them.
4. Scripts and KQL never match on a type prefix such as `caj-usnm-`. They use outputs, the `project` and `environment` tags, or, while legacy names exist, a regex that accepts both forms.

### Phase 4: only at a prod environment rebuild

Triggers: a region move, a subscription move, or Azure forcing a new Container Apps environment. No such rebuild is planned; until one happens these names are documented exceptions, not an open task. Scope: the skeleton in the exception table, plus the lake and Cosmos only if the move copies them anyway.

Side by side works only into another subscription. The stack name (`usnm-{env}`, `env.sh:83`) and the settings file (`.azure/{env}/.env`) depend on the environment name alone, so a second `prod` in the same subscription would replace the live stack, whose `deleteResources` then removes the old resources, or overwrite the live settings. A region move or a forced new Container Apps environment therefore also goes to a new subscription, or first gets a PR that gives the second copy its own stack and settings names.

Runbook:

1. Rehearse the whole sequence on dev first, without DNS, then tear dev down.
2. Build the new environment side by side in the new subscription with `bootstrap.sh prod --subscription NEW --move` (08 §8.9). It gets a new suffix, so `pinned` is false, global names don't collide, and it comes up conventional. Custom roles don't collide because `roleName` carries the resource group. It creates its own `usnewsmap.com` zone, which serves nothing until the registrar delegates to it. Its first provision creates the new registry; it then runs CI, which fails because that registry lacks prod's pinned `quickwit/quickwit-usnm` digest (`scripts/ci/quickwit-image.sh:27-31`). That stop is expected.
3. `az acr import` the pinned `quickwit/quickwit-usnm` digest from the old registry, plus `quickwit/quickwit` and the current API, ingest and ja-ocr digests. Then re-run the same `bootstrap.sh` command; it is idempotent, and this time CI finds the digest and bootstrap finishes.
4. Data: object replication with change feed enabled on the source, and daily blob-inventory comparisons until names and sizes match ([object replication][or]); the fallback is AzCopy in a job inside the VNet, with up to about $145 of Private Link processing. Cosmos: the new environment's account already has the new subscription's free tier if no other account there uses it (`bootstrap.sh:115-123`), so nothing is deleted. Pause ingest and backfill in the old environment, export the old account, import into the new one at raised RU/s, and compare counts per container. The old environment keeps serving search and the status page throughout; ingest stays paused until cutover.
5. The day before cutover: 60 s TTLs on `@`, `www` and `api` in the live zone, and the new environment's `asuid` verification TXT records added to it. Issue Let's Encrypt DNS-01 certificates for the three hostnames (TXT records in the live zone), upload them to the new environment, and write their ids to `USNM_SITE_CERT_ID`, `USNM_WWW_CERT_ID` and `USNM_API_CERT_ID` in its settings, so its next provision binds all three hostnames with no managed-certificate wait.
6. Cutover on a weekday at 6:00 AM ET: delegate the domain to the new zone's name servers (08 §8.9 step 3). The old stack stays attached: `teardown.sh` in step 9 reads its managed resource IDs, saves them to its resume file and only then detaches it (`scripts/teardown.sh:64-77, :179-185`). The certificate settings keep the uploaded ids through cutover; a setting on a live hostname is never cleared, because `containerapp.bicep:228` drops any hostname whose certificate id is empty. Later, and within the 90-day life of those certificates, move one hostname at a time to a managed certificate: `az containerapp hostname bind` while the Let's Encrypt certificate is still bound, then write the new id to the setting.
7. Re-onboard the OCR nodes into the new group.
8. Export `CDBControlPlaneRequests` and `ContainerRegistryRepositoryEvents` (the 365-day audit tables, #231) to the lake before deleting the old workspace. A deleted workspace holds its name for 14 days ([delete workspace][law]).
9. Tear down the old subscription's environment with `teardown.sh prod --subscription OLD`. Then one PR deletes the remaining ternaries and `legacyProdSuffix` and updates `prod.json`. From that commit on, the old subscription is never provisioned again.

Cost depends on the data path. Object replication: about $4-5 a day of duplicate storage while the copies overlap (7,244 GB at about $0.018 per GB-month is about $130 a month), plus the rehearsal. The AzCopy fallback adds up to about $145. In total about $100-300 one-time, which pushes that month over the $80 budget.

## Enforcement

Three layers. The first needs no Azure access.

1. **CI name check** in the `infra` job: `scripts/ci/check-names.py --envs=prod,dev,xabcd`.
   - It runs `bicep build-params` on `infra/names/check.bicepparam`, which imports `names()`. Prod is evaluated twice: with suffix `ffapzy` (pinned) and with a fixed sample suffix (conventional, as after a rebuild). The other environments use the sample.
   - Each value must match the hyphenated, global or compact pattern for its type, with `abbr` from the table, the function word from the registry, `env` last (only `sfx` after it, only on global types), and the type's length limit at the 5-character env cap. Otherwise its key must be in `infra/names/exceptions.json`, keys sorted, each entry with a reason, the ADR section and an `until` (phase or issue).
   - `exceptions.json` can only shrink against `origin/main`. That stops the list growing; it does not protect prod, because shrinking is exactly the move that renames.
   - The protection is this: the evaluated prod map must equal `infra/names/prod.json`. A prod rename shows up as a reviewed diff to that file and never as a side effect of a refactor.
   - It also fails when `infra/main.bicep` or a module under `infra/modules` builds a resource name from a string containing `usnm` instead of taking a parameter. It looks only at the `name:` of resource declarations (not `guid(...)` arguments and not a module's deployment `name:`) and at `roleName`, `displayName` and `groupShortName`. Descriptions and child scope paths (`${cosmos.id}/dbs/usnm`, `/scratch/usnm`) are out of scope. An allowlist covers the KQL role filters `'usnm-api'` and `'usnm-web'`, the Cosmos database `'usnm'`, and the `guid()` seeds, with a comment that they are frozen: `usnm-swa-deployer`, `usnm-search-log-writer`, `usnm-ocr-node-writer`, `usnm-archive-writer`, `usnm-workbook-pipeline` and `usnm-workbook-api`. Changing a seed would rotate role IDs and workbook GUIDs.
   - And it fails when the abbreviation list in `sanitize.rs` differs from `naming.bicep`.
2. **Rename guard in `provision.sh`.** Before `az stack sub create`, it runs `az deployment sub what-if` with the same template and parameters and reads the stack's managed resources (`az stack sub show`). Outside complete mode, what-if reports a resource the template no longer declares as Ignore, not Delete ([what-if][wi]), and the stack's `deleteResources` then deletes it. So the guard stops when a resource the stack manages, of a protected type (storage account, Cosmos account, registry, Log Analytics workspace, Key Vault, Container Apps environment, VNet, DNS zone), comes back as Ignore, unless `--allow-rename=<name>` names it. A removal with no replacement counts the same as a rename. Because it reads what-if rather than `names()`, it also catches drops from a condition switched off (`USNM_OCR_NODES`, `USNM_INGEST_SCRATCH`, `USNM_DNS_ZONE`; a recreated zone gets new name servers), and it covers provisions from a branch CI never saw.
3. **Names made outside Bicep.** `scripts/lib/names.sh` builds the names scripts create (the Entra group, and the node, VM and Arc name). `group.sh`, `onboard.sh` and `proxmox-create-vm.sh` reject a `--name` that doesn't match `^usnm-ocr-node[0-9]+-arcs-(prod|dev|x[a-z0-9]{1,4})$`. An optional monthly `scripts/names-report.sh --env=prod` lists tagged resources, including those outside the stack (certificates, Arc machines, smart detectors), and flags any name that is neither conventional nor an exception.

## Alternatives

- **Keep CAF's type-first order** (`appi-usnm-ocr-prod`) and only fix the inconsistencies. Cheapest, and it matches CAF's examples and today's sanitizer and KQL prefixes. Rejected because the maintainer asked for `usnm` first, and CAF allows any standard order ([CAF naming][caf]). With `usnm` first, every project resource sorts together in the portal and in `az` listings of a subscription shared with other projects.
- **Rename everything at once** with a side-by-side prod rebuild in November, tied to the #283 index rebuild, reaching full compliance in about a month. Rejected: it means a 7.24 TB lake copy, a 2-3 hour Cosmos delete-and-recreate window, a DNS and TLS cutover, two Arc re-onboards, a migrated archive and guardrails, and about $100-300 one-time plus a budget overrun, all for naming. Tying it to #283 would also make a search regression impossible to attribute. Its cutover mechanics are kept as the Phase 4 runbook.
- **Drop the suffix** so every name ends in `env` (`usnmocrstprod`). Rejected by the maintainer, 10 October 2026: it rules out a side-by-side rebuild in another subscription, and a name taken elsewhere in Azure fails the deployment.
- **Put an instance number after `env`** (`usnm-ocr-arcs-prod-01`). Rejected: the maintainer's pattern ends with the environment, and numbers fit inside `desc`.
- **The Naming Tool's alert abbreviations** (`insqr`, `inma`). Rejected for one readable `alert`.

## Consequences

- New resources, dev and experiments are conventional from now on at no cost. Prod reaches the convention for everything except its skeleton, the lake, Cosmos, the archive and the governance objects by the end of Phase 3. Phases 0-3 cause no API revision and don't change search latency; running cost stays the same or drops slightly with the tiles account gone.
- About a dozen prod names stay legacy indefinitely, documented here and in `exceptions.json`, until a rebuild happens for its own reasons.
- KQL, workbooks and scripts match both forms during the transition and while old logs are retained (30 days; 365 for the audit tables).
- The status page sanitizer must learn the new forms before the first new name reaches prod.
- Environment names become a closed list of at most 5 characters; CI lints as `dev`.
- Every Bicep change that touches names gets the `prod.json` check, and every provision gets the rename guard, which protects the lake and Cosmos from an accidental delete regardless of naming.

## Open questions

The maintainer decided four earlier questions on 10 October 2026: the suffix stays after `env` (Form), Phase 2 runs now (Phase 2), the Spot resource group goes in Phase 1 (Phase 1), and workbook titles stay readable (Display names). One remains:

1. **Key Vault in dev** (Key Vault isn't built yet, #295). A soft-deleted vault holds its name for 7-90 days ([Key Vault soft delete][kvsd]), which blocks a dev rebuild under the same name. Turn off purge protection in dev and purge on teardown, or vary the dev suffix?
