**Implementation notes (first slice, [`web/`](../../web/README.md)):**

- The timeline is a small SVG bar chart rather than uPlot, because it has one series until compare mode lands.
- Controls are native elements, so Radix and Zustand aren't needed yet.
- The default Positron basemap uses the versioned overview bundle pinned by `web/basemap.json`: global zooms 0–2 and U.S./surroundings zooms 3–5. It is not a Protomaps-schema archive: keeping OpenMapTiles throughout avoids incompatible style layers when switching to OpenFreeMap detail. The API serves immutable, versioned assets directly; Cloudflare edge caching requires the planned proxy cutover and a cache rule. `web/README.md` documents publication and rollback.
- `/datasets` ("Dataset details") is a separate page that says what the site searches, where its text comes from and what the ingest pipeline is doing, from `GET /v1/status`, `GET /v1/versions` and `GET /v1/meta`, and refreshes every 30 s (§7.10). It is lazy-loaded; the app has no router, so `main.tsx` picks it by path with `src/route.ts`. The footer links to it. Its old path, `/status`, redirects to it (the API answers 301; a server that doesn't, such as the dev server, gets the same page and the app replaces the URL). Any other path shows a not-found page, and the API sends it with a 404.
- `/privacy` is the privacy notice (lazy-loaded like `/datasets`, `src/privacy/PrivacyPage.tsx`). The search page, the dataset details page and the not-found page link to it in their footers. It is in `sitemap.xml`, and the API gives its copy of `index.html` its own title, canonical link and `og:url` (`shell_for` in `crates/usnm-api/src/site.rs`).
- Admitted base search URLs (curated examples and recurring searches promoted into the sitemap) open with a static rendering of the same map, timeline and search view, plus a query heading, matching-page count, and up to ten cited newspaper excerpts from the highest-hit city. The map uses the existing browser screenshot renderer, basemap and result data, cached by frontend and index identity and persisted for admitted searches. `/search-map.png` serves only admitted base searches and returns an explicit retryable error instead of an unrelated generic image if capture fails. Background warming includes these base searches. This content is visible without JavaScript and lives outside React's root. With JavaScript, the application mounts automatically in a hidden, inert container with full layout; only after search results, the basemap and the result overlay are ready does it replace all static elements. Failed or crawler-blocked API requests leave the static map and results intact. Other searches and filtered variants keep the dynamic application and `noindex`; the server uses the same sitemap admission policy to choose the rendering path. Preview HTML uses the existing versioned cache, invalidated with the sitemap renderer fingerprint.
- `robots.txt` keeps crawlers (`User-agent: *`) off `/v1/` and `/api/v1/`, and gives the fetchers that AI assistants send when a person asks them something (`Claude-User`, `ChatGPT-User`, `Perplexity-User`, `MistralAI-User`, `Google-Agent`) their own group with `Allow: /`, so they can call the API; training and search-index crawlers stay under `*`. `llms.txt` (in `web/public/`, served as `text/plain` like any static file, no `X-Robots-Tag`) describes the site, the API routes and parameters, and the 429, 503 and 202 retry rules for those agents. Update it when a route or parameter changes.

**Search bar.** One row: the search box, the match mode, From and To, an "Options" button and Search. The filters (the Newspapers or Congress switch, States, Languages and Newspapers) are in a panel the Options button opens below it. The button is a native `<button>` with `aria-expanded` and `aria-controls`; Escape in the panel or on the button closes it and returns focus to the button; a language or newspaper list inside the panel takes its own Escape first. A press outside the panel closes it too. The button counts the filters in use ("Options (2)"), so a link with filters shows them without opening the panel. On phones the same button holds the match mode and dates as well, counts them too, and starts open when the search uses any of them. When the viewport crosses the breakpoint, the button starts over in the state the new layout would open with. A States entry the browser rejects on Search opens the panel, so the browser can focus it. Tests: `web/src/components/SearchBar.options.test.tsx` and `web/e2e/app.spec.ts`.

### Side panel

With a place selected, the panel lists that place's pages. With none selected, it lists places for the current measure, in the playback window (everything up to the scrubber's date, or the "Last N" window ending there, and the lists' notes say which), and each place name opens its pages:

- **Pages:** "Most pages", the places and the states with the most matching pages, five of each at first, with each one's share of them. A state counts the places in it.
- **Median date:** "Earliest and latest", the places with the earliest and the latest median date, five of each at first, among places with at least 5 matching pages (one page has a date, not a median). Every such place is in one list or the other: the earlier half (one more when there is an odd number) under Earliest, earliest first, and the later half under Latest, latest first, so none is in both however long the lists grow, ties included. The search's buckets only place a median in its month (or year). So the places that could be listed, as far down as each list shows, get their matching pages per day from `/v1/days` (06 §6.3.9), and the lists rank and label them by the exact day ("Jan 14, 1895"). Those places are, at each end, the ones ranked by bucket up to the last one shown, plus every place sharing its bucket. The places below them, which no list shows, keep their bucket's order. Every day in the buckets above comes before every bucket below, so the order holds where the two meet. The counts ("Showing 5 of 40.") are of every place. A request takes at most 20 places, and the app sends one after another for more; it asks for each place's days once per search, so a longer list, or the same places at a new date, asks only for the places it adds. With five in each list, as at first, the set is the one the lists asked for before they could grow, and it costs the same one request. A set may hold one request's worth (20 places) for every five places the two lists show between them (up to 100 with 25 in each). Past that, the lists keep the bucket, since a partial set could leave out the true earliest, and say so ("Too many places share a median month to look up each one's day, so these lists go by month."). The first set for a search, and the first after Show more or Show fewer, is asked for at once. Until the search's first answer, the panel says "Finding each place's median day…" and lists nothing, so a month-level list is never shown and then swapped for the exact one. Later sets (playback, scrubbing) are asked for once the set has held still for a second, and meanwhile the last exact lists stay, dimmed and marked "Updating for the new date…" (or "Finding the listed places' median days…" after Show more or Show fewer). The lists rank by the bucket only when that is final: a search by day (its buckets are days, so no request), more tied places than the lists' lengths allow, or a failed request.
- **Relative rate:** "Clearest differences" (11 §11.6).

**Show more.** The Clearest differences lists, both Pages lists and both Median date lists start at five and say how many there are ("Showing 5 of 12."); "Show more" adds the next five, up to 25 ("Showing 25 of 40. The table lists every place."), and "Show fewer" goes back to five. Each list expands on its own, and all go back to five when the search, bucket, window or measure changes, but not when the date moves. Both buttons carry `aria-expanded` (true once more than five show) and `aria-controls` naming the list; after "Show more" focus moves to the first entry added (its place button, or the state's row), and after "Show fewer" to "Show more". On the Median date lists, the entries a press adds are ranked by bucket until their exact days arrive, and may then move, past the end of the list among them. So focus stays on "Show more" while the lists are updating and then moves to the first added entry in the final order (also when the days fail and the lists fall back to the bucket). If the reader has moved focus elsewhere meanwhile, it stays there (`ShownList`'s `ranking`). How many each list shows is kept in `App` (`useListLengths`), so it survives the phone breakpoint moving the lists; the hook and the list with its buttons (`ShownList`) are in `web/src/components/ListLength.tsx`, and the URL doesn't record them. The Median date lists' lengths also decide which places' exact median days are asked for (above). Tests: `web/src/components/ListLength.test.tsx`, `Skew.test.tsx`, `PlaceLists.test.tsx`.

**Prefetching the page lists (#265).** Once a search's lists are final, the app asks in the background for the first page of the place panel's list (`/v1/hits`, `limit=20`, the panel's sort, pinned to the version) for the places at each end of them: the 3 clearest above and the 3 clearest below 1× (relative rate), the 3 places with the most pages (Pages; the states list opens no panel), or the 3 earliest and 3 latest median dates. Opening one of them then shows its pages at once, and the API's in-process and Blob caches hold the answers for later visitors of the same search (06 §6.5). Final means the search's own `200` (never while it is computing or queued, nor the last search's results shown meanwhile), the relative rate fitted (or found unavailable), and the exact median days answered; and no place is open. It runs once per search and measure, from the lists as they first stand, so playback and scrubbing ask for nothing more, and switching back to a measure asks for nothing again. All of a search's measures share one queue: a place already asked for under another measure isn't asked for twice, and at most 2 requests are in flight; a prefetch that gets a `202` waits for the answer as the panel does, but one that finds the API busy (`503`) or gets a `429` gives up, and it is never retried. A new search cancels the requests still running, except one a panel opened meanwhile is showing. Nothing is prefetched when the browser asks to save data (`navigator.connection.saveData`). Japanese searches are prefetched too: `/v1/hits` searches the Japanese pages for them as `/v1/aggregate` does. The panel and the prefetch share one query (`placeHitsQuery` in `web/src/components/placeHits.ts`), so the panel finds the prefetched list under its own query key, and the request URL, which the API caches by, is the same. The key leaves out the time bucket, as the request does, so another bucket of the same search reuses the lists and prefetches nothing again. Tests: `web/src/components/placeHits.test.tsx`.

"Hide" collapses the lists to a "Show …" button and gives the map the width. The choice applies to all three measures and is kept in `localStorage` (`usnm.lists`), not the URL: it is how this visitor likes the page, not part of the search.

### Key states

- **Empty:** example searches as cards, and a coverage map preview. The cards come from the 100 in `web/src/examples.json` ("Cross of Gold, 1896", "Dred Scott", "Marshall Plan"): three at first, then "Show more examples" adds the next ten below them (the last press shows what remains) until every example has shown, when the button goes away. Nothing is replaced or repeated, and focus moves to the first new card. The order is random per page load. The examples' seven eras (1828–1860 to 1945–1963) take turns, the biggest first. The whole order then starts at a random point where every set of three from the start still spans three eras, so the first three cards, and each row of three as the list grows on a wide screen, come from three different eras. Some examples search one language's papers (German, French, Spanish, Italian, Polish); before 1945 those languages have enough places to map, after it none has more than five.
- **Loading:** a skeleton shimmer on the timeline, the previous results dimmed, and a cancel button.
- **Large search:** when the API answers `202` (06 §6.3.5), a status notice (`role="status"`), "Large search, still working…", stays up while the client asks again after each `Retry-After`. While the API says the search is queued for a slot, the notice says how many searches are ahead instead: "Other searches are running. Yours is in line behind 2 more…", or "…next in line…". It stops asking when the visitor changes the search (the query's abort signal). After 150 s from its first request (time queued for a slot included), a little more than the API's 2-minute limit on a computation, it stops and shows the timeout problem. A timed-out or busy search is not retried at once (`isRetryable` in `src/api/client.ts`).
- **No results:** suggestions (switch to "all words", enable OCR-tolerant, widen dates), with a link to the coverage layer.
- **Error:** the problem+json `hint` shown inline.

## 7.3 Client-side temporal engine (replaces `/update`)

The legacy app called the server on **every** animation frame. The new client gets a sparse cube once (see [06 §6.3.3](06-api-design.md#633-get-v1aggregate-response)) and computes every view locally.

**Data structure.** For P places with hits and B buckets:

- Build a **per-place prefix-sum array** `S[p][b] = Σ_{k≤b} hits[p][k]` as a flat `Uint32Array` of size `P × (B+1)`. The worst realistic case is 3,000 × 211 ≈ 633k × 4 bytes ≈ 2.5 MB. A Web Worker builds it in under 20 ms.
- **Cumulative** view at bucket `t`: `v[p] = S[p][t]`.
- **Trailing window** of `w` buckets: `v[p] = S[p][t] − S[p][t−w]`.
- **Share of pages published** (a column in the place table): the same prefix sums over the baseline cube, `rel = v_hits / v_baseline`. The map measure that coloured places by it (`norm=rel`) was removed in October 2026; old `norm=rel` links open on Pages.
- **First appearance** layer: color by `first_day[p]`, and show only places where `first_day ≤ t` (animates the spread).

Every frame is **O(P)**: about 3,000 subtractions, then a single deck.gl attribute buffer update. That comfortably holds 60 fps, whereas the legacy server round-trip ran at 400 ms per frame.

**Sub-bucket playback:** if the user picks Day but the response is weekly (a long range), the UI offers to "refine": it re-queries at day granularity for a range of 4 months or less around the scrubber.

**States implementation (#452).** `layer=states` is available for Pages on the
map, without newspaper filters or Congress, when coverage baselines exist. The
first pass uses solid grey for no pages (a hatched legend swatch), light neutral
for no matches, and five positive-rate quantiles that follow the current window,
keeping ties together. Counts are summed before division, including
coverage-only places: reducing coverage to matching places would inflate rates.
Modern Census 2024 borders include DC and five territories. A lazy
content-hashed GeoJSON asset measures 16,221 bytes gzip. The sortable states
table is the keyboard equivalent, includes Unassigned and CSV, and stays
available without WebGL. Desktop clicks add a state filter; mobile taps pin
details with explicit Filter/Dismiss controls. Truncated matching-place lists
show a warning and never invent an allocation of the missing tail. The minimum
denominator is one page with a small-count warning, not an arbitrary suppression
threshold. See the
[web implementation decisions](../../web/README.md#states-layer) and
[reproducible Census preparation](../../web/src/assets/README.md). States uses a
native MapLibre GeoJSON source with promoted state-code IDs and feature-state
colours below symbol labels; scrubbing does not replace geometry. This replaces
the original recommended deck `GeoJsonLayer`, whose cold luma pipeline linking
caused synchronous stalls. Points and Heat retain deck. The
[opt-in performance gates and measurements](../../web/README.md#states-performance-measurements)
retain the original 489/547 ms cold failures and dependency-level reproduction.
The native follow-up measures actual state-colour pixels in composited browser
frames: five unique-shader selection runs took 124–145 ms and five direct-URL
runs 238–263 ms on M1/Chromium/Metal. Direct States entry defers constructing
the unused deck overlay until a different layer needs it. The 5,000-place gate
now asserts the measured maximum, not just the p95: five isolated 2,000-frame
runs passed below 0.1 ms; concurrent and GC runs still exceeded 2 ms and remain
recorded failures. These are fixture- and hardware-specific results, not
software-renderer, real-network, globally cold-driver or arbitrary-load
guarantees.

## 7.6 Accessibility (WCAG 2.2 AA)

- Every map view has an equivalent **List/Table** tab (place, state, hits, relative, first appearance, last seen), sortable and exportable.
- **Days (#127).** The summary's line under the toolbar starts "Matching pages on 123 days." (`total.days`), and the place panel says "72 pages in this search on 54 days" (`days` on the first `/v1/hits` page), which separates a one-day burst from steady coverage.
- **Newspapers (#121).** Under the place table, a "Newspapers" table from the aggregate's `papers`: newspaper, place and matching pages between the search's dates, the first 25 with "Show all", a "Download newspapers CSV" button (`lccn,newspaper,place,matching_pages`), and on each row "Only this newspaper", which sets the `lccn` filter (in the URL as `lccn=`), and "Issues at loc.gov", the paper's page at the Library of Congress (§7.13). The search options' newspaper filter (§7.13) sets the same filter. While it is on, a notice names the papers with "Show every newspaper". The relative rate isn't available under it (the baselines aren't kept per title, 06 §6.3.3). Under the summary, a line gives the language mix when more than one language has matches: "Matches in 312 newspapers: English 96%, German 3% and Spanish 1%." Each share is against all matching pages, and a paper in several languages counts in each.
- Playback is keyboard operable: `Space` plays or pauses, `←`/`→` step, `Shift+←/→` jumps 10 buckets, `Home`/`End` go to the ends. Focus is visible.
- When `prefers-reduced-motion` is set, autoplay is off and transitions are instant.
- A live region announces "Showing N places, M pages, up to July 12 1896" as the scrubber moves (throttled).
- Text contrast is ≥ 4.5:1 over the map (solid panels, not translucent overlays like the legacy header). Touch targets are ≥ 24 px.

## 7.8 Analytics (privacy-preserving)

As built, the site counts page views and nothing else (`src/pageview.ts`). When the app starts it works out its page (`search`, `datasets`, `privacy` or `not-found`; `datasets` was `status` before #294) and sends one page view to `POST /v1/beacon` on its own origin (06 §6.3.7). The app has no client-side router, so every page shown is a page load and gets exactly one; searching on the home page changes the URL but not the page, and sends nothing.

- **Contents.** The page name and its fixed title (`TITLES` in `src/route.ts`). On the first page view of a page load, also `document.referrer` cut down to its origin (`internal` if it is the site itself, empty if there is none) and the landing URL's `utm_source`, `utm_medium` and `utm_campaign`, lowercased and cut to 64 characters. Later page views of the same load, if there ever are any, say `internal`. Never the path, the query string or the search; the API refuses any field beyond these.
- **Sending.** `navigator.sendBeacon` with the JSON as a string (sent as `text/plain`, so no preflight), falling back to `fetch` with `keepalive` if `sendBeacon` is missing or refuses. It never delays the page, and failures are ignored.
- **When.** Only when the page's origin is `https://usnewsmap.com` in a production build, so `npm run dev`, `vite preview` and the end-to-end runs send nothing, except the tests that load the build as that origin on purpose (below). `VITE_PAGE_VIEWS=1` at build time turns it on for any origin (to try it against a local API) and `0` turns it off. `navigator.doNotTrack === "1"` (or `window.doNotTrack`) and `navigator.globalPrivacyControl === true` turn it off in every case, and the API drops page views that arrive with `DNT: 1` or `Sec-GPC: 1`.
- **Storage.** Nothing: no cookies, no local or session storage, no IndexedDB, no Cache Storage, and no user, session or device id. An end-to-end test (`e2e/pageview.spec.ts`) loads a search and checks all of those are empty.
- **CSP.** The request is same-origin, so `connect-src 'self'` already allows it; the policy is unchanged.
- **Tests.** Unit tests cover the report's fields, the origin and tag handling, the opt-outs and the fallback (`src/pageview.test.ts`). The end-to-end tests load the build as `https://usnewsmap.com` (every request to that origin answered by the local server) and assert the exact body of each page view, that it carries no search text, and that GPC, DNT and other origins send none.

The earlier plan for this section (the Application Insights JavaScript SDK with custom events for searches, playback and sharing) is not built: the SDK can't authenticate to a component with local auth disabled. Popular queries for pre-warming, if they are ever collected, would come from the server side as daily counts per canonical query string, kept only when at least 5 requests made the same one that day, with no IP, user agent or other identifier.

## 7.9 Language filter

Visitors can limit a search to newspapers printed in chosen languages, for example to see where the German-language press carried a story.

**Where it lives.** In the search form's options, after States: a "Languages" button that opens a checklist below it. The button says what is chosen ("Languages: any", "Languages: German", "Languages: 3 chosen"). It sits in the panel the "Options (n)" button opens (§7.2), and a language choice counts as one in that number. Like States and the dates, a change applies when the visitor presses Search, so a choice and a new query go out as one search.

**The choices.** `GET /v1/meta` lists the catalog's languages for the published version (`languages`, 06 §6.3.2): each language the `lang` parameter accepts, with its newspapers (titles) and, when the snapshot records them, pages. The list is in that order, most pages first (most newspapers when pages aren't known), so English comes first. Each choice reads "German (2 newspapers)", with the name from `web/src/lib/languages.ts` (the catalog's own name for a language that file doesn't list). Languages the catalog records without a three-letter code, and newspapers with no language recorded, can't be filtered on and aren't offered. A code in the URL that isn't in the list (an older link, or a language no published newspaper has) is still shown, checked, at the end of the list, so it can be cleared.

**How it combines.** Languages are "any of": `lang=ger,spa` finds pages from newspapers in German or in Spanish. The other filters narrow it further: dates, States and match mode all apply as well ("German newspapers in Texas and Wisconsin").

**Multilingual newspapers.** The search index stores each page's languages from its newspaper's catalog record, so a page matches when its newspaper lists any chosen language. A newspaper catalogued as English and German is found by English, by German and by both. It also counts in each of its languages in the checklist, so those counts add up to more than the number of newspapers, as on the dataset details page's "Pages by language" table (06 §6.3.6). The filter is by newspaper, not by the language of the words on a page: an English quotation in a German paper is in the German results.

**Page languages (#289).** On a version that filters by each page's own languages (`/v1/meta`'s `language_filter: "page"`, 05 §5.5.8), the control says so. The button reads "Languages: pages in English", "Languages: pages in German, Spanish", "Languages: pages in 3 languages"; the legend is "Page languages"; the hint "Pages written in any of these, found from each page's words. Leave all unchecked for every language."; and each choice shows pages ("German (412,345 pages)"). The summary's language line reads "Matches in 12 newspapers: pages in English 90% and German 12%." when the aggregate counts by page language (`languages.by: "page"`). On a title-language version everything is as described above.

**URL.** `lang=ger,spa`: lowercase codes, sorted and without repeats, which is the API's canonical order (06 §6.3.1). Anything that isn't three letters is dropped when the URL is read. With nothing chosen the parameter is left out, and the search covers every newspaper. The share link is the page URL, so it carries the filter, and the place panel's page list asks `/v1/hits` with the same `lang`.

**Empty and no-match states.** If `/v1/meta` has no `languages` (an older API) and the URL names none, the control isn't shown. A search that matches nothing under a language filter gets the usual "No pages match" notice, which then suggests removing the language filter as well as the state filter.

**Relative rate.** The relative rate compares each place's matches with what its pages published would predict (doc 11). Under a language filter the API's baselines count only the pages of newspapers that list one of the chosen languages (`series.baseline`, `total.baseline_pages` and `cube.baseline_ref`, 06 §6.3.3), so German matches are compared with German pages and the view works as without a filter. The map, table and CSV behave the same, and the place table keeps its "Share of pages published" column. Two things differ. The "Papers in X and English" line is left out, since the baselines already compare like with like. And a language can have too few places: below 10 places with pages in the window the view says so ("The relative rate needs at least 10 places with pages between these dates. Showing page counts."; the end-to-end build, on its 6-place fixture corpus, uses 5). On a version published before pages were counted per language, the API sends `null` baselines for `lang`; choosing Relative rate then shows "The relative rate isn't available with a language filter on this version of the index. Showing page counts.", and the table leaves out the share column.

**Without a filter (#237).** An English search is compared with English-language newspapers' pages too: the API reads the query's words (06 §6.3.3) and, when they're English, its baselines count the pages of newspapers that list English, while its matches still count every page. The relative rate's info button ("About the relative rate", beside the Pages / Relative rate toggle) says which pages it compares with, from the aggregate's `baseline` (`web/src/lib/baseline.ts`): for an English search, "Each place's matching pages are compared with the pages of its English-language newspapers, since this search's words are English. The few matches in newspapers catalogued in other languages, mostly bilingual papers, still count."; for a Japanese one, its Japanese-language newspapers; under a filter, its newspapers in the languages chosen; otherwise all its newspapers' pages, in every language, with a pointer to Languages. The place table's share of pages published uses the same pages. A place whose newspapers are all in other languages has no English pages, so it drops out of an English search's relative rate, and its share shows "—" (unknown) rather than 0.

**The "Papers in X and English" line.** That line names a place's newspaper languages in the relative-rate lists, tooltips, table and CSV, so a reader can see why a place may read low for an English term. With a language filter on it isn't shown, because the baseline is per language and the reason no longer applies. Without a filter it is unchanged, also for an English search compared with English pages: a bilingual paper's matches in its other language still count, so its place can read high.

**Accessibility.** The button is a native `<button>` with `aria-expanded` and `aria-controls`; the checklist is a `<fieldset>` with the legend "Newspaper languages" and one labelled checkbox per language. Tab and Space work as usual. Escape closes the list and returns focus to the button; a click outside the list closes it and leaves focus where the click put it. The end-to-end test runs axe with the list open.

**Tests.** `web/src/state/url.test.ts` (parsing, canonical order, round trip), `web/src/components/LanguageFilter.test.tsx` (labels, ordering, keyboard, the place table without the share column), `web/src/engine/skewInput.test.ts` (no language line under a filter), `web/src/components/SearchBar.test.ts` (the options count), `web/src/lib/baseline.test.ts` and `web/src/components/MeasureToggle.test.tsx` (which pages the relative rate compares with), `web/src/api/client.test.ts` (`lang` on `/v1/aggregate` and `/v1/hits`), `crates/usnm-api/tests/api/languages.rs` (`lang_filters_by_any_title_language`, `lang_filter_keeps_exact_baselines`, `lang_filter_on_an_older_snapshot_has_no_baseline`, `an_english_query_is_compared_with_english_pages`, `a_language_filter_still_decides_the_baseline`, `a_query_of_uncertain_language_keeps_every_page`) and `reference.rs` beside it (the `languages` list in `/v1/meta`), `web/e2e/skew.spec.ts` (an English search's note) and `web/e2e/language.spec.ts` against the fixture API, whose synthetic titles include one German, one Spanish and one English and German newspaper.

## 7.11 Japanese pages

LoC has no searchable text for its Japanese-language pages, so we read them ourselves (04 §4.8) into an index of their own. A query with any Japanese character searches only that index (06 §6.4, #139). Results never mix the two indexes. The site makes that visible in three places:

- **Search bar.** While the box holds Japanese script (`lib/japanese.ts`, the same ranges as `usnm_core::ja::is_ja`), a note under it says what the search covers: "Japanese searches cover only the 11,058 Japanese-language pages we read ourselves. The Library of Congress has no searchable text for them." The count comes from `/v1/meta` `ja.pages`. Before `/v1/meta` loads there is no note. On a version without a Japanese index the note says the feature isn't available yet, and the API answers such a search with 422. The box points to the note with `aria-describedby`.
- **Input methods.** Typing Japanese uses an input method (IME), and its Enter confirms a word. That Enter must not send the search. The box ignores Enter while a composition is open (`compositionstart`/`compositionend`, `isComposing`), and also when `keyCode` is 229, because Safari ends the composition before the confirming keydown.
- **Hits.** A page whose text is our OCR (`ocr` on the hit, 06 §6.3.4) gets an "Our OCR" badge, with a title explaining that LoC has no searchable text for the page, that ours comes from NDLOCR-Lite, and to expect some misread characters. Its link reads "View the page image at the Library of Congress" and carries no highlight terms, since LoC's viewer has nothing to highlight. The same explanation is also in the badge as visually hidden text, because the title isn't announced reliably and isn't shown on touch screens. On a version that keeps LoC's original text beside ours (`text_layout: 3`, 05 §5.5.7, #925), a page whose `matched_in` has `loc_original` and not `loc` also gets a "Library of Congress OCR" badge (`locOriginalNote` in `lib/matchSource.ts`): our text for the page doesn't contain the match, LoC's text does, and the note says which text the snippet comes from, in the same two places (title and hidden text). A page that matched in ours, alone or with LoC's, has no such badge.

Progress of the OCR itself is on the dataset details page, under "Our OCR of the Japanese-language pages" (§7.10).

## 7.13 Newspaper filter

Visitors can choose newspapers by name and search within them (#274), rather than first running a search that happens to match a paper.

**Where it lives.** In the search form's options, after Languages: a "Newspapers" button that opens a panel below it. The button says what is chosen ("Newspapers: any", "Newspapers: The Omaha Daily Bee", "Newspapers: 3 chosen"). It sits in the panel the "Options (n)" button opens (§7.2), and a newspaper choice counts as one in that number. Like the other filters, a choice applies when the visitor presses Search. Under a Congress search (§7.12) it is hidden and dropped.

**Finding a paper.** The panel has a box: "Type part of a title or a place." Each word typed must begin a word of the title, the place, the state's two-letter code or the LCCN, ignoring case, accents and punctuation, so "omaha bee" finds The Omaha Daily Bee and "nouvelle-orleans" L'Abeille de la Nouvelle-Orléans. Titles that begin with the text come first (a leading "The" aside), then titles that hold every word, then matches on the place; within each, most pages first. The first 50 are listed, each with its title and "Omaha, NE · published 1871–1922 · English · 12,345 pages from 1880 to 1910": place, years of publication, languages, and pages with the years of the paper's first and last pages here, which tell papers of one name apart. "Published" years are the catalog's (the paper's whole run, 06 §6.3.11): "published from 1896" is a run with no end recorded, "published until 1922" one with no start. "Pages from … to …" are the years of its pages in the version (`first_page_date`, `last_page_date`), so a paper published 1871–1922 with pages here from 1880 to 1910 says both. A version that doesn't record the page dates shows the page count alone ("12,345 pages"). Choosing a paper adds it to the papers chosen and clears the box; choosing a chosen one (marked ✓) takes it out. A search can name up to 60, the API's `lccn` limit.

**The list.** `GET /v1/titles` (06 §6.3.11), pinned to the version like `/v1/places` and kept for the session. It loads only when the panel is first opened or the URL names a newspaper, so a visitor who never uses the filter doesn't download it; about 3,000 titles, filtered in the browser. Until it loads the box is disabled ("Loading newspapers…"), and the chosen papers show their LCCNs.

**The papers chosen.** Listed under the box, each with its details, "Issues at loc.gov" (its page at the Library of Congress, in a new tab) and "Remove"; "Clear newspapers" removes all. Papers are "any of", and the other filters narrow them further.

**Browsing a paper without a word.** Searches still need a word. A paper's page at the Library of Congress lists its issues by date, so the filter's chosen papers and each row of the Newspapers table (§7.6) link there. When `/v1/meta` says `browse_pages` (the API's `USNM_BROWSE_PAGES`, off until its cost on the production index is measured, 06 §6.3.4), each chosen paper also has "Browse pages" (#274). It closes the filter and opens "Pages of The Omaha Daily Bee" under the search form, with focus on its heading: "12,345 pages on 3,210 days · every page, with no search word", "Oldest first" and "Newest first", and the pages 20 at a time ("Load more"), each as in the place panel (§7.2) with the opening of its text in place of snippets and its link at the Library of Congress. It lists the paper's whole run, whatever the search's dates, from `/v1/hits?lccn=…&limit=20` with no `q` (`api.titlePages`), kept per version, paper and order. ✕ or Escape closes it. It is local to the page, not in the URL. Without `browse_pages` the button isn't there, and an older API, which doesn't send the key, is treated as off.

**Results.** Under the filter the notice over the results names the papers, with "Show every newspaper": "Only pages from The Fixture Gazette 2 and The Fixture Gazette 6." It names all of them up to three; from four on, two names and "and n more", so never "and 1 more". The names come from the list, else from the aggregate. For one paper it adds ", so the map shows its place only": a title has one place. The relative rate is off, as for "Only this newspaper" (its baselines aren't kept per title, 06 §6.3.3), and its button says why: "Not for one newspaper…" or "Not for chosen newspapers…". A search with no matches suggests removing newspaper, language or state filters.

**URL.** `lccn=sn99000002,sn99000006`: lowercase, sorted and without repeats (§7.5); the share link carries it.

**Accessibility.** The button is a native `<button>` with `aria-expanded` and `aria-controls`. The box is a combobox (`role="combobox"`, `aria-autocomplete="list"`, `aria-expanded`, `aria-controls`, `aria-activedescendant`) over a multi-select listbox ("Newspapers found") whose options carry `aria-selected`; focus stays in the box. ↓ and ↑ move through the matches (wrapping), Enter chooses the highlighted one and never submits the search, and Escape closes the matches, then clears the box, then closes the panel and returns focus to the button. A polite status says how many papers match. The end-to-end test runs axe with the matches and the chosen papers showing.
