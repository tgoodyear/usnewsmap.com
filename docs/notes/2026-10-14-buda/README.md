# BUDA spike procedure for #481

Status: not executed against a BOINC server. [ADR-0020](../../design/adr/0020-boinc-buda-evaluation.md) records the accepted decision not to adopt BUDA under the reviewed implementation. This procedure is retained only as a reference if the decision is reconsidered; it does not authorize a production or experimental deployment. See the [observations](../2026-10-14-buda-evaluation.md) and [completed Mac standalone tests](../2026-10-14-buda-mac-offline-tests.md).

## Inputs and baseline

An operator needs access to the server/bridge job, the offline signing host, a Linux test client and an arm64 Mac. Use a test project or a scheduled experimental revision of the existing server. Confirm the actual deployed BOINC commit; this procedure was reviewed against `22bbebe08e2eaac5d5e88a6d93b88e800cb6341c`.

Record the baseline app versions, active workunit counts and daemon configuration. Keep those observations locally; commit only aggregate test results without account, host or subscription identifiers. Use the [synthetic cached-page fixture](../../boinc/worker-image.md#local-synthetic-demonstration), fresh dispatch and state directories and directory-backed native stores. Do not publish the experimental outputs to the production OCR lake.

Choose a released, anonymously pullable worker image by full GHCR digest. Verify its architecture and preserve the matching engine metadata used by `usnm-boinc export`. The `--image` argument to that exporter is the worker digest `sha256:<hex>`; the Dockerfile needs the full pullable reference `ghcr.io/tgoodyear/usnm-boinc-worker@sha256:<hex>`. Do not substitute the engine or base image digest for the worker digest.

## Add the experimental BOINC app

1. Register the stock app `buda` using the administrator's Manage application page. Retain `usnm_ocr`, `usnm_assess` and `usnm_gold`.
2. Download the Linux wrapper from [release 22](https://github.com/BOINC/boinc/releases/tag/dockerwrapper%2F22) and verify the release asset digest. Version 22 is a prerelease, so record exactly which wrapper was tested.
3. Stage it under `apps/buda/1.0/x86_64-pc-linux-gnu__docker/` with a wrapper-only `version.xml`:

   ```xml
   <version>
       <file>
           <physical_name>docker_wrapper_22_x86_64-pc-linux-gnu</physical_name>
           <main_program/>
       </file>
       <is_wrapper/>
   </version>
   ```

4. Sign this wrapper on the existing offline signing host, using the project's existing key and signing procedure. Transfer only the signed release artifacts to the server. GitHub's checksum and release signature do not replace the project's BOINC code signature.
5. Grant the test operator BUDA administration and submission access through stock `manage_privileges` and the Manage permissions UI. Retain existing entries when adding the BUDA definition to `html/project/remote_apps.inc`. Use the complete PHP example in [BUDA setup](https://github.com/BOINC/boinc/wiki/BUDA-setup).
6. Add the two experimental daemon entries below to the configuration generated by the server revision. The repository's `images/server/lib.sh` renders `config.xml` at startup, so a manual change to the live file is not persistent. Preserve its current app daemons. Validate a staged configuration before restarting.

   ```xml
   <daemon>
       <cmd>sample_trivial_validator --app buda</cmd>
       <output>buda_validator.out</output>
       <pid_file>buda_validator.pid</pid_file>
   </daemon>
   <daemon>
       <cmd>script_assimilator --app buda --script "batch_collect_assimilate.py wu_name batch_id files2"</cmd>
       <output>buda_assimilator.out</output>
       <pid_file>buda_assimilator.pid</pid_file>
   </daemon>
   ```

7. Follow stock `bin/upgrade` and `bin/update_versions` for the staged project. Confirm the script assimilator and its Python script are present in the built image and project, and the `docker` plan class uses the project's current minimum `80213` and detects Docker on the Linux client. Verify the existing daemons still run after startup.

The trivial validator is for transport observations only. Its successful results must not be counted as scientific validation.

## Define the OCR science app and submit a web batch

In the BUDA Manage apps UI, create a uniquely named experimental science app, for example `usnm_ocr_spike_v1`, with:

| Field                      | Value                                                                  |
| -------------------------- | ---------------------------------------------------------------------- |
| Input filenames, in order  | `page request.json`                                                    |
| Output filenames, in order | `text.txt layout.xml result.json`                                      |
| Maximum output size        | 32 MiB per file; keep the native collector's stricter text/JSON limits |
| Turnaround                 | 3 days                                                                 |
| Output compression         | Off for this test                                                      |

Upload a Dockerfile and the existing [job.toml](../../../ocr/boinc/job.toml) to the operator's file sandbox. The Dockerfile is a single `FROM` line containing the confirmed full GHCR worker digest. The image supplies the existing worker command; there is no need to copy executables or compile science code in the Dockerfile. Include `job.toml` as an application file, choose CPU type `intel` and plan class `docker`. At the pinned source the resulting variant name is `intel_docker`; let the UI generate `variant.json` and file metadata.

Copy the two files from a freshly exported synthetic job into a scratch folder `fixture/`, then zip that directory as a BUDA batch. Upload it through the file sandbox and submit it from the BUDA Submit jobs page. Record the actual batch and workunit IDs locally. Run the same page through the current separate app as the baseline, keeping its image and engine metadata identical.

Measure scheduling, cold image download and build time, warm second-job time, peak memory and output permissions. Check the three outputs with the native worker contract checks. Test pause and resume and confirm the runtime limits are enforced. Expect `results/<batch-id>/batch_<batch-id>__job_fixture__file_<filename>` from the web batch. The current bridge cannot collect this name directly; preserve the spool and use a test-only mapping to its original exported `usnm_<job-id>` name before directory-backed collection. A copied spool test is not proof of durable bridge integration.

## Submit through the remote API

Use `submit_rpc_handler.php` with a form POST field named `request` containing `<submit_batch>`. The pinned handler accepts an authenticated batch targeting `<app_name>buda</app_name>` and per-job `<input_template>`/`<output_template>` elements.

Use the generated science app templates, including their `<buda_app_name>usnm_ocr_spike_v1</buda_app_name>` marker, as the per-job templates. Stage the two synthetic inputs using the API's normal supported input-file modes and preserve their order. Supply the baseline resource bounds from `usnm-boinc submit`, including memory, disk, FLOPS and deadline, in the batch's `job_params`. Choose a unique test workunit name and record the returned batch ID before any retries.

This is a hypothesis derived from the generic handler, not a tested BUDA-specific endpoint. Verify authorization with the operator's test account, including a second account without submission privileges. Do not use `tools/submit_buda` for this test: it is local-only debugging and creates no user-associated batch. A successful API response is insufficient; require the task to schedule, execute, validate and assimilate. Test a lost response before implementing bridge retries, since blindly resubmitting can duplicate work.

## Test custom validation and worker identity

Drain the experimental trivial-validator batch before replacing that daemon with a custom validator. Keep the existing three apps' validation untouched.

For an initial stock-BOINC route, use one project-owned `script_validator --app buda` dispatcher with `result_id files` for initialization and `result_id result_id2 files files2` for comparison. Implement that dispatcher as a separate reviewed change: it must look up each result's workunit in the database and use an administrator-owned mapping from immutable science-app identity to the existing check and compare policy. Never route using an app name or script path supplied by the returned JSON. Reject unknown identities and cross-policy comparisons. Database lookup failures must be retryable rather than silently accepted.

| Test                     | Required observation                                                                                                                                                                                                      |
| ------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Assessment check/compare | Valid matching results pass; malformed files and conflicting results fail; use quorum/target 2/2 in an administrator-controlled input template.                                                                           |
| Gold check               | Valid measured output passes the existing check against the server's gold manifest; malformed or forged manifest identity fails.                                                                                          |
| OCR                      | Existing native validation still runs before publication. Do not call this fuzzy consensus validation until #444's validator is integrated and tested.                                                                    |
| Unknown science app      | Dispatcher rejects it before any canonical result/publication.                                                                                                                                                            |
| Late variant edit        | Queue a synthetic task while the client is suspended, change its experimental variant, then resume. Record which files are sent. Repeat with a replacement result. Use a second science-app name for the safe comparison. |
| Recovery                 | Restart between submission and journal persistence, and between assimilation and native collection. Prove one publication and correct worker identity for each page.                                                      |

If stock script dispatch is unsuitable, the upstream change needs to pass trusted workunit and science-app context to the validator hooks and apply administrator-owned policies. A variant JSON validator field alone would not establish either trust or immutable selection.

## Test the arm64 Mac

The [native ARM worker build and tests](../2026-10-14-buda-native-arm64.md) now provide a local ARM image and a dedicated native-only build environment. Use that architecture for further Mac testing. Publishing the image and registering and signing the app version remain server and release work; generate fresh cohorts using the native release digest when one exists.

The version 22 asset `docker_wrapper-22-apple-darwin` contains both `x86_64` and `arm64` slices. BOINC 8.2.15 is now installed and detects the existing Podman 5.5.2. Native ARM payload and emulated OCR standalone tests passed; cold standalone building needs a heartbeat, and paused-task restart failed because the installed helper reparses the state format as shell syntax. No client-scheduled BOINC task ran. See the [measured results and reproduction](../2026-10-14-buda-mac-offline-tests.md) before proceeding. On a fresh host, follow [BOINC's Mac setup](https://github.com/BOINC/boinc/wiki/Installing-Docker-on-Mac). BOINC manages its own Podman machine, separate from a Desktop user's machine.

Register a signed BUDA app version for the Mac client's actual primary platform (expected `arm64-apple-darwin__docker`, confirm from its scheduler request). Use the universal wrapper, and add an ARM science variant with the same immutable worker digest only if that image provides Linux arm64. Record the registry manifest architecture and the selected variant. The setup guide's Intel-only app registration does not cover a native arm64 BUDA client: the pinned scheduler deliberately suppresses Intel fallback for BUDA.

Require scheduling, container execution, upload, validation and collection on the Mac. If the worker digest is amd64-only, record that as a failed native-image prerequisite; do not silently replace its digest or claim that Rosetta or emulation preserves the baseline. Windows/WSL remains a separate unexecuted compatibility check.

Confirm the three existing apps and their daemons match the baseline. Keep #481 open until the intended evaluation is complete or an explicit decision ends the spike on the source-confirmed blockers.
