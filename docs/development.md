# Development

How to run and test US News Map locally. Nothing here needs an Azure account or the real newspaper data: the API serves a small **synthetic** corpus from [`fixtures/`](../fixtures/README.md), and local stand-ins cover the Azure code paths.

## Run the API and the site

Requires a stable Rust toolchain (see `rust-toolchain.toml`). The web app also needs Node.js 24.

```sh
cargo test --workspace                 # unit + API integration tests against the fixtures
cargo run -p usnm-api                  # serves the synthetic fixture corpus on :8080
curl 'localhost:8080/v1/aggregate?q=%22cross+of+gold%22&from=1896-06-01&to=1896-12-31'
curl 'localhost:8080/v1/hits?q=%22cross+of+gold%22&place=P00001&limit=5'
curl 'localhost:8080/v1/days?q=%22cross+of+gold%22&place=P00001,P00006'
```

With the API running, `cd web && npm ci && npm run dev` serves the site on `http://localhost:5173` (see [`web/README.md`](../web/README.md)).

## Against Quickwit

The same fixtures can be served by [Quickwit 0.9.1](https://github.com/quickwit-oss/quickwit/releases/tag/v0.9.1), the pinned version, set up the way production runs it. `scripts/dev/quickwit-fixtures.sh` loads the fixture indexes with a writer node, stops it, and starts a read-only searcher that polls the metastore:

```sh
url=$(QUICKWIT_BIN=/path/to/quickwit scripts/dev/quickwit-fixtures.sh --workdir /tmp/qw)
QUICKWIT_URL=$url cargo test -p usnm-search --test quickwit_parity   # Quickwit vs the reference backend
USNM_BACKEND=quickwit USNM_QUICKWIT_URL=$url cargo run -p usnm-api
kill "$(cat /tmp/qw/quickwit.pid)"
```

Without `QUICKWIT_URL`, the parity tests skip; CI runs them in the `quickwit` job. Quickwit has no fuzzy term queries, so on this backend `/v1/meta` reports `"fuzzy": false` and fuzzy queries return 422 (05 §5.5.1).

## Ingest pipeline

`usnm-ingest` turns LoC batch archives into a published version: `enqueue` records a batch list, `curate` claims queued batches and writes curated Parquet, and `release` builds a new index (a delta, or a base with `--full`) and its reference snapshot, then writes `current.json` last. `run` does all three. To try it on the synthetic corpus, rebuilt as two batch archives:

```sh
repo=$PWD                                                       # run from the repository root
python3 scripts/dev/fixture-batches.py --out-dir /tmp/usnm-ingest   # archives, batches.json, reference/catalog/
cd /tmp/usnm-ingest
cargo run --manifest-path "$repo/Cargo.toml" -p usnm-ingest -- \
  --state-file state.json --curated curated --reference reference \
  run --list batches.json --synthetic --index-dir reference/indexes
USNM_DATA_DIR=/tmp/usnm-ingest/reference USNM_STATE_FILE=/tmp/usnm-ingest/state.json \
  cargo run --manifest-path "$repo/Cargo.toml" -p usnm-api
```

With `USNM_STATE_FILE`, the API's `/v1/status` (and the site's `/datasets` page) reads the local pipeline state; in Azure it reads Cosmos (`USNM_COSMOS_ENDPOINT`). To index into Quickwit instead, replace `--index-dir …` with `--quickwit-bin /path/to/quickwit --quickwit-metastore file:///tmp/usnm-ingest/qw --quickwit-index-root file:///tmp/usnm-ingest/qw`; the pipeline runs its own writer node for the release.

In Azure the same binary runs from the `usnewsmap-ingest` image with `--cosmos https://{account}.documents.azure.com/`, Blob URLs for `--curated` and `--reference`, and `--quickwit-metastore azure://qw-index --quickwit-index-root azure://qw-index`. The store, state and index-target options also read environment variables (`USNM_CURATED_URL`, `USNM_REFERENCE_URL`, `USNM_COSMOS_ENDPOINT`, `USNM_QUICKWIT_*`, …; see `usnm-ingest --help`). `enqueue` with no `--list` reads LoC's own batch listing; add `--batches name_ver01,…` to take only some.

## Against local Azure stand-ins

`scripts/local-azure/` runs the Blob and Cosmos code paths without an Azure account. That includes Entra tokens, conditional Cosmos writes, and several `curate` workers sharing one queue, which the `--state-file` store can't do because it serves one process at a time. It starts:

- [Azurite](https://github.com/Azure/Azurite) for Blob Storage, in OAuth mode, so it checks each token's audience, issuer and expiry
- `shim.py`: a managed identity endpoint, and a plain-HTTP proxy in front of Azurite's HTTPS port (the Rust clients only trust public CAs)
- `cosmos.py`: the Cosmos DB REST calls `CosmosDocs` makes, with etags, 409/412, query paging and session tokens. It only accepts Entra tokens for Cosmos. It follows our reading of the REST API, so the first run against a real account is still the real test.

It needs `azurite-blob` on `PATH` (`npm install -g azurite`), Python 3 and `openssl`.

```sh
. "$(scripts/local-azure/up.sh --workdir /tmp/usnm-azure)"     # starts everything, exports the USNM_* and IDENTITY_* variables
cargo build --release -p usnm-ingest -p usnm-api
ingest=target/release/usnm-ingest
$ingest enqueue --batches dlc_zurich_ver04,dlc_misctopsn83025894_ver01,dlc_misctopsn83021129_ver01
$ingest curate & $ingest curate & wait                  # two workers, one queue
$ingest titles-sync --lccns sn85042252,sn83025894,sn83021129
$ingest release --index-dir /tmp/usnm-azure/indexes
USNM_DATA_DIR=/tmp/usnm-azure target/release/usnm-api   # reads the snapshot from Azurite, caches responses there
scripts/local-azure/down.sh --workdir /tmp/usnm-azure   # data stays; up.sh on the same directory resumes
```

`$ingest duplicates` reports the pages that ship in more than one curated batch (JSON on stdout; changes nothing). `titles-sync` with no `--lccns` or `--list` fetches every title in LoC's listing (hours); `run --batches …` syncs only the titles for those batches. Set these on `up.sh` to change the Cosmos stand-in: `COSMOS_PAGE=2` exercises query continuation, `COSMOS_429=0.1` throttles a tenth of requests, and `COSMOS_SEED=state.json` starts from a `--state-file` run.

## Checks

The formatting, lint, test and build commands CI runs are listed in [CONTRIBUTING.md](../CONTRIBUTING.md), and [What CI runs](#what-ci-runs) says which job runs what, when, and what a pull request needs green. The web app's end-to-end tests are described in [`web/README.md`](../web/README.md).

Markdown-only PRs run formatting and the private-address scan, not application or
BOINC builds. BOINC build workflows exclude `**/*.md` after their positive path
patterns; mixed code-and-doc changes still build. CodeQL selects no languages
for Markdown-only changes.

Run `npm run format` in `web/` before pushing. It runs Prettier (pinned in `web/package.json`) from the repository root, with the root's `.prettierrc.json` and `.prettierignore`: it formats the web app's TypeScript, JavaScript, CSS, HTML and JSON, except `package-lock.json`, build output and `web/src/examples.json`, which keeps each example's view on one line. It also formats every Markdown file in the repository except the reports under `docs/reports/`, because pandoc builds their PDFs and sizes table columns from the Markdown's layout. In Markdown it keeps prose lines and code blocks as written. It leaves data JSON outside `web/`, YAML, Bicep, Rust and Python alone. `npm run format:check` is the check CI runs. Where Prettier's layout would change how a Markdown block renders, wrap the block in `<!-- prettier-ignore-start -->` and `<!-- prettier-ignore-end -->`.

### What CI runs

`.github/workflows/ci.yml` starts on every pull request, every push to `main` and every manual dispatch. It has no path filter, so a required check always reports. The first table lists its jobs in the order the file has them, under the `name:` that GitHub shows in the list of checks. The second lists the other fourteen workflows in `.github/workflows/`.

**When the jobs run.** The `changes` job (`scripts/ci/changes.sh`) works out what the change touches and sets one true or false output for each area; the table names the output in backticks. Every job but `no private addresses` waits for `changes` and runs only when its output is true. A job skipped this way shows as skipped, which satisfies a required check. A pull request is compared with its base branch, and a push to `main` with the commit before the push. When the changed files can't be worked out, everything runs.

- A change to Markdown or to `docs/` alone starts `changes`, `no private addresses` and, for Markdown, `markdown`.
- A manual dispatch (the bootstrap script makes one to publish images) runs every job except `ops data` and `stack change needs a provision`; the jobs marked `main` only are skipped on another branch. With `scope: ocr-worker`, which needs `main`, it runs only `rust`, `queue`, the three OCR worker jobs and the two jobs that always run.
- An edit to `ci.yml` outside a job (triggers, `env`) or in `changes` runs everything. An edit inside another job runs that job and the others that read the same outputs. The same holds for the actions in `.github/actions/` that `ci.yml` calls: `setup-rust`, `setup-node-web` and `build-check-image`.

**What must be green.** The "Protect main" ruleset requires the eight jobs marked "yes". It matches them by `name:`, so renaming one means changing the ruleset too; `scripts/ci/test_changes.py` checks that these names still exist. The ruleset does not list the others, but a red one is a real failure: `no private addresses` enforces a rule in [CONTRIBUTING.md](../CONTRIBUTING.md), and `publish and roll out` on `main` waits for most of them. Treat any red job as yours to fix.

Times are the median for the job over the most recent 75 runs of `ci` on `main` (23 October 2026) in which it ran. `web` is from a pull request run, because it ran in none of those, and `fixtures` had no recent run. A run lasts as long as its slowest job: about 10 minutes without `quickwit`, about 20 with it, and under a minute for documentation.

**To get a green pull request**, run the checks for what you changed before you push. If one still fails, the failing step's name in the check says what it tests.

1. See which jobs your branch starts. The script prints the changed files, then each output. It needs `cargo` and `jq` to decide which crates a change reaches; without them it runs more rather than less.

   ```sh
   git fetch origin main
   GITHUB_EVENT_NAME=pull_request GITHUB_BASE_REF=main scripts/ci/changes.sh
   ```

2. Run the commands that match. [CONTRIBUTING.md](../CONTRIBUTING.md#run-the-checks) has the Rust, web and infrastructure commands as `rust`, `web` and `infra` run them, apart from the ones below. Node is 24.
3. Format Markdown: `npm run format` in `web/`; `web` and `markdown` run `npm run format:check`.
4. Commit no private address anywhere: `scripts/ci/no-private-addresses.sh`.

### Script tests

`scripts/ci/run-unit-tests.py` runs every `scripts/**/test_*.py`, so a new test file runs in CI without being added to a list in `ci.yml` (the `infra` job's "script unit tests" step). Run it from anywhere in the checkout; `--list` shows what it would run. `python3 -m unittest discover -s scripts` is not a substitute: with no `__init__.py` under `scripts/` it reads only the files directly in `scripts/`, where no test sits, so it finds none of those in `scripts/boinc/`, `scripts/azure/` and the other directories. The runner leaves out the tests that need something the generic job lacks (Pillow, the ops venv, the C++ headers, or a workflow of their own) and the archived scripts under `scripts/archive/`, with the reason for each in its `EXCLUDE` table; those run in steps of their own. Run one file with `python3 -m unittest -v scripts/boinc/test_install.py`.

### Data that is not in the tree

Report data (`docs/reports/*/data`, `docs/data`) and the benchmark's page images and raw results (`ocr/bench`) are release assets, not tracked files: `scripts/ops/data-assets.sh --fetch --set report-data` or `--set bench-assets` downloads the set named in `ops/data-assets.json`, checks its sha256 and extracts it in place. The `publish data assets` workflow publishes a changed set from a commit. See [reports/README.md](reports/README.md).

### JSON data files

Each JSON data file in the repository has a spec and a check that CI runs:

| File                                             | Spec and check                                                                                                                                                                                                                                                           |
| ------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `catalog/overrides/*.json`                       | Parsed into `deny_unknown_fields` structs in usnm-ingest, with per-field audit checks and sorted keys (`cargo test -p usnm-ingest`)                                                                                                                                      |
| `ops/data-assets.json`                           | The release tag and tarball sha256 of each data set `scripts/ops/data-assets.sh` fetches (`report-data`, `bench-assets`); shape and sorted keys checked by `scripts/ops/test_data_assets.py`                                                                             |
| `ops/version-snapshots/*.json`                   | `ops/version-snapshots/schema.json`, checked by `scripts/ops/check-version-snapshots.py` (CI job `ops`)                                                                                                                                                                  |
| `ops/index-history.json`                         | `ops/index-history.schema.json` and sorted keys at every level, checked by `scripts/ops/check-index-history.py` (CI job `ops`); run it on `scripts/ops/reconstruct-index-history.py`'s output before replacing the file                                                  |
| `web/src/examples.json`                          | `examples.test.ts` checks every entry has exactly the fields of `Example` (`web/src/examples.ts`) and a `view` of `ViewState` fields (`npm test`); the API's `prewarm::Example` rejects unknown fields (`cargo test -p usnm-api prewarm`)                                |
| `infra/env/*.json`                               | `infra/env/schema.json`, checked by `scripts/lib/env_settings.py --check` (CI job `infra`): only public settings the schema lists, typed, keys sorted, laid out as `json.dumps(indent=2)` writes it; the schema lists exactly the settings `infra/main.bicepparam` reads |
| `infra/workbooks/*.json`                         | `scripts/ci/check-workbooks.py` (CI job `infra`): each file `infra/modules/workbooks.bicep` loads parses, has `version` and `items`, and names the module's workspace placeholder instead of a resource id                                                               |
| `fixtures/data/**`, `fixtures/skew-vectors.json` | Regenerated and compared (`python3 fixtures/generate.py`, `cargo test -p usnm-core --test skew_vectors`)                                                                                                                                                                 |

`check-version-snapshots.py` and `check-index-history.py` need `fastjsonschema` (`scripts/ci/requirements-ops.txt`); `check-workbooks.py` and `scripts/lib/env_settings.py` use only the standard library, so `python3 scripts/ci/check-workbooks.py` and `python3 scripts/lib/env_settings.py --check` run as they are:

```sh
python3 -m venv /tmp/ops && /tmp/ops/bin/pip install --require-hashes --no-deps -r scripts/ci/requirements-ops.txt
/tmp/ops/bin/python scripts/ops/check-version-snapshots.py
/tmp/ops/bin/python scripts/ops/check-index-history.py
/tmp/ops/bin/python -m unittest scripts/ops/test_check_version_snapshots.py scripts/ops/test_check_index_history.py
```
