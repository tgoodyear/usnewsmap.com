# Development

How to run and test US News Map locally. Nothing here needs an Azure account or the real newspaper data: the API serves a small synthetic corpus from [`fixtures/`](../../fixtures/README.md), and local stand-ins cover the Azure code paths.

## Run the API and the site

You need the stable Rust toolchain (`rust-toolchain.toml` pins the `stable` channel with `rustfmt` and `clippy`) and, for the web app, Node.js 24.11 or later (`web/package.json`, `engines`).

```sh
cargo test --workspace                 # unit and API integration tests against the fixtures
cargo run -p usnm-api                  # serves the synthetic fixture corpus on :8080
curl 'localhost:8080/v1/aggregate?q=%22cross+of+gold%22&from=1896-06-01&to=1896-12-31'
curl 'localhost:8080/v1/hits?q=%22cross+of+gold%22&place=P00001&limit=5'
curl 'localhost:8080/v1/days?q=%22cross+of+gold%22&place=P00001,P00006'
```

With the API running, `cd web && npm ci && npm run dev` serves the site on `http://localhost:5173` ([`web/README.md`](../../web/README.md)). The API's settings are in [Configuration](configuration.md).

## Against Quickwit

The same fixtures can be served by [Quickwit 0.9.1](https://github.com/quickwit-oss/quickwit/releases/tag/v0.9.1), the pinned version, set up the way production runs it. `scripts/dev/quickwit-fixtures.sh` loads the fixture indexes with a writer node, stops it, and starts a read-only searcher that polls the metastore:

```sh
url=$(QUICKWIT_BIN=/path/to/quickwit scripts/dev/quickwit-fixtures.sh --workdir /tmp/qw)
QUICKWIT_URL=$url cargo test -p usnm-search --test quickwit_parity   # Quickwit against the reference backend
USNM_BACKEND=quickwit USNM_QUICKWIT_URL=$url cargo run -p usnm-api
kill "$(cat /tmp/qw/quickwit.pid)"
```

Without `QUICKWIT_URL` the parity tests skip; CI runs them in `quickwit (parity)`. The ingest pipeline test runs against a writer node of its own: `QUICKWIT_BIN=/path/to/quickwit cargo test -p usnm-ingest --test pipeline --locked`. Quickwit has no fuzzy term queries, so on this backend `/v1/meta` reports `"fuzzy": false` and fuzzy queries return 422 (05 §5.5.1).

## Ingest pipeline

`usnm-ingest` turns LoC batch archives into a published version: `enqueue` records a batch list, `curate` claims queued batches and writes curated Parquet, and `release` builds a new index (a delta, or a base with `--full`) and its reference snapshot, then writes `current.json` last. `run` does all three. To try it on the synthetic corpus, rebuilt as two batch archives:

```sh
repo=$PWD                                                       # run from the repository root
python3 scripts/dev/fixture-batches.py --out-dir /tmp/usnm-ingest   # archives, batches.json, reference/catalog/
cd /tmp/usnm-ingest
cargo run --manifest-path "$repo/Cargo.toml" -p usnm-ingest -- \
  --state-file state.json --curated curated --reference reference \
  run --list batches.json --synthetic --index-dir reference/indexes
USNM_DATA_DIR=/tmp/usnm-ingest/reference USNM_STATE_FILE=/tmp/usnm-ingest/state.json \
  cargo run --manifest-path "$repo/Cargo.toml" -p usnm-api
```

With `USNM_STATE_FILE`, the API's `/v1/status` (and the site's `/datasets` page) reads the local pipeline state; in production it reads Cosmos (`USNM_COSMOS_ENDPOINT`). To index into Quickwit instead, replace `--index-dir …` with `--quickwit-bin /path/to/quickwit --quickwit-metastore file:///tmp/usnm-ingest/qw --quickwit-index-root file:///tmp/usnm-ingest/qw`; the pipeline runs its own writer node for the release.

In an environment with ingest jobs, the same binary runs from the `usnewsmap-ingest` image with `--cosmos https://{account}.documents.azure.com/`, Blob URLs for `--curated` and `--reference`, and `--quickwit-metastore azure://qw-index --quickwit-index-root azure://qw-index`. Prod has no ingest jobs (`USNM_INGEST_JOBS` is off): its releases run on an on-prem host through `scripts/onprem/release.sh`, which builds with a local state file, staged reference data and `file://` Quickwit paths, then copies the version to Azure with `publish-staged` ([full rebuild on-prem](../operations/rebuild-and-index-storage.md#full-rebuild-on-prem)). The store, state and index-target options also read environment variables (`USNM_CURATED_URL`, `USNM_REFERENCE_URL`, `USNM_COSMOS_ENDPOINT`, `USNM_QUICKWIT_*`, …; see `usnm-ingest --help`). `enqueue` with no `--list` reads LoC's own batch listing; add `--batches name_ver01,…` to take only some.

## Against local Azure stand-ins

`scripts/local-azure/` runs the Blob and Cosmos code paths without an Azure account, including Entra tokens, conditional Cosmos writes, and several `curate` workers sharing one queue, which the `--state-file` store can't do because it serves one process at a time. It starts:

- [Azurite](https://github.com/Azure/Azurite) for Blob Storage, in OAuth mode, so it checks each token's audience, issuer and expiry;
- `shim.py`: a managed identity endpoint, and a plain-HTTP proxy in front of Azurite's HTTPS port (the Rust clients only trust public CAs);
- `cosmos.py`: the Cosmos DB REST calls `CosmosDocs` makes, with etags, 409/412, query paging and session tokens. It accepts only Entra tokens for Cosmos. It follows our reading of the REST API, so a real Cosmos account may still behave differently.

It needs `azurite-blob` on `PATH` (`npm install -g azurite`), Python 3 and `openssl`.

```sh
. "$(scripts/local-azure/up.sh --workdir /tmp/usnm-azure)"     # starts everything, exports the USNM_* and IDENTITY_* variables
cargo build --release -p usnm-ingest -p usnm-api
ingest=target/release/usnm-ingest
$ingest enqueue --batches dlc_zurich_ver04,dlc_misctopsn83025894_ver01,dlc_misctopsn83021129_ver01
$ingest curate & $ingest curate & wait                  # two workers, one queue
$ingest titles-sync --lccns sn85042252,sn83025894,sn83021129
$ingest release --index-dir /tmp/usnm-azure/indexes
USNM_DATA_DIR=/tmp/usnm-azure target/release/usnm-api   # reads the snapshot from Azurite, caches responses there
scripts/local-azure/down.sh --workdir /tmp/usnm-azure   # data stays; up.sh on the same directory resumes
```

`$ingest duplicates` reports the pages that ship in more than one curated batch (JSON on stdout; changes nothing). `titles-sync` with no `--lccns` or `--list` fetches every title in LoC's listing (hours); `run --batches …` syncs only the titles for those batches. Set these on `up.sh` to change the Cosmos stand-in: `COSMOS_PAGE=2` exercises query continuation, `COSMOS_429=0.1` throttles a tenth of requests, and `COSMOS_SEED=state.json` starts from a `--state-file` run.

## Checks

[CONTRIBUTING.md](../../CONTRIBUTING.md#run-the-checks) lists the Rust, web and infrastructure commands CI runs. [What CI runs](#what-ci-runs) says which job runs what, when, and what a pull request needs green. The web app's end-to-end tests are in [`web/README.md`](../../web/README.md).

Run `npm run format` in `web/` before pushing. It runs Prettier (pinned in `web/package.json`) from the repository root with the root's `.prettierrc.json` and `.prettierignore`. It formats the web app's TypeScript, JavaScript, CSS, HTML and JSON, except `package-lock.json`, build output and `web/src/examples.json`, which keeps each example's view on one line. It also formats every Markdown file in the repository except the reports under `docs/reports/`, whose PDFs pandoc builds with table columns sized from the Markdown's layout. In Markdown it keeps prose lines and code blocks as written. It leaves data JSON outside `web/`, YAML, Bicep, Rust and Python alone. `npm run format:check` is the check CI runs. Where Prettier's layout would change how a Markdown block renders, wrap the block in `<!-- prettier-ignore-start -->` and `<!-- prettier-ignore-end -->`.

`python3 scripts/ci/check-doc-links.py` checks local Markdown link targets and heading anchors under `docs/`, without network requests; the `web` and `markdown` jobs run it beside formatting. Data removed from the tree must be linked as its published release asset, with extraction instructions and a verified member list, not as a local file that no longer exists.

### What CI runs

`.github/workflows/ci.yml` starts on every pull request, every push to `main` and every manual dispatch. It has no path filter, so a required check always reports. Instead its `changes` job (`scripts/ci/changes.sh`) works out what the change touches and sets an output for each area, named in backticks below. Every other job but `no private addresses` waits for `changes` and runs only when its output is true; a job skipped this way reports as skipped, which satisfies a required check. A pull request is compared with its base branch, and a push to `main` with the commit before the push. When the changed files can't be worked out, everything runs.

- A change to Markdown or `docs/` alone runs `changes`, `no private addresses`, `worker and BOINC checks` (which then expects all its children skipped) and, for Markdown, `markdown`. The BOINC build workflows exclude `**/*.md` after their path patterns, and CodeQL selects no language, so a mixed code-and-docs change still builds and a docs-only one doesn't.
- A manual dispatch (`scripts/azure/bootstrap.sh` makes one to publish images) runs every job except `ops data`, which runs only when its own files change, and `stack change needs a provision`, which runs only on a push. Jobs marked `main` only are skipped on another branch. With `scope: ocr-worker`, which needs `main`, it runs only `rust`, `queue`, the OCR worker jobs and the jobs that always report.
- An edit to `ci.yml` outside a job (triggers, `env`) or in `changes` runs everything. An edit inside another job runs that job and the others that read the same outputs. The composite actions `ci.yml` calls from `.github/actions/` count as part of their jobs: `setup-rust` (the stable toolchain without debug information for dev and test builds, and the Cargo cache, saved only on `main`), `setup-node-web` (Node 24 with the npm cache) and `build-check-image` (one image built into the local Docker daemon, not pushed).

#### Jobs and required checks

The "Protect main" ruleset requires the nine checks marked "yes" below. It matches them by name, so renaming one means changing the ruleset too; `scripts/ci/test_changes.py` checks that the names still exist. Four of them are aggregates that run nothing themselves (#1232): `quickwit (parity, ingest release)`, `container image builds`, `infra (bicep lint, build)` and `worker and BOINC checks` fail when a selected child job fails, is cancelled or is skipped unexpectedly. Require the aggregates; their children are path-filtered. Fix any red job, required or not: `no private addresses` enforces a rule in [CONTRIBUTING.md](../../CONTRIBUTING.md), and `publish and roll out` waits for most jobs.

Superseded pull-request runs are cancelled; runs on `main` and dispatched runs are not. Rust test binaries' durations appear in the `rust` and `quickwit` job summaries. The [hosted-CI note](../notes/2026-10-26-hosted-ci-critical-path.md) (26 October 2026) measured run times before and after the jobs were split into parallel children (#1232).

`publish and roll out` waits for `changes`, `rust`, `queue`, `page language samples`, `quickwit`, `fixtures`, `ops`, `image`, `infra`, `web`, `markdown`, `web end-to-end` and `no private addresses`. A skipped one doesn't block it; a failed or cancelled one does. The BOINC and OCR worker jobs are not among them. It publishes for the commit `main` points at, and for an older commit when none of the commits `main` has gained since then change `image`. Otherwise it publishes nothing, so a slower run for an older commit can't replace newer images. The second case exists because the newer runs publish nothing: without it, a scripts-only merge right after an API change left the change undeployed (#1063). `scripts/ci/head-of-main.sh --unless-changed image` decides, classifying the newer commits with `changes.sh`.

`ocr worker release` follows the same rule for the worker and the dashboard, with `scripts/ci/head-of-main.sh --unless-changed ocr_worker,ocr_dash` (#1074); the job checks out the full history for it. A newer commit that changes either build releases in its own run, and this one skips.

Every IndexNow notification needs the public API to report a sitemap checkpoint current for its serving build. After a roll, the notification also waits up to 30 minutes for Azure to generate a checkpoint for the deployed build, then requires the public sitemap to match its URLs and page content, so a shared Azure checkpoint can't make an older public API look ready. If Azure sign-in, sitemap discovery or either readiness check fails, the notification is skipped and `indexnow.yml` retries it hourly; it never bypasses the public-sitemap check or fails the run. Acknowledgements are kept on the `indexnow-state-<environment>` branches (`scripts/ci/indexnow.sh`).

#### Other workflows

The other workflows in `.github/workflows/` start from their own `paths:` filter, a schedule, a dispatch or the end of a `ci` run on `main`. None is a required check. A pull request that touches none of a workflow's paths gets no run from it; `codeql.yml` has no path filter. Most image workflows then run an `inputs` job (not named `changes`, the required check's name) that calls `scripts/ci/changes.sh`, and build only when the output for their image is true; `boinc-iris.yml` and `boinc-train.yml` build on their `paths:` filter alone. `boinc-qwen.yml` and `boinc-surya.yml` also read which models or variants to build (`boinc_qwen_models`, `boinc_surya_variants`; #1585): a change that reaches only the `usnm-boinc` build stage both share builds Qwen 2b and Surya CUDA alone, and one that touches the image's own directory or scripts, its workflow or its build action builds 8b and Vulkan too. Image pushes run only on a manual dispatch from `main`, except `ocr-bench.yml`, which publishes on a push to `main` that touches its paths, and `publish-data.yml`, which publishes from whichever ref it is dispatched on.

#### Local checks before pushing

Run the checks for what you changed before you push. If one still fails, the failing step's name says what it tests.

1. See which jobs your branch starts. The script prints the changed files, then each output. It needs `cargo` and `jq` to decide which crates a change reaches; without them it runs more rather than less.

   ```sh
   git fetch origin main
   GITHUB_EVENT_NAME=pull_request GITHUB_BASE_REF=main scripts/ci/changes.sh
   ```

2. Run the commands that match. [CONTRIBUTING.md](../../CONTRIBUTING.md#run-the-checks) has the Rust, web and infrastructure commands as `rust`, `web` and `infra` run them; the table below has the rest. CI sets `RUSTFLAGS=-D warnings`, which makes rustc warnings errors in `cargo test`; `export RUSTFLAGS='-D warnings'` does the same locally, at the cost of one full rebuild.
3. Format Markdown with `npm run format` in `web/`, and check links with `python3 scripts/ci/check-doc-links.py`.
4. Commit no private address anywhere: `scripts/ci/no-private-addresses.sh`.

### Script tests

Use Python 3.12 in a virtual environment, and install the pinned picture-test dependency first: the picture tests read real Parquet fixtures with PyArrow. CI installs the same.

```sh
python3.12 -m venv /tmp/usnm-script-tests
. /tmp/usnm-script-tests/bin/activate
python -m pip install -r scripts/pictures/requirements.txt
scripts/ci/run-unit-tests.py
```

`scripts/ci/run-unit-tests.py` runs every `scripts/**/test_*.py` and `boinc/scripts/**/test_*.py`, each in its own process, so a new test file runs in CI without being added to a list in `ci.yml`. Run it from anywhere in the checkout; `--list` shows what it would run. CI runs three shards with `--shard-index N --shard-count 3`, which balances the heavy modules by measured time, and `--timings FILE` writes each module's time and outcome, which CI keeps as an artifact. With no shard flags it runs everything. `python3 -m unittest discover -s scripts` is not a substitute: with no `__init__.py` under `scripts/` it reads only the files directly in `scripts/`, where no test sits. The runner leaves out the tests that need something the generic job lacks (Pillow, the ops virtual environment, the C++ headers, or a workflow of their own) and the archived scripts under `scripts/archive/`, with the reason for each in its `EXCLUDE` table; those run in steps of their own. Run one file with `python3 -m unittest -v boinc/scripts/test_install.py`.

### Data that is not in the tree

Report data (`docs/reports/*/data`, `docs/data`) and the benchmark's page images and raw results (`ocr/bench`) are release assets, not tracked files: `scripts/ops/data-assets.sh --fetch --set report-data` or `--set bench-assets` downloads the set named in `ops/data-assets.json`, checks its SHA-256 and extracts it in place. The `publish-data.yml` workflow publishes a changed set from a commit. See [reports/README.md](../reports/README.md).

A trained OCR model is a release asset too, with its notice, provenance and `SHA256SUMS` committed under `ocr/models/<name>/`; see [`ocr/models/yidj2/`](../../ocr/models/yidj2/README.md).
